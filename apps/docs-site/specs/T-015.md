# T-015 — What a tenant table is, and the check that fails when one has no policy

*Spec written 4 September 2026 from T-015's build, recording the definition the code settled on rather than the one the ticket body guessed at. Source of truth for scope is the T-015 ticket body plus this spec. The check itself is `packages/schema/test/rls.test.ts`; decisions recorded here are taken.*

## Problem Statement

ADR 0032's isolation model is a non-owner `app_rt`, one worker login role, both under `FORCE ROW LEVEL SECURITY`, every tenant policy written `(SELECT current_workspace_id())`. The model is only as good as its coverage. A table added six months from now without a policy is not a failing test — it is a silently readable table, and nothing in the tree would notice. `[DESIGN4]` states the guarantee; this task is the gate that holds it, and it exists before most of the tables do so that it gates a schema rather than audits one.

The definition of *tenant table* is the substance. The ticket guessed "carries a `workspace_id` column". That definition is wrong in this schema, in both directions, which is why it is written down here instead.

## Solution

**A tenant table is every table `src/` declares, minus the exemption list.** Nothing else. The check is a Vitest suite in `packages/schema` running against the Testcontainers Postgres the package already exports as `@better-answers/schema/testing`, inside the workspace's `check`, so it fails on the contributor's machine before CI.

### Why not the `workspace_id` column

The column test fails in both directions here:

- `public.member` and `public.invitation` **carry `workspace_id` and are deliberately exempt** (ADR 0009's 2026-09-01 amendment). The membership read is what *validates* a workspace claim: the resolver sets `SET LOCAL app.workspace_id` from a credential and then, in the same transaction, reads the member row to check the person is in that workspace. A policy on `member` would make that read depend on the scope it exists to justify. `invitation` sits beside it: it is read by id by a person who is not yet a member of the workspace it names. The test asserts exactly this, by name, rather than letting it pass as an accident — `rls.test.ts` "carries no workspace column on Better Auth's tables" expects `false` for every identity-set table except those two.
- A future tenant table could name its scope column something else, and would then pass a column check while carrying no policy.

The declaration-minus-exemptions definition is query-evaluable without either risk: `declaredTableNames()` (`packages/schema/scripts/worker-view.ts`) reads the `PgTable` exports of `src/index.ts`, and the worker-view drift test already fails on any table in the migrated database the declarations do not know. So "declared" and "exists" are held equal elsewhere, and this check can lean on it.

### What the check asserts

Against the live catalogue — `pg_class.relrowsecurity` and `relforcerowsecurity` joined to `pg_policies`, never a parse of migration files — for every tenant table:

1. `relrowsecurity` **and** `relforcerowsecurity` are both true. `ENABLE` alone is bypassed by the table's owner, so `FORCE` is the brace on the belt of `app_rt` being a non-owner. It also catches the one thing `withRLS()` cannot emit: Drizzle has no `FORCE` API, so the line is hand-written in a custom migration, and a table whose author forgot it fails here.
2. Exactly one policy, named `<table>_workspace_isolation`. Policies are OR-combined, so a second, wider policy would widen the table silently; one policy per tenant table is the invariant.
3. That policy's `qual` **and** `with_check` both contain `current_workspace_id()` — the one seam function, never a literal and never a second function.

Zero policies is the dangerous state the ticket names, and it fails at (2): it looks configured, returns nothing, and is usually "fixed" by granting rather than by writing the policy.

The runtime behaviour is proved separately in the same file, as `[SEC3]` requires of a grant: a missing scope returns zero rows and never another tenant's, a write into another tenant's scope is refused, and the one `SECURITY DEFINER` lifecycle function refuses every role but `app_rt`, every workspace the transaction is not scoped to, and every unknown workspace.

## Implementation Decisions

### One exemption list, one reason per entry

`RLS_EXEMPTIONS` (`packages/schema/src/rls-exemptions.ts`) is a record of qualified table name to a one-line reason. It is the one place a reviewer looks, and adding an entry is a visible diff that carries its justification — never a pattern that quietly matches a new table.

The two arrays it is built from stay where their owners need them: `IDENTITY_SET` beside Better Auth's declarations in `identity-tables.ts`, `GLOBAL_TABLE_NAMES_BEYOND_IDENTITY` beside the counters in `counter-tables.ts` (both are read by migrations and documents that have nothing to do with RLS). The union of the two is exported as `EXEMPT_TABLE_NAMES`, and the suite asserts `RLS_EXEMPTIONS`'s keys equal it, in both directions, plus a non-empty reason per entry. `[TEST7]`: a name can neither gain an exemption without a reason nor keep one after its array drops it.

The existing both-ways check stays as it was and is the harder one: every declared table with RLS off is in the exemption list, and every name in the list is such a table. So the record cannot exempt a table that in fact has a policy, and a table that loses its policy cannot hide.

### Where each edge case landed

- **The identity set** (sixteen tables, ADR 0009's amendment, ADR 0032): exempt. Better Auth reads them by secret or principal id *before any workspace is known* and returns the workspace id — isolated by key, not by scope. `workspace` is in the set because the picker lists a person's workspaces before one is chosen; it holds a tenant's name, not a secret. The worker role is revoked on the whole set in migration 0005, asserted directly (`[SEC3]`).
- **Deliberately-global reference tables**: exempt, and each named. Today that is `ingress_counter` alone (`GLOBAL_TABLE_NAMES_BEYOND_IDENTITY`) — the pre-authentication per-IP and per-email counter, which runs before a workspace exists to scope it by. Its sibling `mcp_call_counter` is a tenant table and carries the ordinary policy, because a token always belongs to a workspace.
- **Join tables**: no special case. `oauth_client_resource` joins two global records and is exempt as one of them; a join table between two tenant rows is a tenant table and carries `workspace_id` and the policy like any other. The definition needs no clause for them.
- **Partitioned children** (`index.chunk`'s per-workspace list partitions): **the policy is asserted on the parent only, and the children are unreachable by privilege.** A parent policy does not apply to a query aimed at a child table, and migration 0000's default privileges would have granted the runtime roles DML on a partition created later — so `create_workspace_partition` issues `REVOKE ALL ON "index".<partition> FROM app_rt, worker_rt` inside the same transaction that creates it (migration 0002). The proof is two tests: chunk rows scope correctly through the parent, and a direct query against a partition is refused with `permission denied` under *any* scope, including the owning tenant's. The children are also outside the declared set (`declaredTableNames()` knows the parent, and the introspection excludes `chunk\_%`), so they are neither tenant tables nor exemptions — they are behind a closed door.

### Where it runs

`packages/schema`'s `test` script, therefore its `check`, therefore the root `check`. The suite starts one migrated Testcontainers Postgres for the file and rolls back each behavioural test; the catalogue assertions read `pg_class` and `pg_policies` directly on the pool.

## Testing Decisions

**A good test crosses the seam a caller crosses and asserts what the system does for whom.** Two seams carry this spec, and both already exist.

1. **The catalogue**, read as Postgres holds it after the journal has run — the coverage assertions above. This is the seam that cannot be fooled by runtime DDL, which is the reason the ticket named it: the lifecycle definer function is the one runtime-DDL path, and its output is checked the same way.
2. **`app_rt` against a real table** — the zero-rows and refused-write proofs, and the worker role's refusals, run as the runtime roles themselves rather than as the container's superuser. Seeding runs through the factory as superuser (which bypasses RLS by design); every assertion runs under `SET LOCAL ROLE`.

The exemption-list drift check is a pure unit test with no container, so it fails in milliseconds when someone edits one array and not the record.

## Out of Scope

- **Generating policies by DDL trigger.** The Supabase guidance that prompted this task recommends exposing an `api` schema and generating RLS by trigger. The schema half does not transfer — that advice exists because PostgREST serves a schema over HTTP, and this platform has no PostgREST: Hono and Drizzle hold the connection, so `public` is never network-reachable, and Drizzle keeps owning `public` (ADR 0007). The coverage half is what this task takes, as a check that fails rather than DDL nobody reviewed.
- Any change to the policy shape, the seam function, or the role seam — those are ADR 0032 and `T-003`.
- Column-level or row-level checks beyond the tenant scope predicate.

## Further Notes

- **Facts a fresh session would otherwise rediscover:** `withRLS()` cannot emit `FORCE ROW LEVEL SECURITY` (no Drizzle API), so it is a hand-written line in a custom migration and the catalogue test is the only thing pairing them; `declaredTableNames()` reads `src/index.ts`'s exports, so a table declared in a file that `index.ts` does not re-export is invisible to this check and to the worker-view drift test both; the partition children are excluded from introspection by the `chunk\_%` pattern, deliberately.
- **GitNexus impact analysis** was unavailable on the day this landed (index locked); the blast radius was reasoned manually and is small: one new module, one added re-export, and a test-only change of which constant the suite reads.
