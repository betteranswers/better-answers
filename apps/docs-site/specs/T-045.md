# T-045 — One origin for the SPA and the authorization server

*Spec written 3 September 2026 from the T-045 grilling (`.scratch/session-audit-2026-09-03/t-045-grill.md`, three rounds, frontier empty; inputs `seam-review.md` §5, ADR 0008, 0009, 0022, T-037's PR #19). Source of truth for scope is the T-045 ticket body plus this spec. Decisions recorded here are taken; do not re-open them.*

## Problem Statement

The product answers on two hostnames that must share one session. The single-page app, sign-in and the workspace picker live on `app.`; the OAuth 2.1 authorization server and the MCP surface live on `mcp.`. To make a session made on `app.` answer the OAuth flow on `mcp.`, the session cookie is scoped to the apex, so a browser sends the product's bearer to every subdomain of the apex, present and future, and to any of them served by a third party. The reason the two hosts were split, Cloudflare Access in front of `app.`, was removed on 2 September 2026. What remains of the split is cost: two trusted origins, a dual-host fence entry for the flow's resume, a cross-origin consent hop, a fourth hostname for T-005's tunnel and rate-limit rules, and a consent flow that cannot be proved in the browser suite because the loopback estate has two hosts and a host-only cookie.

The issuer URL a Claude connector registers against is `mcp.`'s origin. No client credential exists yet, so the change is cheapest now and impossible to make quietly later.

## Solution

One origin. The SPA, sign-in, the picker, consent, the authorization server's endpoints, discovery, the key set and the MCP surface all answer on `app.<apex>`. The MCP surface's address becomes `app.<domain>/mcp`. `agent.` stays the machine route and the apex keeps answering nothing. The session cookie becomes Better Auth's own host-only `__Secure-` cookie; the apex-cookie configuration is deleted. The hostname fence becomes a path fence on the app host with one hostname fewer, and consent keeps its own entry with a navigation-only fence on its POST. The browser suite proves sign-in and the MCP consent flow on that one origin. The MCP prototype path is re-proved against the real claude.ai over a Cloudflare quick tunnel on the new issuer. One new ADR states the decision; the three ADRs it touches gain a one-line amendment pointing at it.

Sign-in methods were decided in the same grilling and are recorded here for the record they create: email code or Microsoft, never a password. Microsoft sign-in is its own task after this one.

## User Stories

### The person in a browser

1. As a workspace member, I want to sign in once on `app.` and have that session answer the connector's OAuth flow, so that connecting Claude never asks me to sign in a second time.
2. As a workspace member, I want my session cookie sent only to the product's own host, so that a documentation site or any future subdomain never receives it.
3. As a person connecting Claude, I want the consent page on the same origin as the product, reached by a navigation and answered by a redirect, so that the flow is one origin end to end and nothing hops between hosts.
4. As a person connecting Claude, I want the consent page to be a page of its own and not a screen inside the product's shell, so that a decision to grant access is never dressed as an ordinary screen.
5. As a person connecting Claude for the second time from the same client, I want the platform to either show consent again or skip it on the strength of my earlier answer, and to say in the browser suite which of the two it does, so that the behaviour is a proven fact rather than a guess.
6. As a person whose credentials an Admin has revoked, I want consent refused on the one origin exactly as it was on two, so that the collapse loses no refusal.
7. As a person in several workspaces, I want the picker to resume the OAuth flow on the one origin exactly as before, so that the collapse changes nothing I can see.

### The connector and the MCP surface

8. As a Claude host, I want the issuer, the protected-resource document, the authorization-server metadata, the key set and the MCP endpoint all on the app origin, so that discovery from `app.<domain>/mcp` finds everything without a second host.
9. As a Claude host, I want every access token's audience to equal the MCP URL on the app origin, so that a token minted for this surface is bound to the address I registered.
10. As a Claude host, I want the CIMD allow-list and PKCE unchanged by the collapse, so that a code obtained on the one origin still lands only at Claude's own redirect.
11. As the owner, I want the prototype path re-proved against the real claude.ai on the new issuer before T-005's first deploy, so that the first client credential is created against an issuer that will not change.

### The estate

12. As the operator, I want `PUBLIC_URL` to be the app origin and `APP_HOSTNAME` derived from it, so that there is one truth for the product's host and nothing to type twice on deploy day.
13. As the operator, I want the app to refuse to start unless `PUBLIC_URL`, `AGENT_HOSTNAME` and `APEX_HOSTNAME` are present, well formed and different, so that a missing hostname stops the process rather than opening it.
14. As the operator, I want T-005's tunnel rules, rate-limit rules and uptime checks to name three hostnames and paths on `app.`, so that the deploy unit describes the estate that exists.
15. As the operator, I want the apex to go on answering nothing and `agent.` to go on carrying only the share agent's surface, so that the collapse touches one boundary and not three.

### The attacker

16. As a script on the app origin, I want to be unable to complete consent with a fetch, so that a same-origin script cannot grant a client access on the person's behalf.
17. As a page on another origin, I want to be unable to post consent, request a code or start a sign-in for someone, so that the fences that held across two hosts hold on one.
18. As a request on a hostname the deploy unit never named, or on the apex, or carrying a hostname only in a forwarded header, I want to be refused before any body is read, so that the second fence holds as it did.

### The builder and the reviewer

19. As a builder, I want the hostname fence to be one list of path surface to hostnames to reason, one entry fewer and one role fewer, so that what is true is read in one place and tested both ways.
20. As a builder, I want the hostname test, the config test, the endpoint snapshot and the OAuth-flow suite re-cut to the one origin, so that the suite states the estate that exists rather than the one that did.
21. As a builder, I want the browser suite's loopback estate to have one product host, so that the consent flow is provable in a real browser.
22. As a builder, I want the harness's default client to speak to the app origin, so that a test written after this spec reads naturally and one written before it still passes or fails for a stated reason.
23. As a reviewer, I want one new ADR that states the origin decision, the consent reasoning and the two written triggers, and one-line amendments on the three ADRs it supersedes, so that the decision is read in one place and the chronological convention holds.
24. As a reviewer, I want the ADR index to gain the new row and change the three amended rows in the same commit, so that the index test passes and the live conclusion is never stale.
25. As a reviewer, I want the `[SEC3]` adversarial pass recorded in the PR body, so that the collapse's threat model is written where it can be checked.
26. As the owner, I want the words *MCP surface* and *sign-in* in the glossary to match what the code does, so that the interface, the documents and the tests agree.

## Implementation Decisions

### The origin (grilling Q1, Q2, Q7)

- **Everything on `app.`.** The SPA, the tRPC mount, Better Auth's handler, the consent page, `/oauth2/*`, `/.well-known/*`, `/jwks` and `/mcp` answer on one origin. The two alternatives, `mcp.` kept as a bearer-only resource host and two hosts plus `docs.` moved off the apex, were rejected: the first keeps a second document-serving host and a four-hostname fence for one bearer path; the second leaves the future-subdomain exposure and the unprovable consent flow.
- **`PUBLIC_URL` is the app origin.** `APP_HOSTNAME` is derived from it through the fence's own reading of a host, exactly as `mcp.` was derived by T-039. `AGENT_HOSTNAME` and `APEX_HOSTNAME` remain bootstrap env. The three must differ, the derived one included; the app refuses to start otherwise. The `mcp` hostname role and the `mcp` field of the public-hostnames shape are deleted.
- **No public docs site.** The ops documents' public halves live in the docs-site source, unrendered (T-044). ADR 0022's line placing `docs.` on Cloudflare Pages is struck. `.cubic/wiki` is orientation only.
- **The MCP surface's address is `app.<domain>/mcp`.** The protected-resource document's `resource`, every token's audience, the client-registration default and allowed resources, and the glossary entry all say so.

### The fence (grilling, assumed and unobjected)

- The fence stays one ordered list of surface to hostnames to reason, a catch-all last, tested both ways. It loses the `mcp` role and the dual-host resume entry.
- Entries after the change: the share agent's surface on `agent`; `/mcp`, `/.well-known/*`, `/jwks` and `/oauth2/*` on `app`; `/consent` on `app` as its own entry; `/health` on `app` and the loopback; the apex with an empty path set; the catch-all on `app`. The `/sign-in` and `/choose-workspace` entry and the `/oauth2/continue` entry fold into the catch-all, because the reason each existed, separating the product's screens from the issuer's host, no longer names two hosts.
- Each surviving entry's reason is rewritten to say why it is a path on `app.` rather than why it was a host. The consent entry's reason says why consent keeps a name in the list at all: it carries the navigation-only fence below, and a builder reading the list must see that consent is not simply the wildcard.

### Consent on the one origin (grilling Q5)

- **Consent stays server-rendered by the api on the app origin**, outside the SPA's shell. The reason it is acceptable on the same origin as the product is the closed client list plus PKCE: the CIMD allow-list admits only `claude.ai`, so a code obtained by any script in the shell lands only at Claude's own redirect, and PKCE binds it to the verifier the host holds. This replaces ADR 0009's earlier reason, "outside the shell because it is on the other host".
- **A navigation-only fence on the consent POST.** The consent form answers with a redirect, so it can be reached only by a document navigation: a POST whose `Sec-Fetch-Dest` is not `document` is refused. The existing same-origin fence on the POST stays. Together they say: a browser navigated a form here from this origin; no fetch did.
- **Shown once per person per client, unverified.** Better Auth stores consent per user and client. Whether an existing consent row skips the screen on the next authorization from the same client is settled by the browser suite, not assumed; the result is written in the new ADR either way.
- The consent page's URL, the login page's URL and the post-login page's URL all sit on the one origin. The oauth-flow endpoints that Better Auth is called with in-process speak as that origin.

### The cookie (grilling Q6, Q9)

- **Better Auth's own `__Secure-` host-only session cookie, now.** The apex cookie domain and the cross-subdomain cookie branch are deleted from the auth dependencies, the server factory and the fence module.
- **`__Host-` is a written trigger, not a change.** The new ADR states the condition: the day a subdomain of the apex is served by anything but this process, the cookie moves to `__Host-`, because cookie-tossing login fixation needs such a subdomain and none exists. Better Auth documents the `__Secure-` prefix and a custom cookie name; `__Host-` is undocumented, which is why it is the trigger and not the default.

### Trusted origins and the pages

- Better Auth's trusted origins become one entry, the app origin. The origin check stays explicitly on under every test runner, as it is today.
- The consent page, the login page and the post-login page are named absolutely on the app origin. The comment that explained why consent was named absolutely against a different origin is replaced by the one-origin reason.

### The browser suite's loopback estate

- The loopback estate becomes one product host. The suite's server takes the app origin as the loopback origin it serves on, as it does today for the app; the derived app hostname is the loopback address; `agent` and the apex keep their loopback names.
- A consent spec joins the suite. It signs in through the existing sign-in helper, starts an authorization from a CIMD client served by the in-process transport, lands on consent, accepts, and asserts that the redirect carries a code to the client's redirect URI and nowhere else; then it authorizes again from the same client and records whether consent is shown or skipped. A refused case, revoked credentials, is one more test on the same path. The builder should expect that Better Auth refuses a non-https redirect URI: the in-process client document names an https redirect that the browser never reaches, and the test reads the redirect's location rather than following it.

### The api test suite

- The harness's constants become one product origin: the public URL is the app origin, the MCP URL hangs off it, the default client speaks to the app hostname. Every suite that named `mcp.` for a path is re-cut to `app.`; any test whose point was the two-host separation is deleted with its reason stated in the PR.
- The hostname test is re-cut: the MCP endpoint, the authorization server, the discovery documents and consent answer on `app.`; the resume and the product's screens are the catch-all's; `agent.`, the apex, an unnamed hostname, a forwarded-header hostname and a trailing-dot hostname behave as they do today. The both-ways role test keeps its shape with one role fewer.
- The config test: `PUBLIC_URL` derives the app hostname; the three must differ; the parser-rewritten-host refusals move from the `mcp.` wording to the `app.` wording.
- The Better Auth endpoint snapshot is re-cut once and reviewed by a human, as T-039 intended.

### T-005 (grilling, assumed and unobjected)

- T-005's hostname line reads three hostnames: `PUBLIC_URL` with `APP_HOSTNAME` derived, `AGENT_HOSTNAME`, `APEX_HOSTNAME`. Its tunnel line names three ingress rules. Its rate-limit line names rules by path on `app.`: `/oauth2/*`, `/.well-known/*`, `/mcp` without a bearer, and the sign-in endpoints. Its uptime line names two paths on one host: `/health` and the protected-resource document. The Cloudflare Pro trigger is unchanged.
- These are body edits to T-005 made origin-first per the issue-tracker procedure, in the same session as this spec lands or in the PR's own commit; they are part of this task's acceptance.

### Records (grilling Q13)

- **One new ADR, 0034**, states the origin decision and its rejected alternatives; the consent reasoning; the `__Host-` trigger; the sign-in decisions of the same grilling, which are that password and sign-up endpoints on the wildcard are refused by configuration and reviewed in the endpoint snapshot, that the social surface opens for Microsoft in its own task, and that the per-client `sso` shape is the written trigger for the day a client's IT asks; and the result of the consent-skip question once the browser suite has answered it.
- **ADR 0008, 0009 and 0022 each gain a one-line amendment** pointing at 0034: 0008 for the MCP surface and `/oauth2/*` on the app origin; 0009 for one origin, one session, consent's reason and the cookie; 0022 for three hostnames, `docs.` struck, rate-limit rules by path.
- The ADR index gains a 0034 row and the 0008, 0009 and 0022 rows change in the same commit; the index test is the gate.
- The glossary's *MCP surface* and *sign-in* entries already carry the decisions from the grilling session and are checked against the code in the PR.
- The fence module's header, the config module's comments and the harness's comments say `app.` where they said `mcp.`, and say three hostnames where they said four.

### Sign-in methods (grilling Q4, Q10 to Q12; recorded, built elsewhere)

- Email code or Microsoft, never a password. Claude and Notion were rejected as sign-in methods because neither is where a company's IT creates and removes people.
- Microsoft is a sign-in method through Better Auth's social provider on one multi-tenant Entra app registration the platform owns; a person is invited by email first; accounts link only on an exact verified-email match with the invitation; a mismatch is refused on the refused screen and the Admin re-invites the right address. The Entra redirect URI is `https://app.<apex>/callback/microsoft`, which is why the origin lands first.
- This is its own task after T-045 and before the first client is onboarded; it does not block T-005. The Entra app registration is the owner's action outside the repo.

## Testing Decisions

**A good test crosses the seam a caller crosses and asserts what the system does for whom.** It never imports a slice's internals, never mocks our own code, builds its state through the harness and runs against a real Postgres. Three existing seams carry this spec; no new seam is added.

### Seams, highest first

1. **Browser to policy** in the web workspace's Playwright suite, over the real server, a real Postgres and a real browser on one loopback origin. The consent spec is the deliverable here: sign in, authorize from a CIMD client, consent, code at the redirect, second authorization from the same client shown or skipped, revoked credentials refused. The existing sign-in, sign-out and routes specs pass unchanged in behaviour on the one host.
2. **The api endpoint** through the test harness's host-shaped client: the hostname suite, the config suite, the endpoint snapshot and the OAuth-flow suite, re-cut to the one origin. The navigation-only consent fence is tested here: a POST with `Sec-Fetch-Dest: empty` and the person's cookie is refused and mints nothing; the same POST as a document navigation succeeds. The cross-origin refusals stay.
3. **The ADR index test**: a 0034 row exists and the three amended rows carry the new date.

The claude.ai re-prove over a Cloudflare quick tunnel is not a test. It is the acceptance artefact T-045's ticket names and is recorded in the PR body with the issuer used, the date and the outcome, as prototype 61 recorded its run.

### Prior art

- The hostname suite, one `it` per surface per host, and the both-ways role test at its end.
- The OAuth-flow suite for the full authorize-consent-token path in process, its cross-origin refusals and its audit assertions.
- The web suite's sign-in spec and its harness helpers for provisioning, membership, revocation and the captured code.
- The config suite for bootstrap refusals.
- The ADR index test.

## Out of Scope

- **Microsoft sign-in** and the Entra app registration: its own task, cut from this spec.
- **The per-client `sso` shape**: a written trigger in ADR 0034, not work.
- **`__Host-`**: a written trigger, not work.
- **T-005's enactment**: tunnel, compose, rate-limit rules and uptime checks are built there; this task re-cuts T-005's lines only.
- A public docs site on any hostname.
- Any change to the CIMD allow-list, PKCE, scopes, token lifetimes or the MCP surface's four entries.
- Any change to the share agent's route, `agent.`, or the apex.
- Personal tokens, the platform console, People.

## Further Notes

- **Facts a fresh session would otherwise rediscover:** the api mounts no CORS middleware; the consent POST already refuses a foreign `Origin` and answers with a 302; the fence is one ordered list with a catch-all, tested both ways; `mcp.` is derived from `PUBLIC_URL` since T-039 and `MCP_HOSTNAME` is read nowhere; the harness's default client speaks to the `mcp.` hostname unless a test names another; the browser suite's server runs on a loopback http port with the app on `127.0.0.1` and `mcp.` on `mcp.localhost`; the web suite has no consent spec today.
- **Order inside the PR:** config and fence first, with their suites; then auth wiring and consent's navigation fence, with the OAuth-flow suite; then the harness and the browser suite's loopback estate, with the consent spec; then ADR 0034, the three amendments and the index; then T-005's body edits. The quick-tunnel re-prove is the last act before the PR opens and its outcome goes in the body with the `[SEC3]` pass.
- **The one unverified behaviour** is the consent-skip on an existing row. Whichever way the browser suite answers, the answer is written in ADR 0034 and nothing else in this spec depends on it.
- **After this spec:** T-045 is the task; the Microsoft sign-in task is created beside it, depending on it.
