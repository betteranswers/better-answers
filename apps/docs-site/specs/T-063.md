# T-063 — Identity founded: one person id, one minter, and who may write the identity set

*Spec written 5 September 2026 by /to-spec over the identity grilling session of the same day — three rounds over the seven candidates of the 2026-09-05 architecture review (handed off in `handoff-better-answers-2026-09-05.md`), a staff-engineer review that ran between rounds two and three and reversed one decision, and the T-048 and T-006 specs this ticket now sits in front of. Decisions recorded here are taken; do not re-open them. The ticket is split by /to-tickets in a later session.*

## Problem Statement

One person is named three ways and none of them is what the glossary says. A concept file names them `human:<email>`; the erasure routine promises to rewrite that to `human:<member-id>`, which the glossary calls "a per-member ULID minted at member creation" — but the code writes a composed string at provisioning and lets Better Auth mint its own shape everywhere else; and the ledger T-059 is about to found names them by a "stable identity id" nobody has defined. There is no minter in production at all: the only ULID function in the tree is a test helper built on random characters with no time component, and four tickets (T-059, T-060, T-061, T-052) each need one.

The builders of the next five tickets would each choose. T-060 needs a group membership key; T-061 needs an actor for a person who is not a member; T-052 needs the actor form its commit trailer carries; T-054 needs a proposer column; T-027 needs to know what *revoke credentials* does when the person also belongs to another company's workspace — today it ends every session in every workspace, from one workspace Admin's click. Nobody owns filling the Principal's group list, and the table-ownership map ADR 0029 promised does not exist, so the resolver reading a slice's table and two slices writing `member` are facts nobody recorded.

Underneath: the audit ledger's vocabulary has no families. The incoming People screens were built for people-shaped events; the platform's vision also audits knowledge acts, source acts and the platform's own runs, and without the words settled now, the first ledger row fixes a shape the rest must live with.

## Solution

A person has **one id**: the id on Better Auth's user row, minted by the platform's own minter, carried as `userId` on every Principal, written as `human:<person-id>` on every record the platform keeps, and never written into a concept file. The member row's id becomes a key nothing of ours references.

One **minter** in the kernel mints every id the platform writes — and Better Auth is handed the same function, so users, sessions, members, invitations and, later, groups, requests and ledger rows share one shape that one boundary refinement checks and one contracts fixture pins for both tiers.

**Revocation gains a scope.** A workspace Admin revokes a person's credentials *in this workspace*: an instant on the membership row that the resolver refuses against, exactly as it already refuses against the person-level instant, with tokens ended only where their consented workspace matches. Revoking *everywhere* stays one act and becomes the operator's. No workspace ever learns whether a person belongs to another.

The **actor form** is one string across records — `human:<person-id>`, `process:better-answers-<purpose>`, or an agent's id — with a kernel type and one function that derives it from a Principal. The audit slice will have two doors: one that derives the actor from the caller, and one only the platform principal can open to name someone else. The **ledger's families** are four words — people · knowledge · sources · platform — and an act is named `family.subject.verb`, so a screen filters by prefix and no central list is ever edited.

On erasure, `human:<email>` in a workspace's files and history becomes a **per-workspace erasure pseudonym** minted at erasure, not the person id, so two companies' rewritten histories cannot be linked; the ledger, which never held an email, is never rewritten.

The **table-ownership map** is founded: one checked-in record naming which slice writes each table and which reads another's, asserted both ways against the declared tables. The glossary gains *person id*, *operator* and *erasure pseudonym*, retires *member id*, and gives *audit event* its families and *revoke credentials* its two scopes; one new ADR records the person-id decision and four existing ADRs are amended where they said *member id*.

No new tenant table lands here. This ticket is the substrate the T-048 and T-006 clusters and the People screen build on, sized as one PR of about a day.

## Implementation Decisions

**The person id.** The id on Better Auth's user row is the platform's one id for a person: `userId` on the Principal, the requester on an access request, the key in `group_member`, the actor on the ledger, the proposer and decider on a suggestion, the id in the commit trailer. The member row keeps a primary key because the organisation plugin requires one, but nothing of ours references it, joins on it or shows it; the members slice keys every People act by (workspace, person). The glossary's *member id* entry is retired in favour of *person id*; code keeps the name `userId` — the glossary says so, and no rename is made.

**The minter.** One pure function in the kernel returns a ULID: 48 bits of milliseconds, 80 bits of randomness, monotonic within a millisecond, Crockford base32, 26 characters — a pinned library under `[DEPS1]` or a short hand-written implementation, either with a test for shape, ordering and uniqueness. Better Auth receives the same function through its custom id-generation option; the option is called with a model name and sometimes a size hint, and the size hint is ignored by design. Three facts about the library, verified against the installed version, are recorded beside the wiring so nobody re-derives them: session tokens, authorisation codes, client secrets and token `jti` values are produced by the library's own random-string paths and never by the minter; the organisation plugin routes member and invitation creation through the adapter, so both receive minted ids; and a caller-supplied id is dropped by the adapter unless forced, so a pre-minted id is never sent through Better Auth's API — core's direct SQL writes are unaffected. Installing a custom minter switches off the library's "opaque invitation id" heuristic, after which accepting, rejecting or cancelling an invitation by id requires a verified email; the option that requires email verification on invitation is therefore set explicitly to true, so T-027's accept page rests on a decision.

**Boundary refinements.** The identity ids of `user`, `session`, `member` and `invitation` narrow to the ULID pattern the workspace id already uses; the OAuth tables stay unrefined, because one of them stores a digest as its id by the library's design. The test factory imports the production minter and its own random-string helper is deleted. Provisioning mints the first Admin's member id through the minter instead of composing it. This is pre-production: development databases are re-seeded, and no data migration is written.

**Revocation in a workspace.** The member row gains a nullable revocation instant, declared through the organisation plugin's additional-fields schema so the library and the platform agree on the column. The resolver's one membership query reads it beside the person-level instant, and a claim issued before either is refused with the existing *credentials revoked* word — no new refusal word, one outcome on every surface. The workspace-scoped act itself — writing the instant, revoking the refresh and access tokens whose consented workspace is this one and which were minted before it, and writing its ledger row — is T-027's, since the ledger and the members slice land between here and there; this ticket lands the column, the resolver's refusal, the token-revocation predicate as a tested store function, and the words. The person-level act stays as built, takes the platform principal until T-028 gives the operator a principal kind, and is never callable from a workspace Admin's procedure. The external UI's *Suspended* member status is not adopted: revocation ends what was issued and a fresh sign-in mints anew, on both scopes.

**The actor form.** The kernel gains an actor-id type — a string in one of three forms: `human:<person-id>`, `process:better-answers-<purpose>`, or an agent's id as ADR 0019 already shapes it — and one function deriving it from a Principal. Concept files keep `human:<email>` in `generated.by` and `verified[].by` (ADR 0019 stands); the git author line keeps name and email; only the commit trailer carries the actor id. The audit slice's two doors are this ticket's stated interface for T-059 to build: one taking a Principal and deriving the actor, one taking the platform principal and an explicit actor, typed so that a user principal cannot reach it; the access-request act is the one caller of the second.

**The ledger's families and act names** are settled here as words and coded by T-059: four families — **people**, **knowledge**, **sources**, **platform** — and an act named `family.subject.verb` (`people.member.role_changed`, `knowledge.suggestion.accepted`, `sources.binding.published`, `platform.reconciler.replayed`). Corrections and promotion decisions are knowledge acts; routes, ceilings, exports and provisioning are platform acts. The family set is the only closed list; each slice declares its own acts against a template type the audit slice exports, and one test walks every slice's declared acts and checks the family prefix both ways. The ledger carries a nullable batch id (ADR 0014 rule 4 honoured: a bulk acceptance is N governed writes and N rows sharing one batch id); its month partitioning is superseded in words with a row-count trigger, because partitioning a policy-bearing table changes the catalogue assertion the RLS helper proves and retention deletes need a role that is not the app's. No summary and no severity are stored — both are rendered from the act and its detail. Runs, the answer audit (ADR 0017), signals and alerts (ADR 0025), spend and the inbox are their own records and never ledger rows.

**Erasure rewrites to a pseudonym.** On a valid erasure request, `human:<email>` across a workspace's files and history, its git author lines by mailmap, and its `bundle_commit` and verification rows are rewritten to a per-workspace **erasure pseudonym**, minted by the minter at erasure and recorded on the erasure request beside the person id; the user row is pseudonymised — email to a unique tombstone, name cleared, id kept — and the member row is not the target. The ledger is never rewritten. The erasure map gains what the identity set now holds: invitation emails, verification identifiers, session IP and user agent, and the linked account id. The erasure request table and routine are not built here; the decision is recorded in the ADR amendments so the routine's ticket codes against it.

**Refusals and results.** The kernel gains one refusal word for an act a role may not perform and one guard that narrows a Principal to Admin or returns that word; T-060 and T-061 use it on every verb. The result convention is stated once in the kernel and followed by every slice entry point: a slice act returns a Result whose error is either a closed union of refusal words a caller can act on or the normalised Error of a store failure, and a slice entry point never throws. The constraint-name match that reads Postgres's errors into refusal words becomes one kernel helper.

**The table-ownership map.** A checked-in record in the schema package, shaped like the RLS exemptions record: every declared table names its owning slice, and every read or write of a table by another slice is an entry with a reason. Founding entries: the identity set is Better Auth's, written by the workspaces slice (provisioning, revocation) and the members slice (People acts, the invitation T-061 mints); the Postgres door reads `member`, `user` and, from T-060, `group_member` inside the resolver; the audit slice owns `audit_event`; the members slice owns `group`, `group_member` and `access_request`; the concepts slice owns the concept, commit, evidence and verification tables and the two graph tables. A test asserts both ways against the declared tables, and a second asserts that every named owner is a slice that exists. Lint enforcement of "a store file imports no slice's table" is a written trigger, not built.

**Two guards and one move.** Better Auth's delete-user feature stays unconfigured and a `[SEC3]` test proves its endpoint is refused. The "which workspaces does this person hold" read leaves the auth module's raw pool for the workspaces slice, so the picker's three identity paths and T-061's request act read one function, and the RLS exemption's reason for `member` names it as the picker's cross-workspace read by person id.

**Contracts.** A fixtured agreement pins the ULID pattern and sample ids so both tiers' conformance suites read it; the contract version bumps.

**Documents.** A new ADR — a person has one id — states the decision and its alternatives: a per-workspace pseudonym as the everyday id (rejected: two ids per person on every record and a join for every pre-membership act), Better Auth's own id shape kept (rejected: two id shapes, two refinements, and a ledger whose id order disagrees with its timestamps), the sole-membership revocation rule (rejected: a cross-tenant oracle, a race with an invitation accepted elsewhere, and a tenant Admin's transaction reaching other tenants' credentials), and one global rewrite target on erasure (rejected: linkable across controllers). Four amendments, each with its index row in the same commit: ADR 0009 (the member id the admin plugin was refused for destroying is now the person id; revocation's two scopes; the minter behind Better Auth), ADR 0014 (the member row carries no id of ours), ADR 0019 (the erasure rewrite target is the erasure pseudonym), ADR 0020 (the user row is pseudonymised, the pseudonym is minted at erasure and kept on the request, the erasure map's new entries).

**Glossary**, landed in the same PR so `[GLOSSARY1]` holds before any code names the words. Proposed wording for the implementer:

- **person id** — the platform's one stable id for a person: minted by the platform at their first sign-in, carried on the identity set's user row, `userId` on every Principal, and what every record names a person by as `human:<person id>`. Never written into a concept file, which keeps `human:<email>` (ADR 0019). _Avoid_: member id (retired 05/09/2026 — the member row's key names nothing), user id (on a screen).
- **erasure pseudonym** — the per-workspace opaque id, minted at erasure and kept on the erasure request, that `human:<email>` becomes across that workspace's files and history on a valid erasure request. Never the person id, so two workspaces' rewritten histories cannot be joined on one person.
- **operator** — the platform's own administrator over every workspace: a real person on the identity set with the platform-level role, a third principal kind beside a user and the platform, audited under their own id. Never a workspace *role*; *Admin* is the highest role a workspace has.
- **revoke credentials** — the one revocation act, in two scopes. *In a workspace*: a workspace Admin ends every session and token a person holds there, by an instant on the membership row the resolver refuses against; nothing outside that workspace changes, and the Admin never learns whether others exist. *Everywhere*: the operator ends every session and token the person holds, by an instant on the person. Both end what was issued; a fresh sign-in mints anew. _Avoid_: suspend, ban, deactivate.
- **audit event** — the existing entry gains: every event belongs to one of four families — **people**, **knowledge**, **sources**, **platform** — named as the first word of its act; runs, the *answer audit*, *signals* and spend are their own records and never audit events.
- *actor id* gains the ledger's form: on a record the platform keeps, a person is `human:<person id>`; the file forms stand.
- *erasure request* gains: carries the erasure pseudonym it minted.

## Testing Decisions

A good test crosses the seam a caller crosses and states behaviour a caller can observe — a refusal word, a minted shape, a row that is or is not there — never how it was done. Real Postgres through the Testcontainers harness for every store test (`[TEST2]`), the platform's own code never mocked (`[TEST3]`), state built through factories (`[TEST4]`). Four seams, all existing:

- **The Principal resolver** through the Postgres door (prior art: the principal tests in core): a claim issued before the membership's revocation instant is refused with the existing word; one issued after it resolves; a person revoked in workspace A resolves unchanged in workspace B; the group list is untouched by this ticket.
- **The workspaces slice's entry point** (prior art: the workspaces tests): provisioning writes a minted member id that parses at the boundary; the moved membership read lists a person's workspaces and nothing else; the token-revocation predicate ends only the tokens whose consented workspace matches.
- **The api HTTP harness** (prior art: the OAuth-flow and routes tests): a person who signs in gets a user id in the ULID shape; a session id in the same shape; the delete-user endpoint is refused; the invitation-acceptance verification option is on.
- **The schema package's suites** (prior art: the boundary-parity and RLS tests): the narrowed identity refinements pass the parity test; the ownership map is asserted both ways against the declared tables, and every owner it names is a slice that exists.

Beside those, one pure test for the minter (shape, time ordering across two instants, uniqueness and monotonicity within a millisecond) and the tier-contract conformance tests on both sides reading the new fixture. This PR touches the identity tables, so it gets the adversarial security pass `CODING_RULES.md` requires beside the two document-driven review axes.
