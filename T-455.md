Name the day production's upload sweep switches from `list` to `remove`, and write it in the sweep's own section of the runbook.

## Agent Brief

**Category:** enhancement
**Summary:** Anchor the runbook's existing switch rule to a concrete day: one week after the first client upload is bound on production.

**Current behavior (verified on main 9fdf00b7, 27/09/2026):**
- The api config and the platform compose file both default `UPLOAD_SWEEP` to `list`, and nothing sets `remove`.
- The runbook already explains how to read `found` and `removed`: the `sweeps` check body, the `sweep pass` log line, and the `sweep_pass` table through `browse_ro`. It also gives a rule: switch after a week of list-only passes in which every rise in `found` has a failed bind or a lost race behind it.
- What is missing is *which* week. Production holds no bound originals yet, so a list-only week now reads `found=0` and validates nothing. T-331 brings the first client's workspace, but as an imported bundle, which writes no originals, so it does not change that.

**Decision (made at triage, 27/09/2026):**
Best practice for a destructive collector is a dry run against real data, then enable. So the day is **seven days after the first client upload is bound on production**, and only if the runbook's rule holds for that week.
- Before that day, the orphans are bounded. A failed bind or a lost race leaves one original, up to 64 MB, and there are no client binds yet.
- After that day, the orphans may hold personal data nobody can find (ADR 0020). So the switch should not wait past the first week.
- The 24-hour grace already keeps removal from reaching an original whose bind is still running.

**Out of scope:**
- Setting `UPLOAD_SWEEP=remove` in Coolify. That is the operator's act on the named day, following the runbook step this ticket writes.
- Changing either default to `remove`.
- A code gate that switches the mode itself.
- Changing the grace period.
