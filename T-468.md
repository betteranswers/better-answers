## Goal

`apps/web/e2e/sources.spec.ts:226`, "an Admin binds by keyboard and sees landed, indexing, indexed", timed out in two merge-group runs: 36164645368 (25/09/2026 17:02Z) and 36266123068 (26/09/2026 19:27Z). The first ran it under its older title, "an Admin binds a document by keyboard and watches its state move landed, indexing, indexed as the worker runs". Both failed at the same step, waiting for the file chooser:

```
Test timeout of 30000ms exceeded.
Error: page.waitForEvent: Target page, context or browser has been closed
waiting for event "filechooser"
> 242 |     const choosing = page.waitForEvent("filechooser");
      |                           ^
  243 |     await page.keyboard.press("Space");
```

The wait starts before the Space press, so the press opened no chooser in the test's 30 s. Find out why, and fix it at the cause.

## Notes

Each merge-group run's pull request had passed its own pull-request run first. A queue ejection costs a full `check` and rebuilds every entry behind it.

Under CI the browser suite now retries a failed test once. A test that passes on its retry is named as flaky in the job's summary and in a warning annotation. The retry keeps the queue moving, but it is not the fix, and a green retry does not close this ticket.

The suite's conventions are `/browser-suite`. Sibling tickets: T-469, T-470, T-471 and T-472.

## Cause

Named 28/09/2026 (`/diagnosing-bugs`). The chooser opened, uncaught, and was cancelled.
- Calling `page.waitForEvent("filechooser")` is what makes Playwright send `Page.setInterceptFileChooserDialog {enabled:true}`, and it does not wait for Chromium to acknowledge it. The Space press went out in the same millisecond, and key events reach the renderer by another path, so the send order does not decide the handling order.
- When the keyup's click asked for a chooser before the interception had landed, the chooser opened uncaught. The headless shell cancelled it, no `Page.fileChooserOpened` came, and the wait ran to the test's 30 s timeout.
- What the page did (instrumented in a failing run): the File input had focus; keydown, keypress and keyup reached it, then `click` and `DOMActivate`, with user activation live. A `cancel` event fired on the input 3–8 ms later. Passing runs end in `input` and `change` from `setFiles`, with no `cancel`. Neither the screen nor focus was at fault.
- Why only sometimes: across 60 runs with protocol logging, all 4 failures had the interception's acknowledgement arrive after the Space keyup was sent (in one, about 12 ms after the keyup's reply). 42 passes had it before the keyup, and 14 after but in time. Load decides the race: 1 of 30 failed at the default workers, 9 of 60 on 4 workers.
- Ruled out: focus off the File input (the failure snapshot shows it active), `:active` cleared between keydown and keyup (`click` fired), a single-key shortcut swallowing Space (the event reached the input).
- Fix, in how the spec waits: the wait starts before `b` opens the dialog, so a dozen awaited page round trips, run on the same main thread after the interception command, come before Space. The spec also asserts the File input is focused before Space, so wrong focus fails by name. `--repeat-each 60 --workers 4`: 60 passed (9 of 60 failed before).
- `--repeat-each 30`: 30 passed. Whole local suite: 192 passed, 10 failed; the 10 are the claude.ai-redirect tests in `consent.spec.ts` and `console-people.spec.ts`, which fail the same way on unchanged `main` in the cloud container. The merge group's `full-web` was green.
- Other specs read for the same hazard: no other spec waits for the file chooser. `sources.spec.ts:215` and `:318` call `setInputFiles` directly. The response, request and navigation waits in `sign-in.spec.ts:54`, `ask-to-join.spec.ts:168`, `frame.spec.ts:436` and `display-name.spec.ts:36` need nothing from Chromium first. `page.route` and `catchClaudesRedirect` are awaited, and `route` waits until its interception is on. None affected.
