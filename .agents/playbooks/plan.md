# Plan

These changes add this repository's facts to a plan. They leave the ten live lanes, the perf block and step 6 as pstack wrote them, because `check-plan.mjs` checks those.

- **After** "When the change is one or two files with an obvious approach, skip the plan. Say so and stop.", also skip the plan when one owner can build the work in one session, as one pull request or a short stack of them. Say so, name the Feature, Refactoring or Bug fix playbook it runs under, and stop.
- **In** "Unless the operator names a path, write the file under the agent store", write the plan in `docs/plans/` as `YYYY-MM-DD-HHMM-<type>-<slug>-plan.md`, where `<type>` is the Conventional Commits type. The plan's intro names the route block the plan serves and links its brief, `docs/specs/route/<id>.md`. The pull request that adds the plan sets the block's row in `docs/specs/v01-route.md` to `planned` and links the plan. Each PR id is its Linear issue, `BA-N`.
- **After** "Each returns file pointers, conventions, test commands, and entry points." When a PR shapes a screen, its explorer reads the personas that screen serves in `docs/personas/personas.md`, and the PR's design names them.
- **After** "Each returns file pointers, conventions, test commands, and entry points." One explorer reads the archived record of each ADR the block's brief names, `docs/archive/adr/NNNN-*.md`, against its live doc under `docs/solutions/architecture-patterns/`, and lists each rule the archive holds that the live doc lacks, as a question the plan settles. A decision has gone missing that way before.
- **After** "Each returns file pointers, conventions, test commands, and entry points." One explorer reads the rules files that `docs/agents/workflow.md` says a review reads, for each directory the plan touches, and returns the rules that bind the work. The planner reads the comments on each PR's Linear issue with `list_comments`. For each PR, the plan lists the rules files and the issue comments it read, or says none, and cites each rule and comment it acts on. Two plans of BA-44 from one prompt once differed this way: only one carried an api rule, and the one that never called `list_comments` left out a requirement a comment set (BA-62).
- **In** "Follow this dependency graph", each PR that adds a migration, and each PR that edits `contracts/`, runs alone until it merges. The graph never puts two PRs of the same kind in flight at once. The drizzle journal does not merge, and neither do the digest constants that both tiers generate from `contracts/`.
- **In** "put the resolved skill path or exact commands in each live lane's boot recipe", the web's driver skill is `browser-suite`, at `.claude/skills/browser-suite/SKILL.md`.
- **Replace** "<The merge or append rule from the execution playbook, with the patch-id rule from `playbooks/shipping.md`.>" with the rule in `docs/agents/workflow.md` *Merging*. An agent that did not write the PR posts `PASS` at the head SHA. Once the PR's own `check` is green, the session queues its own PR through the merge queue with `gh pr merge <n> --match-head-commit <sha>`. A push after the verdict needs a new verdict. Queued is not merged, so the session reads the PR back with `gh pr view <n> --json state,mergedAt`. **How to read this** and each **Merge.** block's last box name the same merger.
