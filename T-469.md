## Goal

`apps/web/e2e/sources.spec.ts:943`, "widens a Public binding's audience, then says nothing is wider", failed in two merge-group runs 32 minutes apart: 36251369401 (26/09/2026 15:16Z) and 36253209262 (26/09/2026 15:48Z). The failure was the same in both:

```
Error: expect(locator).toHaveText(expected) failed
Locator:  getByRole('region', { name: 'Bindings' }).getByRole('status')
Expected: "“Price book” is Public for everyone in the workspace, and no class or audience is wider."
Received: "Widened “Price book” to Public for everyone in the workspace. 0 concepts and 0 compositions moved with it."
> 983 |     await expect(bindingsRegion(page).getByRole("status")).toHaveText(
```

After the second `w`, the status kept the first widen's sentence for the whole 5 s. Either the press never reached the act, or the act's answer never replaced the status. Find which, and fix it at the cause.

## Notes

Each merge-group run's pull request had passed its own pull-request run first. A queue ejection costs a full `check` and rebuilds every entry behind it.

Under CI the browser suite now retries a failed test once. A test that passes on its retry is named as flaky in the job's summary and in a warning annotation. The retry keeps the queue moving, but it is not the fix, and a green retry does not close this ticket.

The suite's conventions are `/browser-suite`. Sibling tickets: T-468, T-470, T-471 and T-472.

## Cause

Named 28/09/2026 from the agent's probe (`/diagnosing-bugs`). The second `w` did reach the act, and its sentence did replace the status. Then the first widen's late answer overwrote it.
- The widen is optimistic: `useClassSetOnTheRow` (`sources-api.ts`) sets the row to Public / everyone the moment the dialog confirms, before the api answers. The spec read that row as the widen landing and pressed `w` at once, so `widestAlready` wrote "…no class or audience is wider."
- The widen's own sentence comes from the per-call `onSuccess` in `settledSaying` (`bindings-view.tsx`), which TanStack runs only after the api answers and `onSettled`'s list re-read ends. It then wrote "Widened …" over the newer sentence.
- Why only sometimes: the spec passed when the matcher read the status in the 20–100 ms gap between the two sentences. A loaded merge-group run can miss that gap.
- Evidence: a MutationObserver probe on the status, with `**/trpc/sources.widen**` routed. Unchanged spec, no hold: 30 passed, with the widen still in flight at the second `w` in about 22 of them, the status flipping "…is wider" → "Widened …" 15–100 ms later. Unchanged spec, the widen's answer held until just after the second `w`: 5 of 5 failed with CI's exact error. Fixed spec, the answer delayed 1.5 s: 5 of 5 passed.
- Fix, in how the spec waits: it waits for the widen's own sentence before it reads the row and presses `w`. No screen change: a person pressing `w` mid-widen sees both true sentences in turn.
- `--repeat-each 30` on the fixed test: 30 passed. Whole local suite: 192 passed, 10 failed. The 10 (5 in `consent.spec.ts`, 5 in `console-people.spec.ts`) fail the same way on unchanged `main` in the cloud container, where only the chromium 1194 headless shell is installed and the claude.ai redirect goes to `chrome-error://`. The merge group's `full-web` leg, on the pinned browser, was green.
- Other specs read for the same hazard, none needing a fix: `sources.spec.ts` (publish, narrow, widen by keyboard, keep-in-text then narrow, dismiss), `people-groups.spec.ts`, `console-people.spec.ts`, `people-invitations.spec.ts`, `people-requests.spec.ts`. Each waits for its act's own sentence before the next act. One related gap, not fixed: `people.spec.ts`, "flags a member's name within budget, and again answers alike". `DisplayNameFlag` writes its sentence before the api answers, so the second flag's assertions pass before either answer arrives. It cannot fail by accident, but it does not prove the second flag answers alike.
