`apps/web/e2e/people.spec.ts:281`, "lets an Admin reach and search members by keyboard alone", failed in two merge-group runs: 36191195746 (25/09/2026 21:22Z) and 36199767696 (25/09/2026 23:07Z). The failure was the same in both:

```
Error: expect(locator).toHaveValue(expected) failed
Locator:  getByRole('searchbox', { name: 'Search by name or address' })
```

Under CI the browser suite now retries a failed test once. A test that passes on its retry is named as flaky in the job's summary and in a warning annotation. The retry keeps the queue moving, but it is not the fix, and a green retry does not close this ticket.

## Cause

Named 28/09/2026 (`/diagnosing-bugs`). The Escape went to the "Keyboard shortcuts" button, not the search box.
- The keystrokes list is a Radix popover. When it unmounts, `@radix-ui/react-focus-scope` hands focus back to its trigger in a zero-delay `setTimeout`, without checking where focus is by then.
- Chromium runs input events ahead of timers, so the spec's next keys could land first: `/` focused the search and "sam" was typed and narrowed the rows to one. Then the timer moved focus to the button, and the spec's Escape reached the button.
- Why only sometimes: the failing runs' spec waited only for the list to leave (`toHaveCount(0)`) before pressing `/`, so it depended on who won that race.
- Evidence: a throwaway spec replaying the failing commit's steps (47ad0f5) with an in-page log of keydown, focusin, input and the list's removal failed 13 of 60, 5 with this exact symptom and 8 with the same steal landing earlier. One "sam" failure, in ms: list removed at 257.8, focus to search 264.4, "s", "a", "m" at 278–291, focus to the button at 300.6 (43 ms after the list went), Escape at the button 304.2. With the fix the same steps passed 60 of 60.
- Fix, in the screen (`apps/web/src/shared/keystrokes.tsx`): the list hands focus back only when focus was lost with it (it sits on `body`). A key that already moved focus keeps it, for every spec and for a person who types fast. A jsdom test (`apps/web/test/keystrokes.test.tsx`) holds both cases. `main` had already added a wait for focus to return (`keystrokesDismissed`), which hid the race in this one spec; its comment, skill row and a `console-people.spec.ts` comment now say what the screen does.
- `--repeat-each 30`: `people.spec.ts`, "lets an Admin reach and search members by keyboard alone", passed 30 of 30. Whole local suite: 192 passed, 10 failed; the 10 are the claude.ai-redirect tests in `consent.spec.ts` and `console-people.spec.ts`, which fail the same way on unchanged `main` in the cloud container. The merge group's `full-web` was green.
- Other specs read for the same hazard: `audit-log.spec.ts:262-265` (Escape, waits for the list to go, then `f`: the same race, closed by the screen change), `accept-invitation.spec.ts:259-261` (could not fail: `s` works from either focus), `people-requests.spec.ts:210` (a Tab loop that survives a steal), `sources.spec.ts:1075-1077` (checks do not depend on focus). Already safe: `console-people.spec.ts:418`, `people.spec.ts`, `sources.spec.ts:1061`. Dialogs and sheets use their own focus return, and every spec waits for it or navigates next.
