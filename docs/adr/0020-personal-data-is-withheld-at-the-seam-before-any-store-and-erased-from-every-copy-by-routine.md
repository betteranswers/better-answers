# Personal data is withheld at the seam before any store, classed in three words of which readers see one; the routine rewrites every copy of what the platform wrote, and a person edits what the company wrote

**Sensitivity** is one of three classes on a binding, a source document, a chunk, a source entity and a concept row — **Restricted** (the default for every binding, every `Person` source entity and every `Person` concept: Admins and the members an Admin names), **Internal** (anyone in the workspace, narrowed by `audience`) and **Public** (content the company already publishes; still narrowed by `audience`, never a bypass). Only *Restricted* is ever a reader word; the other two are Admin words. What the pre-scan finds is a **finding** — counts by category on the document, with the category and the offsets into the normalised text — never a class.

Flagged content is **ingested whole**, and the **redaction seam** in the worker's conversion step (and on the referenced read tool's return) replaces each span with a placeholder — one neutral `[withheld]` for the *always* set; `[date of birth withheld]`, `[home address withheld]`, `[personal contact withheld]`, `[person A]` for the rest — **before chunking, embedding, extraction and every LLM call**, so no derived store, no memo and no model ever holds the value; the original bytes keep by retention class in the object store and are opened only by an Admin, each view an audit event. The seam's output is versioned by rule version and detector pin; a re-detection re-baselines the evidence resting on it as a platform act and never raises *source moved on*. Three tiers of **redaction rule**: an **always** set that is policy, not a detection claim — special-category cues (sentence-level), financial account identifiers, government identifiers — which no binding switches off, though an Admin may restore one span with a reason; a **default-on** set per binding — dates of birth, home addresses, personal contact details on a consumer-domain list; a **default-off** set — person names (a stable per-binding `[person A]`) and job titles, seeded on for meeting-note, support-ticket and HR-shaped bindings. The officer-block rule always wins: a name inside a PSC or officers section is withheld with its block. Special-category data is never inferred by a prompt, and its presence narrows the document to Restricted on landing.

Findings are shown on the enumeration sample, at the extraction-plan review — grouped by **category × rule** with samples, two bulk acts, *keep in text (business fact)* with a reason and *narrow these documents*, per-document lines only for the always set and special category — and in the publish dialog, whose audit row carries the totals and the hash of the per-binding **DPIA input** the platform emits (types, scope, class, rules in force, routes with processor, country and retention tail, retention class, audience). There is no publish block; **widening** is blocked while special-category findings are unreviewed. Only an Admin widens; a class change is a row update read at query time; a rule change reprocesses only the documents the rule fired on, keyed on their findings, never on a binding-wide version; narrowing raises the *should not have shown* report over answers already given.

A **`Person` concept** exists, carries only what the company itself publishes — name, role, public work contact, public bio, organisation link — minted only from a Public source or typed by an Editor, never from a meeting note, ticket or referenced fetch (those are graph source entities); its IRI is opaque; it starts Restricted; a leaver's reads **Left**, never *Deprecated*, and is later discarded. A person's actor id **`human:<email>`** is retained under a documented basis (legitimate interests, accountability) while their checks stand, reviewed on the storage-limitation cadence; a **valid erasure request** runs the history rewrite as a **routine** — every `human:<email>` becomes ~~`human:<member-id>` (the per-member ULID minted at member creation)~~ `human:<erasure pseudonym>` (2026-09-05 amendment below), `bundle_commit` rows rebuilt from the rewritten git, moved `verification.content_hash` values re-hashed under origin *erasure-rewrite*, author lines mailmapped, ~~the member row pseudonymised~~ the user row pseudonymised (2026-09-05 amendment below), `git reflog expire --expire=now --all` and `git gc --prune=now` on the bare repository and on the VPC 2 mirror (there is no forge and no indexer to pause — ADR 0024), the index, evidence and graph re-derived, exports already issued listed as not recalled. Names in free text are listed for the owner to edit; documents that never reached git are suppressions, not a rewrite. A **`subject_request`** family (access · erasure) reuses the erasure map's per-store finder on the one-month clock.

Redaction runs **before any route**, so hosted-vs-local is the workspace's route policy per purpose, never per document; a route with `retention_mode: zdr` refuses in code what steps outside ZDR; every route, the embedding route included, carries a **retention tail** the erasure report and the DPIA input state. A reader outside a Restricted document's audience sees nothing of it — no hit, no hint, no count; one inside sees the placeholders wearing *Restricted*, in the app and over MCP alike. The seam is **Presidio** (`presidio-analyzer` + `presidio-anonymizer` 2.2.364, MIT, at `data-privacy-stack/presidio`) with **GLiNER-PII** (`presidio-analyzer[gliner]`, ~~gliner 0.2.28~~ gliner 0.2.29 (2026-09-11 amendment below), Apache-2.0, `urchade/gliner_multi_pii-v1` on CPU) as the NER and six recognisers of ours — sort code + account number, date of birth in context, health cue, UK street address, the officer-block rule, the entity → category mapping — every span asserted back against the text, versions pinned and recorded on each finding.

We decided this because the first corpus's most useful file is also the flagged one, so quarantine is the manual work the product exists to remove and role-gating in place puts a sort code in four stores and at a processor; because a placeholder written before chunking is the one control that holds whatever a predicate, a prompt or a client's context does with the text afterwards; because no detector clears 0.6 F1 on independent benchmarks (research 65), so the design is detector + review by category + a Restricted default rather than trust in recall; because a bid writer, not a DPO, is the first Admin and the safe set must be what they get by doing nothing; because a company with no platform keeps its DPO's name and its team page (`[OKF1]`), so people belong in the bundle narrowly rather than nowhere; because a check's author is a fact of the company's knowledge and the credibility signal Liam chose (ADR 0019), yet a name is personal data the right to erasure reaches — and "beyond use" is a backup concept, not a live-git one (research 51, 66); and because one rule switch must never re-extract fifty thousand documents through a hosted route.

## Considered options

- **Two classes**, or **a five-level government scheme** — the website and the board minutes wear one word; or levels nothing in v0.1 acts on. **"Open"** as the third word — collides with the MCP entry and reads as *published*.
- **Quarantine documents with findings** — the useful file is the flagged one. **Ingest in place, role-gate the chunks** (ticket 06's question) — a value in pgvector, in the prompt and at the processor; erasure becomes a search of embeddings.
- **Pseudonymise every name everywhere** — "[person] holds the ISO 27001 lead" is a worse answer than the client's own file. **Nothing by default** — the first Admin is not a DPO. **"Any domain but ours" = personal contact** — withholds the buyer contact a bid needs.
- **A per-document finding list** — noise at five thousand documents and 0.5 F1. **A publish block on special category** — vacuous once landing narrows; blocking widening is the control.
- **Reprocess on a binding-wide rule version** — ≈ £750 and two days for one switch, and confirmed alias merges invalidated.
- **No `Person` concepts** — Answer bodies already name people, so a ban keeps no name out of git. **A `Person` with everything the page shows** — a personal mailbox and two career histories are not the company's to republish.
- **Rewrite on every leaver** — every clone and export diverges. **Never rewrite** — "we cannot" is not a basis. **Actor alias** as the rewrite target — already the word for an imported id's mapping.
- **Restricted bindings local-only** — unextractable for every client without a GPU. **Per-document routing** — two prompts, two memo keys, for a value already withheld.
- **An "incomplete — restricted content exists" hint** — a count is a leak. **Typed placeholders for the always set** — `[special category withheld]` beside a name tells the audience health-class data exists.
- **Regex only** — no names, addresses or health; 0.17 F1. **A transformers/spaCy-trf engine** — GPU-shaped for no gain over GLiNER on CPU.

The graph's part of the erasure routine is a full re-derive of the bundle-and-record partition as a new generation whose **flip and sweep are one step** — the sweep's last commit is the timestamp on the report — and, for source entities, suppression + reprocess per document; a drill dump taken after an erasure is never kept; Neo4j's transaction-log retention is the spike's question. ## Amendment — 2026-08-28, backups as copies of personal data (ticket 41, ADR 0022)

Every Postgres dump, git bundle and mirror is a copy the erasure map lists: it holds `suppression`, `erasure_request`, findings and pre-rewrite history. Three consequences. **The report's dates are computed from the timestamp of the last dump before the rewrite** — 48 hours · 30 days · 8 weeks · 6 months (governance-mode object lock makes them certain in both directions) — with this wording: *"Backup copies taken before <last-dump-at> are beyond use: restored only in a disaster, encrypted at rest, deletable only by the escrowed credential, expiring on <hourly> · <daily> · <weekly> · <monthly>. Should a restore from such a copy occur, this request is re-applied before the platform serves reads."* **Every restore replays the erasures completed after the dump** (`replay-erasures --since`) before `app` turns healthy — the clause that makes "beyond use" honest. **The routine holds `pg_advisory_lock(41)`** so no dump is taken while it runs; the VPC 2 mirror is re-pushed with `git push --mirror` and `git gc --prune=now` runs on both copies (ADR 0024 — no forge, no indexer to rebuild); the object-store deletion reaches the unlocked mirror bucket that night. Staging holds no client data outside a drill; every third drill rehearses this routine on a synthetic subject and greps the restored dump for its tokens.

## Amendment — 2026-08-28, a hosted embedding route names its sub-processor; the git step of the routine (tickets 74 and 42, ADR 0024)

A workspace on the **hosted embedding route** sends its chunk text to **Mistral (EU endpoint, DPA, zero data retention on `/v1/embeddings`)** — a sub-processor listed in that workspace's DPIA entry and in the platform's sub-processor list; the route is immutable per workspace (ADR 0007), so the listing never changes silently. Client one takes this route because its content already reaches Anthropic under Claude Teams — a hosted embedder under DPA + ZDR adds no new class of processing. Redaction before any route stands: only redacted text is embedded. The local route remains the platform default and names no sub-processor. The erasure routine's git step is `git filter-repo`, then `git reflog expire --expire=now --all` and `git gc --prune=now` on the bare repository and on the VPC 2 mirror — there is no forge and no indexer (ADR 0024); every Forgejo phrase in this ADR has been rewritten in place to say so. Everything else stands.

## Amendment — 2026-08-30, the promise narrowed to what the routine does (ticket 79, the pre-build gate; applied by T-001)

This ADR's title promised personal data "erased from every copy by a routine". The routine does not do that, and the defect was the sentence rather than the design (architecture review pass 2, finding DF6). The routine reaches every **actor id** the platform wrote — `human:<email>` across history, `bundle_commit` rows, `verification.content_hash` values, git author lines, the member row. It does **not** reach a person's name written *inside a concept body*, which is exactly what a sector capability statement contains and what the redaction seam deliberately lets through, because person names are default-off for a binding that is not HR-shaped.

**The rule that decides this is the minting rule** (ADR 0011), and it is worth stating in one line: *the routine rewrites what the platform wrote; a person edits what the company wrote.* An actor id is a record — the platform keeps it because it runs a use case — so the platform may rewrite it across history without asking. A name inside a concept body is **knowledge the company asserts about itself**; rewriting it would rewrite the company's own assertion, and every export already issued would diverge from the repository. So the owner's forward edit stays the routine for that case: names in free text are listed for the owner, the edit is a new commit, and the name remains in earlier commits, in the nightly bundle, in the VPC 2 mirror and in every export already issued.

**The erasure report says exactly that**, in place of any wording implying total erasure. Its wording is: *"Every actor identifier for this person has been rewritten across the repository's history, the index, the evidence and the map, and in the backup copies listed below. Names this person wrote or that were written about them inside concept bodies are listed for the owner to edit; an edit is a new commit and does not remove the name from earlier commits, from copies already exported, or from backup copies taken before <last-dump-at>."* The three backup dates and the *beyond use* paragraph are unchanged.

**`authored concept bodies` joins the DPIA input** as a category of personal data the platform holds, beside `human:<email>`, the `Person` concept and the per-binding LMDB — because the platform now states plainly that it holds it and does not erase it.

**A fourth question for the lawyer**, beside the three already owed (ticket 63): a capability statement naming an employee is knowledge the company asserts about itself and usually has its own lawful basis independent of the platform — but that is a lawyer's sentence, not ours. Whether a forward edit satisfies Article 17 for that category is the question; the design does not wait on the answer, because the narrowed promise is honest either way.

**The alternative, recorded and not taken.** The routine could also run a targeted text replacement over confirmed body occurrences under the same repository lock — deterministic and complete, and it rewrites knowledge the company itself asserts, so every export already issued diverges from the repository. Rejected on the minting rule.

Everything else in this ADR and its amendments stands, including the seam, the three classes and the three tiers of redaction rule.

## Amendment — 2026-09-05, the rewrite target is a per-workspace pseudonym, the user row is pseudonymised, the erasure map grows (T-073, ADR 0035)

Four records. **The target.** The routine's "every `human:<email>` becomes `human:<member-id>` (the per-member ULID minted at member creation)" is struck: across a workspace's files and history, its git author lines by mailmap, its `bundle_commit` rows and its verification rows, `human:<email>` becomes **`human:<erasure pseudonym>`** — an opaque id the minter mints at erasure, one per workspace, that the erasure request keeps beside the person id so a later subject request about what was rewritten can still be answered. It is never the person id, so two workspaces' rewritten histories cannot be joined on one person (ADR 0035's rejected fourth option). **The row.** "The member row pseudonymised" is struck: the **user row** is pseudonymised — email to a unique tombstone, name cleared, id kept, because the ledger's `human:<person id>` rows name it — and the member row is not the target. **The ledger.** It is never rewritten: it names a person by id and never held an email or a name, which is why the routine reaches files and never the ledger (`CODING_RULES.md`'s AUDIT family, T-079). **The map.** The erasure map gains what the identity set holds: invitation emails, verification identifiers, session IP and user agent, and the linked account id. The Consequences' "*member id* enters `CONTEXT.md`" is spent — the word is retired for *person id* and *erasure pseudonym* — and ADR 0012's mailmap line is amended to match. The erasure request table, its pseudonym column and the routine are not built here; the erasure slice's ticket codes against this amendment. Everything else stands.

## Amendment — 2026-09-11, one declared descriptor per category, the hash the seam does not touch, and the pins as read on the day (T-121)

**The descriptors.** Default decision (7), taken by the owner on 10/09/2026 and built here, is recorded: the seam holds **one declared descriptor per redaction category** — its name, the tier it is ordinarily raised at, the entity names whose recognisers raise it, the score threshold, the lemmas Presidio's context enhancer boosts on, the placeholder word, and whether a finding narrows the document — and everything else derives from that one table: the analyzer's registry, the entity-to-category mapping, the category list the `redaction` agreement holds, and `rule_version`. A rule change is therefore one record and one bump, and the review screen's category list is that record again rather than a fourth copy. The table is `apps/worker/src/better_answers_worker/redaction/descriptors.py`; its eight categories are the agreement's eight, held to it in both directions by the worker's suite, which also holds a digest of the table beside `rule_version` so a descriptor edited without the bump is red rather than quietly different. A threshold in that table is policy and not tuning: the always set asks for less confidence than a tier a binding can switch off, because no binding switches the always set off and a miss there is the expensive direction.

**The hash.** Open for the spike, "what `source_document.content_hash` covers after redaction", is decided and struck above: `content_hash` stays the hash of the **original normalised text, computed before the seam runs**, and the redacted text carries the **version string** beside it. A hash holds no value, so hashing before redaction leaks nothing; a hash over the redacted text would move whenever a rule or a pin moved, and would raise *source moved on* for a document nobody had touched. That is what makes a re-detection a platform act that re-baselines the evidence resting on it rather than a change of the source. The columns S1 lands follow this; nothing in S0 computes a hash.

**The pins, re-read on 11/09/2026.** `[DEPS1]` takes a version from the source at the time of the change and not from an ADR written a fortnight earlier, so every one was read again: presidio-analyzer and presidio-anonymizer stand at **2.2.364**; **gliner has moved to 0.2.29**, and the body's `gliner 0.2.28` is struck above; spaCy is **3.8.16** with the English pipeline **en_core_web_sm 3.8.0**, pinned by its release-asset URL because Explosion publishes no PyPI package for it; torch is **2.14.0**, taken from PyTorch's CPU wheel channel on Linux so the worker image carries no CUDA runtime nothing here would call. The model is `urchade/gliner_multi_pii-v1`, unchanged, and `knowledgator/gliner-pii-base-v1.0` is still the one measured against it on the fixture's own page rather than chosen from a benchmark somebody else ran. Each is one exported constant in `redaction/pins.py` carrying the date it was read, and `detector_pin` is derived from all five packages and the model id together — a pin that named only some of them could not say which of them moved.

Everything else in this ADR and its amendments stands, including the seam, the three classes, the three tiers of redaction rule and the officer-block rule.

## Amendment — 2026-09-11, the routine as built: the anchor and its calendar dates, the identity arm, the mirror's prune, the replay copy, the tools in the api image and the subject identifier set (T-124)

Six records. Five are the default decisions the S0 spec took and the owner confirmed at `/to-tickets` on 10/09/2026; the sixth is the one the owner took at the architecture pass of the same day. The calendar rule under the first is a correction the build made to itself.

**The anchor, and the four dates as a calendar computes them.** The report's beyond-use dates are computed from the instant the routine took `pg_advisory_lock(41)` — `erasure_request.locked_at` and `anchored_at` are one instant — and the report **names which anchor it used**, because when O1 lands `backup_run` the anchor becomes the stamp of the last dump before the rewrite, which is what the 2026-08-28 backups amendment above asks for and what there is no row to read today. The four tiers are **calendar intervals and not counts of days**: `deploy/backup.sh` writes each dump's `backup_run.expires_at` as `now() + interval '<life>'` with the tiers spelled "48 hours", "30 days", "8 weeks" and "6 months", so the monthly tier is Postgres's own month arithmetic. A report promising 183 days would disagree with the platform's own row for the same copy by up to three days — a request anchored on 31 August runs to 28 February by the calendar and to 2 March by the count — and on the day the anchor moves to `backup_run` the report would print a date that was not the row's. The rule is the one the subject request's deadline already states (T-123), reused rather than written a third time: the same day of the month that many months on, or that month's last day where the month is too short. The report's date is therefore **the row's promise**, and the object store's lifecycle rule, which is set by hand in days and knows nothing of a calendar, is configured no shorter than it.

**The identity set, on the person's last membership.** Default decision (1). Where the requesting workspace holds the person's only membership the **user row is pseudonymised** — email to a unique tombstone, name cleared, id kept, because the ledger's rows name it — and the person's sessions, verification rows, invitations and linked accounts are deleted. **The invitations on that arm are deleted in every workspace, and they are the only write of the step that leaves the erasing one** (S0's review, 11/09/2026): the other three are keyed by the person and go with them, while an invitation is keyed by the **address**, so one left standing in another company's workspace is a live copy of the address the report has just told the subject was rewritten — and one that is opened puts that address back into a user row. The person has left the platform on this arm and the write is the platform principal's, not an Admin's, which is what carries it across the fence. Where other memberships stand, the identity set is left whole for the request that ends the last one — **including the invitations**, because the person remains somebody's member and their address is still theirs to be invited by, and an invitation another company sent is that company's record to answer for. The **erasure map** is fenced to the erasing workspace on every family either way: the map is what an access answer is written from, and a document handed to one company is not where another's records are listed, so on the last-membership arm the count found and the count deleted may differ. **This workspace's membership is ended on both arms**: the person is erased from this workspace either way, and a membership that outlived the erasure would be the one row that put them back into it. The report says which arm ran. The writes are the erasure slice's own, made through the Postgres door's unscoped identity transaction with every table it touches recorded as cross-owner access, because the identity tables belong to the api's auth module. The judgement — whether another membership stands — is the **platform principal's**, made under `process:better-answers-erasure` and never shown to a workspace Admin, so it is not the cross-tenant oracle ADR 0035 rejected.

**The mirror's prune is the backup service's.** Default decision (3). After a nightly `git push --mirror` that replaced refs, the same job runs `git reflog expire --expire=now --all` and `git gc --prune=now` on the mirror. This ADR's "gc on both copies" is therefore the routine acting on the bare repository under its own lock and the backup service acting for the routine on the mirror that night, within the report's first date. The routine does not reach VPC 2 and holds no credential for it (ADR 0024), so the alternative — the routine pushing and pruning the second copy itself — would give the app tier a second estate's key for one step of one routine. **T-125 lands the script line; what is recorded here is the decision.**

**The replay copy, under the platform prefix.** Default decision (4). The completed request is written to the object store at `erasures/<workspace id>/<erasure request id>.json` through the object door this ticket founded, under the platform's own prefix, which no workspace principal can address. It carries the workspace, the person id where the subject holds a login and **no key at all where they hold none**, the erasure pseudonym, `completed_at`, the identifier set the suppressions were written from, and the erasure map. Each of those is there because a restore from a dump taken **before** the request brings the person's data back with no `erasure_request` row and no `subject_request` row anywhere to say an erasure is owed: the copy is the only trace that survives such a restore, and `replay-erasures --since` is read against it. It is written **before** the completion commits, from one clock reading used twice, so a run that dies between the two leaves a copy without its row — which is a re-run's input, the routine being idempotent — rather than a completion with no copy, which is the failure the copy exists to prevent. It is deliberately **not the report's twin**, and the two are starved of opposite things: the report is a document put into a person's hands and is handed neither the identifier set nor the pseudonym, because a report naming the pseudonym would be the cross-workspace join ADR 0035 exists to prevent, while the copy is the input to a routine nobody is handed and carries both. So the copy is restricted personal data of the same class as the `suppression` table, and the report's beyond-use dates cover it as they cover every dump.

**The tools the routine uses, in the api image.** Default decision (5). `apps/api/Dockerfile`'s runtime stage carries **git** — the base image carries none, and this image is the only process that writes a workspace's repository (ADR 0012) — and **`git-filter-repo` 2.47.0 with the Python it runs on**, read from PyPI on 11/09/2026 and installed from there at that exact version rather than from apt, which packages 2.38.0. The pin is what keeps the image from skewing with the machines the rewrite is proved on; the api's image test reads the version back out of the built image, so an install that silently stopped happening is red rather than a rewrite that fails in production. The **recorded and rejected alternative is a dulwich rewrite in the worker**: the app is the only git writer and the worker holds no git credential, so that alternative founds a second git writer for one routine and hands the worker a credential the worker's own rules say it does not have.

**The subject identifier set, and the clock.** The decision the owner took on 10/09/2026 at the architecture pass. `subject_request` names its subject by an **identifier set** — the emails and other identifiers the company's files know the person by — beside a **nullable person id**, with `clock_started_at` and `extended_to` for Article 12's extension, the due date being one month on by the calendar rule above. The set is what every store family's finder is given and what the suppressions are written from; it is read only by an Admin, and the replay copy carries it because a restored database older than the request holds no row it could be read off. It is what makes a request answerable for **a person the company's files name who never signed in**: there is no user row to pseudonymise and no history to rewrite, and the whole of the erasure for them is the suppressions the map's documents produce. An access request is answered in **locations and categories** — which store family holds something, and of what kind — and never in the passage itself, because an answer that quoted the text would hand one person another person's document.

Everything else in this ADR and its amendments stands, including the seam, the three classes, the three tiers of redaction rule, the officer-block rule and the report's fixed wording.
