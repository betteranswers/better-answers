# A composition cites its concept by a footnote labelled by the include; the footnote text is never stored; one markdown form is stored and rendered, and the editor is a view over it

A composition's prose — a guide section's Brief, a response — is stored as markdown, and every claim in it that rests on a concept carries a **citation marker**: a markdown footnote reference whose label is the include's id (`…within 30 days[^i7].`). This is OKF's own convention one level up: inside a concept file a body footnote labelled by a `sources[].id` attributes one claim to one whole source (`docs/okf-v02.md`); inside a composition the same mark attributes one claim to one **include** row, which carries the concept's IRI, the context wording chosen (its heading *and* the hash of that section's text), the concept's content hash at generation and the cited span. The footnote **definitions are never stored**: they are rendered from the include rows every time the prose is shown, exported or copied, so a renamed concept never leaves a stale footnote behind. **Rows own membership, markers own placement**, reconciled at save — a marker whose label has no include row is refused before a version is written; an include with no marker is allowed and shown "not placed"; deleting a marker never deletes its row. Two footnote kinds share one syntax and the page always says which: an OKF *source* footnote in a concept body has its definition in the file; an *include* marker in a composition has none. There is **one stored form** — markdown, for compositions and for concept bodies alike — and **one renderer**, a pure function in `packages/` from prose plus include rows plus trust state to markdown, with two profiles (trust words as text tags for the MCP *read guide* tool and the labelled export; none for the clipboard). The editor is a view over that form: visual by default, with the marker as a chip that can be moved or deleted but not typed into and that marks the whole cited span (changing the words inside it asks first — "this rests on *Implementation timeline*: change the concept, or keep your wording as uncited"); source mode one keystroke away for a concept body, which opens in source when its markdown holds anything the visual mode would lose; and **nothing is saved that did not change** — the round-tripped text is compared with the stored text and an equal result writes no version and no commit, so a no-op save never moves a content hash and never flags a citing section.

We decided this because the three things the guide page promises — the passage beside the claim, the contradiction check at the sentence, and a copied text that keeps its citations — all need a mark in the stored prose that survives editing, and every alternative loses one of them; because storing footnote text would be a second home for the concept's title and source, drifting the moment either changes; because a rich-text editor storing its own format would give one text two forms and put a conversion on every MCP read while making the concept file no longer the thing edited; and because an editor that normalises on save silently flags every include *changed since checked* on the day someone opens a body and touches nothing — the failure two reviewers named first (research 57).

## Considered options

- **A markdown link on the claim text pointing at the concept's IRI** — standard markdown, but every cited phrase becomes a hyperlink on the page and on paste, and a link has nowhere to say which wording and which version.
- **No marker in the prose; citations only as the include list beside the paragraph** — the passage cannot sit beside its claim, the contradiction check works per paragraph, and copy can number nothing.
- **Footnote definitions stored in the prose** — a stale title and source on every rename; the copy renderer and the page disagreeing about the same include.
- **A rich-text editor storing editor JSON or HTML, markdown derived on the way out** — two formats for one text; the concept body no longer editable in the file's own form.
- **Markdown source only** — honest and simple; every Sales reader becomes a markdown author, which fails the UX bar (`[UX1]`, research 43).
- **Autosave of compositions** — a version per pause against an append-only version table; an explicit save (one version per save, a client-side draft, confirm on leaving) instead.

## Consequences

- `composition_include` carries `wording_heading` and `wording_hash` beside the concept hash; a renamed wording reads as *wording renamed*, a vanished one as *no longer exists*; matched by hash when the heading is gone (ticket 41's schema spike; ticket 50 says what the section hash covers and whether duplicate headings are refused at commit).
- The **promotion gate** must rewrite include markers into `sources[]` entries with body footnotes labelled by those ids when it mints an `Answer` concept — include ids never enter the bundle (ticket 37).
- A copied Detail atom carries its body's OKF source footnotes as well as the include's citation; the clipboard artefact is rich text with superscript numbers and a trailing *Sources* list (concept title · source and locator · the wording used — no platform link and no trust words; the way back is the `usage` row) and plain text with bracketed numbers; numbers restart with every copy and the preview says so. Real word-processor footnotes cannot be made from an HTML paste; a paste matrix (Word desktop and web, Google Docs, "keep text only") is an acceptance line for the build.
- On a Brief a paragraph shows "rests on N concepts"; the *no citation* tag appears where the gate acts — the Detail layer and the copy preview — and the bid writer's gate treats uncited text as below threshold.
- The visual editor is built from Tiptap 3 with its official markdown extension (the chip as a custom inline atom with its own tokenizer, parser and renderer; unknown markdown kept in a raw block or the body refused visual mode), the source mode from CodeMirror 6 with its markdown language; versions are read from Context7 in the build PR (`[DEPS1]`). Neither library is accessible on its own: the editor is a named `textbox`, outcomes go to a `status` region, the chip is a named inline atom reached by arrow keys and moved by cut and paste, focus is never obscured, targets are 24 px, and the source editor's Tab capture has a listed escape (`[A11Y1]`).
- History keeps three views — a word-level prose diff, an include-list diff over (IRI, wording heading, section hash), a section-tree diff — and a concept's history is its commits.
- The read renderer joins include rows in one query; a per-include fetch (200 rows per guide read) breaks `[UX2]`.
- `CONTEXT.md` gains *citation marker* and *layer (of a section)*; ADRs 0004 and 0012 are amended (ticket 19); nothing in ADRs 0001–0003, 0005–0011, 0013–0014 reopens.

## Amendment — 2026-08-30, roles are levels (ticket 79, the pre-build gate; applied by T-001)

ADR 0019 made roles **levels — Admin · Editor · Viewer — never job titles**, and that rename never reached this file. Where this ADR says *Sales reader* read **Viewer**; where it says *bid writer* read **Editor**. The rejected "markdown source only" option reads: every Viewer would become a markdown author, which fails the UX bar. The gate that treats uncited text as below threshold is the **Editor's**. Everything else stands.
