# The worker composes cocoindex's building blocks and writes only what the engine has no block for; the exit stays cheap

**Where this came from.** Ticket 53 (27 August 2026) drew the line between what the knowledge worker builds and what it takes from cocoindex — research 54's *ours / shared / theirs* table — and recorded it in the constitution as the cocoindex rule. Nothing the table names exists yet: cocoindex is in no manifest and no source file, and the one live clause is the DDL invariant. A specification with no code to check it against is not a coding rule (the coding-rules audit of 5 September 2026, T-078), so the decision is recorded here in the rule's own words, and the rule keeps the two sentences a reviewer can check.

**Theirs — the blocks the worker composes and never rebuilds.** Per-component commit; memoisation with keys and states; stable ids; target sync with deletes; `mount_each` isolation; cooperative timeouts; exception handlers; `stats_group` and `watch()`; one `Environment` per binding — one LMDB per binding (ADR 0005, 2026-08-27 amendment). Rebuilding any of these is the failure this record exists to stop.

**Ours — what the engine has no block for.** The run key (cocoindex's *stable id* is a different word for a different thing); claim, lease, heartbeat and reaper; attempt count and poison threshold; the source-document catalogue with its source id and `gone_at`; retention membership; priced-versus-actual; outcome rows, for changes only; the object-store landing; one run per binding; supervision. These are rows the app's schema owns and the control plane reads (ADR 0005).

**Shared.** The landing checkpoint, grace and run signals: cocoindex reports them, the worker records them.

**What is never relied on.** ~~Undocumented API — `use_state` — is never called.~~ (struck 2026-09-10 — the amendment below: public but undocumented, and never called.) `use_mount` never fans documents onto the critical path; `mount_each` does the isolating.

**The exit stays cheap.** cocoindex types never cross a module seam; the catalogue and the run rows are the durable truth; every LMDB is disposable — never backed up, wiped and reprocessed on erasure (ADR 0005). Every cocoindex target is `managed_by="user"` and the app owns all DDL (ADR 0007, 2026-08-27 amendment): the engine's default `managed_by="system"` would let one binding's deletion drop the shared `index.chunk` and its index under every other binding.

## Considered options

- **Keep the whole table as a rule.** Rejected: a rule is checked against code, and there is no code; the block list drifts from the library's API the day the first pipeline is written, with nothing to flag the drift. The cocoindex rule keeps the two clauses that are checkable now — the seam and the DDL invariant.
- **A thinner *ours* — infer outcomes from `inspect` diffs.** Rejected in ticket 53: cocoindex has no per-item success hook, so outcome rows the worker writes are the only record of what changed.
- **The checkpoint inside cocoindex's work.** Rejected in ticket 53: it collapses into the option above and ties the durable truth to a disposable store.

## Consequences

- The cocoindex rule is two sentences — cocoindex types never cross a module seam; every target is `managed_by="user"` and the app owns all DDL — with this ADR as the pointer for the line itself.
- The first task that adds cocoindex to `apps/worker` reads this record before its first `Environment`, and the table above is what its review checks against.
- Reopening condition: cocoindex documenting a block for anything under *ours*, or removing one under *theirs* — then the line moves, here.

## Amendment — 2026-09-10, a wipe is paired with the deletion of the binding's rows, the memo holds only redacted text, and the seam has a name (T-113)

Measured against the library at `aee7b27d`, the *ours / shared / theirs* line above cuts where it says and `managed_by="user"` does what this record relies on. Three consequences it did not state are stated now. **A wipe is paired with the deletion of the binding's derived rows**, because the LMDB *is* the target-state tracking: wipe it and the next update upserts the documents that still exist and issues no delete for those that went away meanwhile, so "wiped and reprocessed" would leave a withdrawn document's chunks standing — the one thing ADR 0020's erasure promises does not happen. The wipe is one act in order: the binding's `index.chunk` rows deleted in the app's transaction, the directory removed, an `index` job enqueued; chunk ids are minted from `(source_document_id, ordinal)` so the reprocess upserts. ~~**The memo holds only redacted text**: conversion and ADR 0020's detector sit inside one memoised function whose return value is already redacted, versioned by rule version and detector pin with the applicable suppressions as an argument, and nothing beneath it is memoised — a separately memoised conversion would put the raw text in the store ADR 0020 says holds none.~~ (superseded 2026-09-21 — one memo, the detector's, and no memo holds text: the amendment of that date, below) **The seam has a name**: the cocoindex rule's first sentence is kept by one module, `pipeline/`, whose interface takes and returns plain types and whose implementation alone imports `cocoindex`, refused elsewhere by the ruff rule the worker already uses for `unittest.mock`. `use_state` is exported and public, undocumented on the site only; the intent stands and the reason is reworded above. Everything else stands.

## Amendment — 2026-09-11, the directory's removal is the worker's, at the start of the run the deletion enqueued (T-129)

The amendment above orders the wipe — the binding's `index.chunk` rows deleted in the app's transaction, the directory removed, an `index` job enqueued — without saying whose the middle act is, and read in that order it reads as the app's. **It is the worker's.** A binding's LMDB sits on the worker's own volume and no other process reaches it (ADR 0005), so the app's transaction deletes the rows and enqueues the job and can do nothing at all about a directory; the removal is the first statement of the run that job starts, before the binding's `Environment` is opened. The order inside the run carries the same necessity the order across the two tiers does: a run that opened the store first would answer out of the very memo it was enqueued to throw away, and a directory removed under an open handle leaves the engine writing into a store nothing can read — so the cache entry is evicted and then the directory goes. The three acts still happen in the order the amendment gives them, and the pairing itself stands for the reason it states.

## Amendment — 2026-09-21, one memo and it is the detector's: no memo holds text, the findings memo has a store a wipe spares, and a withholding is never cached

The amendment of 10/09 put conversion and the detector inside one memoised function whose return is redacted text, and said nothing beneath it is memoised. An architecture review on 21/09 — its working papers under `.scratch/architecture-review-2026-09-21/` — found what that shape costs. The memo's key takes five facts of policy beside the text, so a keep, a suppression or a rule switch runs the detector again over text whose answer cannot have moved. The stored return is redacted text, which is the only reason an erasure must remove a binding's store, and removing it re-detects the binding. And a withholding is cached, so a fix to one reaches no standing entry unless somebody remembers a version — T-145 moved the overlap rule with none.

**No memo holds text.** The one memoised function is the detector's: `detected(normalised_text, detection_key)` returns the spans the rules raise — rule, two offsets, score — and is the only memoised function in the estate. The engine keeps a 16-byte fingerprint of a call's arguments and the msgpack of its return, never an argument (read in cocoindex 1.0.22's Python and in the engine's source at `aee7b27d`; held by the worker's LMDB-bytes test, extended to this memo). `landed` stays the per-document component and the ceiling's home, **unmemoised**: convert, detect, raise by the officers-block rule, withhold, hash. Policy — the rules in force, the suppressions, the restores, the seed — is one record handed to the withholding and is part of no key. `CONVERTER_PIN` is in no key either: the text is the key, so a converter upgrade re-detects only a document whose normalised text moved. *Which documents were detected afresh* is answered per document. A finding is never rewritten: what a binding does with one is a *withholding* (`CONTEXT.md`), computed on every run, and the stored finding row's tier is written from it.

**The findings memo has a store of its own per binding, which a wipe spares**, because it holds neither text nor target-state tracking: a fingerprint of each document's text and the rule, location and score of each span — what a marked finding row and `content_hash` already keep. The binding's own store is removed as the amendments of 10/09 and 11/09 say. Where this memo lives is decided here and not later: after the first client's documents, moving it costs a detection of every page held.

**The engine also invalidates an entry when the memoised function's body, module, qualified name or version moves.** No file said so before this one. ~~The suite holds the function's module, name and version as a literal, so a rename is a chosen reprocess and never a drift.~~ (superseded 2026-09-22 — the literal is six and the body is outside it: the amendment of that date, below)

The constraint this drops: *a run over an unchanged binding converts nothing*. Every run now converts and withholds every document; every run already read every original, split every document's chunks and wrote every normalised copy outside the memo. **A spike goes first and can amend this record**: a memoised function called inside a mounted component on 1.0.22 — hit, reuse, garbage collection, no deadlock under `mount_each`; the LMDB's bytes both ways with a canary; invalidation on a body edit and a rename against `version=1`; the findings memo surviving a wipe; and conversion plus withholding in milliseconds per document by media type. If a media type converts at hundreds of milliseconds a page, that type keeps an outer memo over a separate detection app, and detection is spared a wipe all the same. The build lands before the first client's data, after S1.

Rejected: **two nested memos** — `landed` is mounted, so a memo inside it lives in the binding's store and dies in every wipe; **the `finding` table as the cache** — a wipe deletes its unmarked rows, so a partial set reads as complete, and the failure is a document silently un-redacted.

## Amendment — 2026-09-22, the spike ran: the frozen identity is six and not three, and a deletion of a binding's chunk rows is paired with that store's removal whatever enqueued it (T-285)

The amendment above says a spike goes first and can amend this record. It ran on 22/09/2026 against the installed cocoindex 1.0.22, on a laptop and not the worker image, and every claim that amendment puts to it held. The one memoised call is made from inside the sync `landed` body under `mount_each`, eight components in flight over fifty documents, and the host's loop does not deadlock. A run, then a restore, then the rules in force flipped, then the detection key moved take 12, nought, nought and 12 detector passes, and ten policy flips leave the findings store at 188,416 bytes throughout. Every file of that store read as raw bytes holds no planted value, no run of the document's sentence and no placeholder word, while the same scan over a memoised function built to return its own text finds the first two. A run whose binding store was removed takes nought detector passes and re-lands every chunk row. Conversion plus the withholding is 1.0 ms a page over a ten-page `.docx` and 1.5 ms over an eight-page PDF, against detector passes of 2,117 and 1,705 ms a page timed beside them in the same process — under a tenth of one percent, and under a fifth of one percent of T-177's 867 ms a page — and a thousand-document no-op run costs 4.3 seconds where today's costs 0.9. No media type converts at hundreds of milliseconds a page, so the shape is the one memo as this record specifies it and nothing keeps an outer memo.

**The frozen identity is six, and the body is outside it.** `version=1` does replace the body: with it declared, an edit to the body invalidates nothing. Every other member re-detects the binding whole. The qualified name does, with the version declared or without it. The mount path does, and the app's name with it, because a function memo lives under its calling component in that app's store and is fetched by a prefix scan of that path — so the `landed` app's name and the component's subpath are as much the memo's identity as the function's own name is. The module rides in the same fingerprint payload as the qualified name, read in 1.0.22's `function.py` rather than run; the store's directory is the sixth by construction, a different store holding nothing. The suite's literal is therefore module, qualified name, version, mount path, app name and directory, and it is what makes each of those a reprocess somebody chose.

**A deletion of a binding's chunk rows is paired with that store's removal, whatever enqueued the deletion.** The amendment of 10/09 states the pairing from the wipe's side. It holds from the other side too, and the failure there is worse. A reprocess that deletes the binding's chunk rows and leaves its store standing — which is what a *rule-change* reprocess does at HEAD — re-upserts none of them: the store is the target-state tracking, so the engine declares only what it believes has moved, and it believes it has already landed every row. Ten documents, ten rows, the rows deleted and the store left standing: nought rows after the run. The same deletion with the store removed first: ten of ten. This is T-137's owed question answered, and the answer is that a rule change wipes or empties the binding.

**The chunks app's target-state tracking holds no row text.** The review of 21/09 left this unknown and asked the spike for it. The same raw-bytes scan over the binding's own store, after ten chunk rows landed, finds the row's chunk id — which is what proves the scan reads the store — and neither the row's body nor any run of it. The wipe's reason stays the tracking and was never the text.

The spike's code is discarded and its findings are on T-285.
