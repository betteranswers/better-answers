# A boundary schema is generated from its table; a refinement only narrows, written beside the column; and a parity test — not a convention — catches the two disagreeing

ADR 0008 makes zod v4 the single validation library at every boundary and ADR 0007 makes Drizzle the only owner of the schema those boundaries carry, but nothing joined the two: a column and the zod schema over it would be written twice and drift in silence. So **`drizzle-zod` generates every zod schema over a table**, in `packages/schema` and nowhere else, and the package's public entry point exports a **boundary schema** — select, insert and update — for every table it owns. The version is **`drizzle-zod@0.8.3`** (npm packument, read 31/08/2026: `dist-tags.latest`, published 06/08/2025, peers `zod: ^3.25.0 || ^4.0.0` and `drizzle-orm: >=0.36.0`, so `zod 4.5.4` and `drizzle-orm 0.45.2` both satisfy it — `[DEPS1]`; the research file records the empirical check on the exact triple). The evidence for every behavioural claim below is `docs/research/t-011-drizzle-zod.md`, which reads the published `index.mjs` and `.d.ts` files rather than any secondary account of them.

**A generated schema is the table's shape; a boundary's shape is narrower.** `workspace_id` is a ULID branded `WorkspaceId`, not any text; a title is trimmed and non-empty, not any `varchar`; an enum is sometimes narrower at a write than the column allows. That difference is a **refinement**, and where one may sit is this ADR's whole subject.

## Where a refinement sits

**In the second argument of the generating call, in `packages/schema`, one entry per column, written as a callback** — `{ workspaceId: (schema) => schema.regex(ULID).brand<"WorkspaceId">() }`, never `{ workspaceId: z.string().brand<"WorkspaceId">() }`. The two forms are different features, not styles. drizzle-zod's `handleColumns` applies the column's nullability and optionality *after* a callback and `continue`s past them for a plain schema, so a plain schema replaces the column wholesale, nullability included: a nullable `text` refined to `z.string().min(1)` stops accepting `null` — measured — and a select schema then rejects a row Postgres legitimately returned, with no type error anywhere. The callback also ties the refinement to the generated schema's class, so a `text → integer` change turns `(s) => s.toLowerCase()` into `TS2339` where the plain form stays green.

**The one exception, and it is ours: a `customType` column takes a plain schema and must never take a callback.** The types map a custom column by its TypeScript data type and claim `z.ZodString`; the runtime maps it by `column.dataType === 'custom'` and emits `z.any()`. A callback therefore compiles and then throws `TypeError: schema.min is not a function` at module evaluation. `index.chunk`'s untyped vector column is exactly this case (ADR 0007's amendments; the column carries no dimension because a dimension is a workspace's `embedding_route_id`, not a column fact), so its boundary schema is a plain `z.array(z.number())` and assertion 4 below carries the whole burden there. `jsonb().$type<T>()` is the same divergence, milder: the inferred type is `T`, the validation is "is JSON".

**A brand round-trips, and that is why the refinement is declared once.** `HandleRefinement` propagates the refinement's own output type rather than reconciling it with the column's, so `.brand<"WorkspaceId">()` survives `z.infer` and reaches the tRPC router, the generated OpenAPI document and the MCP tool schemas that ADR 0008 feeds from one router. The table itself is not branded — `users.$inferSelect.workspaceId` stays plain `string` — so the **boundary schema, not the Drizzle table, is the source of application-level types**.

## What is never written

**A schema that shadows a table.** A `z.object({ … })` naming a table's columns, anywhere outside `packages/schema`, is a second definition of a shape that already has one, and no test can see it because no test knows it claims to describe a table. Positively: a boundary imports its schema from `@better-answers/schema` and **shapes** it — `.pick()`, `.omit()`, `.extend()` with fields that are not columns, `.partial()`. Shaping composes over the generated schema and stays honest; re-describing a column does not. `drizzle-zod` is import-banned outside `packages/schema` (`no-restricted-imports` in `.oxlintrc.json`, the precedent the identity seam sets for Better Auth (ADR 0009)), and inside it every import goes through one module, because drizzle-orm v1 moves the package to a `drizzle-orm/zod` export condition and that upgrade should be one edit.

## When the generated and the refined disagree

**They disagree silently, by design, and the type system will not save us.** `BuildRefineField` admits any `z.ZodType` for a refinement's output, with nothing tying it back to the column: `createSelectSchema(t, { title: z.number() })` on a `text('title')` column compiles clean and `z.infer` follows the *refinement* — a confident, well-typed lie about the table. That unchecked propagation is the same rule that makes brands work, so we cannot have one without the other. A dropped column does fail `check` (`NoUnknownKeys` yields a `DrizzleTypeError`), though on `createSelectSchema`'s five overloads the message surfaces as `TS2769` pointing at the *table* argument and never names the key. A retyped column, a widened `pgEnum`, and a callback whose method survives the retype with a new meaning (`.min(1)` means "non-empty" on a string and "at least one" on an integer) fail nothing at all.

**So the disagreement is caught by five assertions in `packages/schema`, over a registry, against a real Postgres (`[TEST2]`).** The package exports `boundarySchemas` — one entry per table: `table`, `select`, `insert`, `update`. The test recomputes the **unrefined** generation from the same table and compares.

1. **Every table has a boundary.** The set of `PgTable`s exported from `src/schema.ts` (found with `is(value, PgTable)`) equals the registry's key set. *Catches:* a table added in a migration with no boundary schema over it — invisible to types, because an addition is not an error.
2. **The key sets agree.** `Object.keys(refined.shape)` equals `Object.keys(unrefined.shape)`, for each of the three. *Catches:* a column added or renamed, a `.omit()` that drifted, and a plain-schema refinement that reintroduced a `generatedAlwaysAs` key.
3. **Optionality and nullability agree, per key, at runtime.** For every key, `refined.shape[k].safeParse(undefined).success` equals the unrefined schema's, and the same for `null`. *Catches:* the plain form's exact damage — the stripped `null`, the defaulted column gone required — and a column that gained a `.default()`, went nullable, or became generated without its boundary following.
4. **A refinement only narrows, proved against the column.** For each entry, the fixture rows the **refined** insert schema accepts are inserted into a real Postgres inside a rolled-back transaction; every one must be accepted by the table. *Catches:* the widening the types permit — `(s) => z.string()` over a `varchar(255)`, an enum member the `pgEnum` does not hold, an unvalidated `customType` — and it is the only assertion that can. Rows the refinement *rejects* need no test; rejection is free. (`index.chunk` is list-partitioned by workspace and drizzle-orm 0.45.2 has no partitioning API at all — the parent is an ordinary `pgTable` to Drizzle and to drizzle-zod, the `PARTITION BY LIST` is hand-written SQL — so its fixture creates the workspace partition first, and the partition key is a column like any other with nothing in the schema warning that a row matching no partition is refused.)
5. **The inferred type is pinned.** One `Expect<Equal<z.infer<typeof selectX>, …>>` per boundary schema. *Catches:* the retype hole and the widened `pgEnum` — the two the library declines to check — by making a column's type change a diff a person must consciously accept. This is a test-file type assertion producing no runtime value, and it is the opposite of a shadow schema: a shadow schema quietly claims to describe a table, this one exists to fail when it stops matching.

Assertion 4 is what makes this a test rather than a convention. "A refinement only narrows" is a sentence; inserting what the refinement accepts and letting the column answer is the enforcement.

## Considered options

- **Hand-written zod schemas beside the tables** — the drift this ADR exists to close: two definitions of one shape, the second wrong the day after a migration. Settled against before the task began.
- **Generated schemas with no refinements — narrow at each boundary instead.** Every caller then re-derives the brand, the trim and the ULID check, differently, and the assertions have nothing to compare against because there is no single refined schema. Refinement scatters exactly where `[DESIGN1]` wants it concentrated.
- **The plain-schema refinement form throughout, for its brevity.** Rejected on evidence: it drops the column's nullability and optionality at runtime and hides a column's type change from the compiler. Kept for `customType` columns only, where the callback form throws.
- **A type-level drift check alone** (assertion 5 without 1–4). It cannot see widening at all — a `z.string()` over a `varchar(255)` has the right inferred type and the wrong accepted set — and it says nothing about a table nobody generated a schema for.
- **A runtime parity check alone** (1–4 without 5). Cheaper, and blind to the retype hole: `z.number()` on a `text` column changes the inferred type without changing whether the key exists or is optional, and Postgres will happily accept a number written into text.
- **`drizzle-kit`'s snapshot diff as the drift signal.** It watches the migration, not the boundary, and it cannot model `index.chunk`'s partitioning at all, so it would be silent on precisely the table that most needs watching.
- **`createSchemaFactory({ coerce })`** for coercion at the boundary — rejected: coercion turns a wrong type into a plausible value, and `[SEC2]`'s boundaries want a refusal. The factory stays in reserve for the one thing it uniquely does, a `zodInstance` override.

## Consequences

- `packages/schema` gains `drizzle-zod@0.8.3` and `drizzle-orm@0.45.2` as dependencies, one module holding every `drizzle-zod` import, a registry (`boundarySchemas`) on its public entry point, and the five assertions. `drizzle-zod` is import-banned elsewhere.
- **A known staleness, with a trigger.** `drizzle-zod@0.8.3` shipped 06/08/2025; `drizzle-orm@0.45.2` shipped 27/03/2026. No drizzle-zod release has been cut against 0.45.x — the peer range is open-ended and the compatibility is empirical, not promised — and active development is on a `1.0.0-beta` line that requires `drizzle-orm >=1.0.0-beta.2`, which we cannot take while drizzle-orm is 0.x. Every official code sample now imports from `drizzle-orm/zod`, an export condition `0.45.2` does not have. A column type introduced after 0.36 may fall through `GetZodType` to a bare `z.ZodType`; assertion 4 is what catches that. Revisit at the drizzle-orm v1 upgrade, when the import path is the one edit.
- `$defaultFn(fn)` and a database `.default()` are indistinguishable to a generated schema — both are `hasDefault` — so the schema never tells a reader where a value comes from. Where that matters, the answer is a comment at the column, not a second schema.
- `CONTEXT.md` gains **boundary schema** and **refinement**.
- Consistent with ADR 0007 and ADR 0008; it contradicts neither. It extends 0007's one-migration-owner rule by a layer — the table is the single source of truth for its own shape *and* for the schema over that shape, exactly as the worker's reflected definitions are derived rather than written — and it answers 0008's "zod v4 is the single validation library at every boundary" with where a boundary's zod comes from, not whether zod is used.
- `T-003` is the first task that writes tables in anger and where the registry and the five assertions first carry weight.

## Amendment — 2026-09-01, the `customType` exception is constructed and tested per shape (T-025; evidence from T-003, ADR 0032, PR 5)

The plain schema the `customType` exception forces replaces the generated field **wholesale, per generating call**: `createUpdateSchema`'s `.optional()` wrapper is discarded along with the column's nullability, so an update schema that reuses the insert's plain schema demands the column on every update. `T-003` (ADR 0032, PR 5) hit this on `chunkUpdate` exactly as *Where a refinement sits* warns — `embedding` became required on update until review caught it. So where the exception applies, **the plain schema is constructed and tested per shape**: select and insert take the plain schema, update takes it wrapped in `.optional()`, and each of the three has its own test that the column is required, required and optional in turn (`packages/schema/test/boundary-schemas.test.ts`, *the customType exception, per shape*). Assertion 3 exempts the `customType` column, because the unrefined generation is `z.any()` there and offers nothing to compare against; that is why the per-shape tests are written by hand rather than derived. Everything else stands.
