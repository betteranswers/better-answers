# A person has one id — the identity set's user row, minted by the platform's minter that Better Auth is handed too, written `human:<person id>` on every record the platform keeps and never into a concept file; revocation has two scopes; erasure rewrites to a per-workspace pseudonym

One person was named three ways and none of them was what the glossary said. A concept file names them `human:<email>` (ADR 0019); the erasure routine promised to rewrite that to `human:<member-id>`, which the glossary called a per-member ULID minted at member creation (ADR 0020; ADR 0014's 2026-08-27 amendment) — but nothing minted one: provisioning composed the first Admin's member id from other ids, Better Auth minted its own shape everywhere else, and the only ULID function in the tree was a test helper with no time component; and the ledger T-059 founds named its actor by a "stable identity id" nobody had defined. Five tickets about to build (T-059, T-060, T-061, T-052, T-054) each needed the answer and would each have chosen one. This record is the identity grilling of 5 September 2026 (the T-063 spec, `apps/docs-site/specs/T-063.md`); its decisions are taken, and the four code slices that follow it (T-074, T-075, T-076, T-077) code against them.

**A person has one id.** It is the id on the identity set's `user` row (ADR 0009), minted by the platform's own minter, carried as `userId` on every Principal, and written as **`human:<person id>`** on every record the platform keeps — the ledger's actor, a commit trailer's `Actor:`, a suggestion's proposer and decider, an access request's requester, the person half of a `group_member` key — and never into a concept file, which keeps `human:<email>` in `generated.by` and `verified[].by` exactly as ADR 0019 chose. The **member row's key** is a primary key the organisation plugin requires and nothing of ours references, joins on or shows: every People act keys by (workspace, person). The glossary's *member id* is retired; the code's name `userId` stays, because the glossary says so and no rename is made.

**One minter, and Better Auth is handed it.** One pure function in the kernel returns a ULID — 48 bits of milliseconds, 80 bits of randomness, monotonic within a millisecond, Crockford base32, 26 characters — and every id the platform writes comes from it. Better Auth receives the same function through its custom id-generation option, so users, sessions, members, invitations and, later, groups, requests and ledger rows share one shape that one boundary refinement checks (ADR 0028) and one contracts fixture pins for both tiers (ADR 0031); a ledger's id order agrees with its timestamps. Session tokens, authorisation codes, client secrets and token `jti` values are produced by the library's own random-string paths and never by the minter, so a time-ordered id never becomes a guessable secret. Installing a custom minter switches off the library's opaque-invitation-id heuristic, after which accepting, rejecting or cancelling an invitation by id requires a verified email; the option that requires it is set explicitly to true, so T-027's accept page rests on a decision rather than a default.

**Revocation has two scopes.** *In a workspace*: a workspace Admin ends every session and token a person holds there by an instant on the membership row, which the resolver reads in the same membership query as the person-level instant (ADR 0009, 2026-09-01 amendment) and refuses against with the same *credentials revoked* word; only the tokens whose consented workspace is that one are ended. Nothing outside that workspace changes, and the Admin never learns whether the person belongs to another — the refusal is the same whether they do or not. *Everywhere*: the operator ends every session and token the person holds by the instant on the person — one act, taken by the platform principal until T-028 gives the operator a principal kind, and never callable from a workspace Admin's procedure. Both scopes end what was issued; a fresh sign-in mints anew. There is no *Suspended* state.

**Erasure rewrites to a per-workspace pseudonym.** On a valid erasure request, `human:<email>` across a workspace's files and history, its git author lines by mailmap, and its `bundle_commit` and verification rows are rewritten to `human:<erasure pseudonym>` — an opaque id the minter mints at erasure, one per workspace, recorded on the erasure request beside the person id so a later subject request can still be answered — and never to the person id, so two workspaces' rewritten histories cannot be joined on one person. The `human:` prefix survives the rewrite, so the tier ADR 0019 derives from it does too. The user row is pseudonymised — email to a unique tombstone, name cleared, id kept, because ledger rows name it — and the member row is not the target. The ledger never held an email or a name and is never rewritten.

**The actor form and the ledger's words, stated here as the interface T-059 codes.** The kernel gains an actor-id type in three forms — `human:<person id>`, `process:better-answers-<purpose>`, or an agent's id as ADR 0019 shapes it — and one function deriving it from a Principal, so no slice composes the string by hand. The audit slice has two doors and no third: one takes a Principal and derives the actor; the other takes the platform principal and an explicit actor, typed so a user principal cannot reach it, and the access-request act (T-061) is its one caller. The ledger's families are four words — **people**, **knowledge**, **sources**, **platform** — and an act is named `family.subject.verb` (`people.member.role_changed`, `knowledge.suggestion.accepted`, `sources.binding.published`, `platform.reconciler.replayed`): the family set is the only closed list, each slice declares its own acts against a template type the audit slice exports, and one test checks the prefix both ways. Corrections and promotion decisions are knowledge acts; routes, ceilings, exports and provisioning are platform acts. Runs, the answer audit (ADR 0017), signals and alerts (ADR 0025), spend and the inbox are their own records and never ledger rows.

We decided this because a person named by three ids is joined by none of them — a ledger keyed on one, a commit trailer on another and a file on a third cannot answer *what did this person do* without a mapping table nobody owns; because a per-membership id leaves every act a person performs before a membership exists — a first sign-in, an access request — with no actor at all; because the platform's records are the platform's to key, and a shape the library chose is a shape the boundary refinement, the ledger's ordering and the Python tier would each have to learn separately; because one workspace Admin ending a person's sessions in another company's tenant is one company's decision reaching another's, and any rule that decides by counting memberships is an oracle over them; and because an erasure target that is the same string in every workspace lets two workspaces' exported histories be joined on the very person the request was meant to unlink.

## Considered options

- **A per-workspace pseudonym as the everyday id** — the erasure target used for everything, so nothing ever needs rewriting. Rejected: two ids per person on every record, and a join for every act a person performs before a membership exists.
- **Better Auth's own id shape kept**, the platform's minter used only for the platform's own tables. Rejected: two id shapes and two refinements, a ledger whose id order disagrees with its timestamps, and a fixture the Python tier cannot pin.
- **The sole-membership rule for revocation** — a workspace Admin's revocation ends everything when this is the person's only membership, and only this workspace's tokens otherwise. Rejected: a cross-tenant oracle (the outcome tells the Admin whether other memberships exist), a race with an invitation accepted elsewhere in the same instant, and a tenant Admin's transaction reaching other tenants' credentials.
- **One global rewrite target on erasure** — `human:<person id>` in every workspace's history. Rejected: linkable across controllers; two workspaces' rewritten histories join on the person the request unlinked.
- **The external UI's *Suspended* member status** — a state a member is put into and taken out of. Rejected: revocation ends what was issued and a fresh sign-in mints anew, and a state would be a second thing the resolver reads.

## Consequences

- **Amends ADR 0009** (the id the `admin()` refusal protects is the person id; revocation's two scopes; the minter behind Better Auth), **ADR 0014** (the member row carries no id of ours), **ADR 0019** (the erasure rewrite target is the erasure pseudonym), **ADR 0020** (the user row pseudonymised, the pseudonym minted at erasure and kept on the request, the erasure map's new entries) and **ADR 0012** (the mailmap target), each by a dated amendment with its index row in the same commit.
- **`CONTEXT.md`** gains *person id*, *erasure pseudonym*, *operator* and *revoke credentials*; retires *member id*; *audit event* names its four families, *actor id* the ledger's form (and its process form reads `process:better-answers-<purpose>`, as the *platform principal* entry already did), *erasure request* the pseudonym it carries; *minter* enters so the word stops colliding with the *minting rule* (ADR 0011). The words land before any code names them (`[GLOSSARY1]`, T-073).
- **The code lands in four slices**: the minter, Better Auth handed it, the identity refinements and the contracts fixture (T-074); the membership row's revocation instant, the resolver's refusal and the token predicate (T-075); the kernel's actor id, the role refusal and its guard, the result convention and the constraint helper (T-076); the table-ownership map ADR 0029 promised, the membership read moved into the workspaces slice and the delete-user guard (T-077). The workspace-scoped act with its ledger row is T-027's; the operator principal and *revoke everywhere* under it are T-028's; the ledger table, the audit slice and the people-model ADR are T-059's; the erasure routine, the erasure request table and its pseudonym column are the erasure slice's ticket.
- Pre-production: development databases are re-seeded; no data migration is written.
- Reopens nothing in ADRs 0001–0008, 0010–0011, 0013, 0015–0018, 0021–0034; amends 0009, 0012, 0014, 0019 and 0020 as above.
