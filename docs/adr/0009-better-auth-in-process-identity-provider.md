# Better Auth, run in-process, is the identity provider for app login and the OAuth 2.1 MCP surface

The app tier (ADR 0006) embeds Better Auth as a library — its MCP, client-ID-metadata-document, email-OTP and organization plugins over our own Drizzle tables — and is itself the OAuth 2.1 authorization server that Claude Teams connectors register against (dynamic client registration or CIMD, PKCE, protected-resource metadata on a 401, RFC 8414 discovery, RFC 8707 audience binding) and the email-code login for the web app's three roles. We chose this over a separate identity-provider container (Keycloak, the runner-up) because the whole platform is one founder's Coolify deployment (ADR 0005) and every container is an operational cost paid forever: Better Auth adds no process, no memory budget, no second backup story and no second migration owner (ADR 0007) — its tables live in the app's schema under the app's migrations and are backed up with Postgres. It also gives us the per-user principal `{workspace, user, role}` inside the access token from the organization plugin, which is what `[SEC2]` needs at the MCP boundary, without a claim-mapper configuration living outside the repo. The MCP SDK's own OAuth helpers were not an option: they are Express-only and frozen in `server-legacy`; only `requireBearerAuth` is runtime-neutral, and it becomes the seam — the MCP server verifies a token and derives a Principal, and nothing behind that seam knows which library minted the token.

Better Auth was acquired by Vercel on 7 July 2026. The library stays MIT, keeps its name, its team and its open contribution model, and Vercel's stated direction for it — agents acting on users' behalf with scoped, revocable access — is the direction our later acting-credential class needs. We consume it only as an in-process library, never as a Vercel-hosted service, so the acquisition changes stewardship, not our deployment. Stewardship is a watch item for architecture review pass 2.

## Considered options

- **Keycloak 26.7.2** — one container, Apache-2.0, an official MCP guide, anonymous DCR whitelisted to Anthropic's egress range, audience via mapper; the right answer if the authorization server should live out of process. Costs ~1.25 GB, a third-party extension for email-code login, and configuration outside the repo. Kept as the runner-up behind the same seam.
- **SuperTokens** — the original candidate; its OAuth2 provider is managed-only and paid, and its MCP plugin is beta on MCP SDK v1 with no CIMD.
- **Supabase Auth** — would move the database home (ADR 0007's fallback), has no audience binding, and would be a second migration owner.
- **Hosted (Auth0 UK region)** — the fallback if self-hosting auth fails in practice; puts every login on a third party's uptime and terms.
- **Zitadel, Authentik, Ory, WorkOS, Clerk, Stytch** — rejected in research 40 for missing RFC 8414, closed DCR, container count, or US-only data.

## Consequences

- The authorization server is part of the app: `apps/api/` serves `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource` and the registration, authorize and token endpoints; `mcp.` stays a separate hostname with no Access policy (ticket 38).
- Auth tables are ordinary tables in the app's schema; workspace isolation applies to them like every other table (ADR 0005).
- Two things are unverified and are proved by the prototype on the read-only MCP ticket before any build: that a Claude Teams connector completes DCR or CIMD against this server with its real registration body, and that the access token carries the active organisation as the workspace claim. If either fails, Keycloak replaces the authorization-server half behind the `requireBearerAuth` seam; the login half stays.
- The library's version is read from Context7 in the PR that installs it (`[DEPS1]`), not from research 40.
- A bearer token for scripts and Claude Code stays as a second credential path, minted and revoked by the app, never org-shared.

## Amendment — 2026-08-27, the prototype named and the token's shape fixed (ticket 21, ADR 0018)

The two unverified things are proved by prototype ticket 61 against Liam's Claude Teams workspace. The access token carries `{workspace, user, role}` and the MCP audience, lives one hour with rotating refresh; groups never enter it — role and groups are re-read per call with a `credentials_revoked_at` check, since a JWT cannot be revoked server-side. `customAccessTokenClaims` receives no role, so the claim is a `member` lookup at issue time and a cross-check thereafter. A single-organisation user gets `activeOrganizationId` at session creation; a multi-organisation user picks before consent (`postLogin.page` + `shouldRedirect`).

## Amendment — 2026-08-30, Better Auth is a stay, with the exit written as a test (ticket 79, the pre-build gate; applied by T-001)

This ADR left stewardship under Vercel as "a watch item for architecture review pass 2". Pass 2 has run. The answer is **stay** — and the reasons, the triggers and the true cost of the fallback are written down here rather than carried as a feeling.

**Why stay, and what is now proved.** Prototype 61 drove the real claude.ai connector through Better Auth 1.7.2 against this server: CIMD chosen over DCR, the workspace claim carried, a two-organisation picker round-tripping in under a second, every entry answered. **The two things this ADR named as unverified are proved.** It still costs one container fewer than every alternative, adds no second migration owner and no second backup story.

**The risk is narrower than "Vercel might close it."** Vercel needs the library — it is the foundation of Connect. The real risk is the ordinary shape of an open-source project with a commercial parent: the core stays healthy because the hosted product depends on it, and the edges only self-hosters use get less attention. There is direct evidence of that edge from our own prototype: `@better-auth/cimd/node` 1.7.2 is broken on every supported Node and throws before a packet leaves the machine, with **no upstream issue filed by anyone**; `@better-auth/cli` 1.4.21 lags core and its generated migration misses `account.issuer`; and prototype 61 hit three further silent configuration traps, each fatal to the whole connection and each absent from the documentation. **The entire MCP path runs through exactly one of those edges.** The watch item is therefore not abandonment — it is *whether the self-hosted OAuth-provider path stays maintained while Connect becomes where agent identity ships.*

**Three leave-triggers. Any one starts a migration; none of them is a feeling.**

1. **A licence or distribution change** on `better-auth` core or `@better-auth/oauth-provider` — MIT becomes anything else, or the OAuth provider moves behind a paid or hosted-only tier.
2. **The self-hosted OAuth path stops being supported** — `oauth-provider` or `cimd` deprecated, folded into Connect, or twelve months without a release while core keeps shipping.
3. **A security defect we report goes unfixed for one release cycle** on a plugin in our auth path.

Reviewed at the first client's renewal, or the moment a trigger fires. **Ticket 83 is the first live test of trigger 3**: a reported bug with a known, small fix on exactly the plugin the MCP path depends on. How long it takes to land is the first real datum, and collecting it costs nothing.

**The Keycloak fallback is real, and it is not a drop-in.** This ADR's consequence — "Keycloak replaces the authorization-server half behind the `requireBearerAuth` seam; the login half stays" — understated the work. Two things it did not account for. First, we are **CIMD-only** (research 80, fork F2) and Keycloak does DCR, not CIMD, so swapping providers reopens DCR and re-proves the whole claude.ai connector path prototype 61 measured. Second, Better Auth is not only the authorization server: it is also the app's email-code login **and its organisation model, which is where the `workspace` claim comes from**. Call it **two to three weeks, not two days.** That is still worth having — it means no trigger above is an existential event — but the true number is what belongs in an ADR.

**The seam becomes a rule.** `requireBearerAuth` was named here as the seam; it is now a rule of the constitution (retired to this ADR on 2026-09-05; amendment below) and **lint-enforced**: no Better Auth type crosses into `packages/core`, and no `better-auth` or `@better-auth/*` import appears outside the auth module. The seam is what makes two to three weeks two to three weeks rather than a rewrite.

**An SSRF policy on the CIMD fetcher, applied here.** The fetcher retrieves a URL the caller supplies, so it resolves the address before connecting, refuses private and link-local ranges, caps redirects and body size, and re-checks after every redirect. The policy is owned by this ADR and carried with the `@better-auth/cimd/node` fix as a `lifts/` snapshot with its `THIRD_PARTY_NOTICES.md` and a removal condition — the upstream release that fixes it (`[LIFT1]`, ADR 0027).

## Amendment — 2026-09-01, the identity set is isolated by key, not by scope (T-004; research `docs/research/better-auth-tenancy-and-agent-auth-2026-09-01.md`)

This ADR's consequence "Auth tables are ordinary tables in the app's schema; workspace isolation applies to them like every other table (ADR 0005)" is corrected. **Auth tables are the identity set, not tenant tables: Better Auth reads them by secret or principal id before any workspace exists and returns the workspace id, so they carry no `workspace_id` and no RLS policy, are declared by name as the RLS coverage test's exemption, and the tenant guarantee (ADR 0032) begins at the first tenant row a resolved principal reaches.** The set is sixteen tables — Better Auth's `user`, `session`, `account`, `verification`, the JWT plugin's `jwks`, the organisation plugin's `workspace`, `member` and `invitation`, the OAuth provider's seven `oauth_*` tables and its limiter's `rate_limit` — named in `packages/schema/src/identity-tables.ts` (`IDENTITY_SET`). One more global table sits beside it, the pre-authentication counter `ingress_counter` (`GLOBAL_TABLE_NAMES_BEYOND_IDENTITY`), and the union is the RLS coverage test's exemption list, checked both ways by `packages/schema/test/rls.test.ts` ("the identity set"): every declared table with row-level security off and no policy in `pg_policies` is in the list, and every name in the list is such a table. The argument, stated precisely: the exemption is for **unscoped, key-based reads before authentication** — a session by its token, a user by id or email, a verification by identifier, a client by its `client_id` URL, a refresh token by its hash — none of which lists across principals; and among them the **consent's `referenceId`** is what puts a `workspace_id` on a credential, and the **membership read** (`member` by `(workspace_id, user_id)`, the one row that carries a `workspace_id` on purpose, `invitation` beside it) is what validates it: the resolver sets `SET LOCAL app.workspace_id` from the credential's claim and, in that same transaction and before any other statement, reads the member row — a missing or refused membership rolls the transaction back with no tenant row ever read. The worker role is revoked on the whole set (migration 0005; the refusal is a `[SEC3]` test).

**Better Auth's organisation model is mapped onto the platform's `workspace` table** (`schema.organization.modelName: "workspace"`; its `organizationId` fields read `workspaceId`), and `workspace` therefore leaves `withRLS()`: the pre-consent picker must read a workspace's name before any scope exists, and a second table duplicating id and name would carry an invariant no foreign key enforces. The workspace id rides on Better Auth's own `referenceId` on tokens and consents. Workspaces are **platform-provisioned** (grilling Q11): `provisionWorkspace` in `packages/core/src/workspaces/` is the one act — the row, its chunk partition through the one definer function, the first Admin, the config row, in one transaction — and Better Auth's own creation endpoint is closed to people (`allowUserToCreateOrganization: false`), its after-create hook wired to the same partition step for the day self-serve is flipped.

**The CIMD Node bug is now filed upstream**, so the 2026-08-30 amendment's "with **no upstream issue filed by anyone**" is stale: it is better-auth/better-auth#10810 (open), and fix PR better-auth/better-auth#10730 (open, against `next`) is the removal condition named in `apps/api/lifts/better-auth-cimd-node/THIRD_PARTY_NOTICES.md`. Ticket 83's report is moot. The three leave-triggers and trigger 3's first datum stand as written.

Two smaller records. **The 2026-08-27 amendment's "the access token carries `{workspace, user, role}`" is superseded**: the token's claim set is `{workspace, user}` — prototype 61 observed no `role` claim — and the role is read per call in the same transaction as the read it authorises (`withPrincipal`, `packages/core/src/store/postgres/`), as ADR 0018's 2026-08-31 amendment says; the resolver's refusal on `iat` before `credentials_revoked_at` is the revocation check both name, and `revokeCredentials` (`packages/core/src/workspaces/`) is the one act that writes the instant, ends the sessions and revokes the refresh tokens minted before it. And the surface is served CIMD-only (research 80 F2): dynamic client registration stays at Better Auth's default, off, so the *client (connected)* the glossary describes is a cached metadata document, not a registration. Everything else stands.

## Amendment — 2026-09-02, one session for the browser, the pages move to the SPA, the client list closes, `admin()` refused (T-022 grilling; research `docs/research/t-022-better-auth-admin-plugin.md`)

Four records. **One session across `app.` and `mcp.`**: the SPA signs in on `app.` (ADR 0006 amended; ADR 0022 amended to take `app.` out from behind Cloudflare Access, since a second email-OTP in front of Better Auth's is a defect, not defence), and the cookie is scoped to the apex through Better Auth's cross-subdomain cookie setting so the same session answers the OAuth flow on `mcp.`. **The sign-in and workspace-picker pages T-004 rendered from `apps/api/src/auth/pages.ts` are replaced by the SPA's screens** — `loginPage` and `postLogin.page` point at the SPA — and the consent page stays server-rendered on `mcp.`, because consent must never sit behind the product's own shell. Their T-004 tests move to the browser-to-policy suite.

**The CIMD allow-list closes to `claude.ai` for v0.1** (`isMetadataDocumentUrlAllowed`), and `offline_access` leaves the default scopes for any other host; both are the `[SEC3]` independent pass's owner decisions, taken, and land with T-005. A second *connected client* is not planned; the second *tenant* is the platform's own dogfood workspace, provisioned by T-005's bootstrap.

**Better Auth's `admin()` plugin is not adopted as shipped.** Three of its endpoints contradict this ADR and ADR 0020: `/admin/list-users` lists every user with no tenant predicate, which is exactly the cross-principal read the identity set's RLS exemption is argued not to contain; `/admin/remove-user` hard-deletes through `member`, destroying ~~the member id ADR 0020 pseudonymises to and never deletes~~ the person id every ledger row names and nothing ever deletes (2026-09-05 amendment below); `banUser` is weaker than `revokeCredentials`, since the ban is checked only at session creation and never by the Principal resolver or on a live token. A platform console is wanted and is its own task (T-028): it adopts the plugin with those paths in `disabledPaths`, gives the operator a real `user` row rather than the platform principal, and amends this ADR for the cross-workspace list it does keep. Workspace Admins manage people through the organisation plugin alone (T-027). Everything else stands.

## Amendment — 2026-09-03 (T-045), one origin, one session, and consent's reason replaced

The 2026-09-02 amendment's "one session across `app.` and `mcp.`" and its cookie "scoped to the apex through Better Auth's cross-subdomain cookie setting" are struck, and so is the Consequences line "`mcp.` stays a separate hostname with no Access policy": there is **one origin**, `app.<apex>`, carrying the SPA, sign-in, the picker, consent, `/oauth2/*`, discovery, `/jwks` and `/mcp`, and the session cookie is Better Auth's own host-only `__Secure-` cookie, sent to the product's host and nowhere else (ADR 0034). Consent stays server-rendered outside the SPA's shell, but the reason "because consent must never sit behind the product's own shell" no longer rests on the other host: it is acceptable on the product's own origin because the **closed client list plus PKCE** means a code obtained by any script in the shell lands only at Claude's own redirect, bound to a verifier no script holds, with a navigation-only fence on the consent POST beside it. The 2026-09-02 amendment's "land with T-005" for the CIMD allow-list is struck: the list is the precondition of consent on the one origin, so it lands with T-045 (`isMetadataDocumentUrlAllowed`, held by `oauth-flow.test.ts`); `offline_access` for any other host is moot while the list names one. Everything else stands.

## Amendment — 2026-09-04, what the identity seam is for, when a token's workspace is fixed, and what the operator is (T-044, the 2026-09-03 session audit's seam review)

Three records, none of them a change of decision.

**The seam is not held open for a provider swap.** The 2026-08-30 amendment made `requireBearerAuth` a rule of the constitution (since retired to this ADR) and priced the Keycloak fallback at two to three weeks; read together those can be taken to mean the seam exists so the provider can be swapped. It does not, and **no swap to Keycloak is planned** — Keycloak stays the runner-up on paper, nothing more. The seam is kept for two reasons that hold whatever the identity provider is. First, `packages/core` is independent of it and testable without it: a Principal is a plain value, so core's suites construct one rather than mint a token, and no Better Auth type crosses the line. Second, **two of the four kinds of caller never hold a Better Auth session at all** — the worker, which reaches core through the control plane under the platform principal, and the platform's own scheduled routines (provisioning, erasure, the reconciler), which have no person behind them (`PlatformPrincipal`, `packages/core/src/kernel/principal.ts`). A seam that only a swap justified would be worth removing; this one is load-bearing on an ordinary day.

**A token's workspace is fixed at consent time.** The workspace is not re-read from the session on each call and cannot be changed by a later picker: it is written onto the credential as Better Auth's `referenceId` when the person consents, and every call the token makes is scoped to that workspace for the life of the token. A person in two workspaces who wants the other one consents again and gets a second token; there is no in-flight switch.

**T-028's operator is a new principal kind, not a threaded `admin()` role.** The 2026-09-02 amendment refused Better Auth's `admin()` plugin as shipped and left the console to T-028. The shape that task takes is a **third principal kind** beside `user` and `platform`, resolved from its own credential and audited under its own identity — not an extra role value threaded through `UserPrincipal`, which would put a cross-workspace caller inside the type every tenant-scoped function takes and make the tenant guarantee (ADR 0032) depend on reading a role field correctly at every call site. Everything else stands.

## Amendment — 2026-09-05, one person id, revocation in two scopes, the minter behind Better Auth (T-073, ADR 0035)

Three records. **The id the 2026-09-02 amendment protected is the person id.** That amendment refused `/admin/remove-user` for destroying "the member id ADR 0020 pseudonymises to"; the id a user delete would destroy is the **person id** — the `user` row's id, the platform's one id for a person, `userId` on every Principal and `human:<person id>` on every record the platform keeps (ADR 0035) — and the member row's key is a key nothing of ours references, joins on or shows. The refusal stands with its reason corrected, and Better Auth's delete-user endpoint is proven refused by a `[SEC3]` test (T-077). **Revocation has two scopes.** The 2026-09-01 amendment's `revokeCredentials` — "the one act that writes the instant, ends the sessions and revokes the refresh tokens minted before it" — is the *everywhere* scope: the operator's act (T-028; the platform principal's until then), never a workspace Admin's. A workspace Admin revokes *in this workspace*: an instant on the membership row, read by the resolver in the same membership query as the person-level instant and refused with the same *credentials revoked* word, ending only the tokens whose consented workspace is that one (the column, the refusal and the token predicate are T-075's; the act with its ledger row is T-027's). No workspace learns whether a person belongs to another, and a fresh sign-in mints anew on both scopes. **Better Auth mints through the platform's minter.** Every id in the identity set — `user`, `session`, `member`, `invitation` — comes from the kernel's one ULID function, handed to the library through its custom id-generation option (T-074); session tokens, authorisation codes, client secrets and `jti` values stay the library's own random strings. The identity-set exemption's reason for `member` gains the picker's cross-workspace read by person id, which moves into the workspaces slice (T-077). Everything else stands.

## Amendment — 2026-09-05 (later, T-078), the identity seam is this ADR's, not a rule's

The 2026-08-30 amendment made the seam a rule of the constitution — `DESIGN5` until this date; the tag is retired and appears nowhere in the tree. Design principles are not coding rules (owner, 5 September 2026), so the seam is recorded here as this ADR's own decision, in the words the rule used. **No Better Auth type crosses into `packages/core`**: a transport verifies a bearer and builds a `Principal`, and nothing behind that seam knows which library minted the token. **No `better-auth` or `@better-auth/*` import appears outside an auth module**, of which there are two, one per side of the wire, and no third — `apps/api/src/auth/` on the server and `apps/web/src/features/auth/` in the browser (T-037); the browser has to know Better Auth's client because the product signs a person in by posting to its endpoints, and what the seam buys there is what it buys on the server: one directory owns the library, everything above it speaks screens, workspaces and roles rather than endpoints, and a reviewer can read the whole of it in a sitting. Both fences are lint-enforced in `.oxlintrc.json` and each has a rule test (`apps/api/tests/lint-rules.test.ts`, `apps/web/test/lint-rules.test.ts`); the lint messages, the tests and Cubic's review rule now cite this ADR. The seam's reason is the 2026-09-04 amendment's, unchanged. Where an earlier record cites the retired tag — ADRs 0028, 0030 and 0033, the two amendments above and the T-046 spec — the citation now reads as words pointing here; no conclusion changes.
