# Kinds emerge from the concepts — there is no vocabulary file; a link, its sentence and the two kinds are the relation

A concept's `type` is the short string its producer chose, folded at write for case and plural only (*client*, *Clients* → *Client*). The **type vocabulary** is the set of kinds in use, **derived** from the concept index with counts per kind and per domain — never a file in the bundle, never a table an Admin curates, never checked closed-world. A new kind arrives with the concepts that carry it: the suggestion set's summary names it ("introduces a new kind: *Course* (12)"), and accepting the concepts accepts the kind — the one gate the platform has (ADR 0012) is the only gate. An Admin governs kinds from a **Kinds list** on the Knowledge screen by renaming or merging one, which is one bulk commit that rewrites every affected `type` and re-keys `concept_identity` in the same transaction (`type` is inside the merge key, so kind drift is identity drift). Where a company wants to say what a kind *is*, the definition is a `Term` concept in a glossary domain — knowledge by the minting rule (ADR 0011), read by the extraction and judging prompts; the starter kinds a new workspace is offered live in the platform bundle's extraction guidance as neo4j-okf keeps them ("prefer these — a better short kind is fine"), not in a registry. Review cadence is a workspace setting keyed by the kind string (ADR 0019).

**A relation is the link.** Every markdown link between concepts is a `LINKS_TO` edge on the map carrying the two endpoint kinds, the section it sits in and the sentence around it; the only named edges are `SUPERSEDES` (the successor's `sources[]` entry or *Supersedes* line, ticket 47), `CITES` (a composition's include) and `IS_CONCEPT` (a source entity resolved to a concept, for every kind). No relations list, no predicate matcher, no "links carrying no relation" count; an agent that walks from a certification to the products linked from it reads the sentence — which is where OKF puts the kind of a link. **Tags stay free strings** as the spec ships them; the chips and a guide's tier axis derive from links to concepts of kind *Tier*, *Framework* and *Sector* (and from `DISTINCT tags`); the app writes nothing into `tags`; ticket 16's rule for what a tag names (a context or a tier, never a guide or an audience) lives in the extraction guidance, not in a check. **An alias is knowledge**: when an Admin answers "Are these the same thing?" for two concept names, the confirmed alias lands as an *Also known as* line in the concept body through an edit suggestion, and `concept_identity` derives its merge-key names from that line and the `title`; a *No* is remembered so the matcher never asks twice. Source-entity merges and `IS_CONCEPT` stay rules in records (ADRs 0014, 0021/0023). Extraction templates name whatever kinds the document kind evidences; the concept / source-entity split stands (ADR 0011 amendment) with no design-time validator — a source-entity type that shares a name with a concept kind uses the same word.

We decided this because OKF's first non-goal is a fixed taxonomy of concept types and its one required key is "not registered centrally" — a producer mints a concept precisely so it need not fit anywhere yet, and consumers must tolerate an unknown kind. ADR 0001 built a schema beside a format chosen for not having one; its atomicity argument (a vocabulary file and the `type` values it governs must change in one commit) disappears when there is no second file — a rename *is* one commit across the concepts. Three reviewers reached the same cuts from three seats (research 76: an OKF purist, a staff engineer, an SMB Admin persona); Liam's driver is simplicity for companies of one to five hundred people, and Dr Jerry Smith's rule — categories emerge from evidence, the system proposes with evidence attached, a person approves — is met by the suggestion gate the platform already has.

## Considered options

- **A per-tenant vocabulary file, authoritative in the bundle, closed-world checked** (ADR 0001; round 1 of ticket 50 as YAML with `types` · `relations` · `contexts`) — a list that restates what the concept files and `index.md` already say; an Admin tending a registry; a "provisional" state on every unknown kind; a plan diff; open-ontologies in the deploy unit. Cut by all three reviewers.
- **An optional `types:`-only file for definitions and read-time aliases** — the one thing not derivable is a definition, but a definition is knowledge and a `Term` concept holds it without a second file format; read-time aliases for an *imported* bundle join the out-of-scope importing line.
- **Typed relations derived from a relations list with sentence matching** — an edge label on the map and nothing on the answer path (ADR 0016's walk filters by the target's kind and the drafting model reads the sentence anyway); silently wrong on shared kind pairs; a registry someone maintains. A predicate label can be derived from edge sentences by an enrichment job later, still in the graph, with nothing re-keyed.
- **Closed-world tags with an app-written tier tag** — a rule with no act, and derived content written into the file beyond `iri` and `locator` (`[OKF2]`).
- **A concept alias as a `concept_identity` row only** — cheaper by one commit; the alias leaves with nothing on export.

## Consequences

- **ADR 0001 is superseded**; open-ontologies, semantica and Hyper-Extract-as-runtime are not dependencies of anything. The ontology tooling research (30) stays a reference for the fog beyond v0.1 (lock, drift, alignment, reasoning), if a client ever asks.
- **Records**: `concept_identity` keys derive from `title` and the *Also known as* line; an alias decline is remembered (a row keyed by the pair, an audit event); no `vocabulary_term`, no plan record, no vocabulary suggestion kind. The Kinds list is a query over the concept index.
- **Graph** (ADR 0023 amended): `LINKS_TO {from_kind, to_kind, section, sentence}` between nodes labelled by kind; `SUPERSEDES`, `CITES`, `IS_CONCEPT` the only named edges; no `RELATES_TO` matrix.
- **Screens** (ADR 0017): Knowledge gains a Kinds list (kind · count · per domain; rename · merge); no seventh screen; the words *plan diff*, *LINKS_TO*, *provisional* never reach a screen — Sam's three trust rules join the UX bar (45): never ask the same question twice; nothing renamed without a sentence and a count first; no screen word the Admin does not own.
- **Writer rules** (from tickets 19 and 37, confirmed): an include's section hash covers the section's subtree with the heading line excluded, normalised as ADR 0014's amendment normalises a body; a body with two headings that fold to the same text is refused at commit ("two sections named X"), an imported bundle's duplicates flagged not refused; an `Answer` lands in the domain of the concept it chiefly cites (`products/<x>/answers/`, else `company/answers/`), shown for override before minting, so its owner is the product's.
- **Signals** (ADR 0025): *kinds with two or fewer concepts* per workspace — the tail that shows drift; nothing else.
- **`CONTEXT.md`**: *type vocabulary* (derived), *company language* (the kinds, names and links the concepts reveal — never a file), *kind* (the reader's word for `type`), *relation* (the link with its sentence), *Kinds list*, *Also known as*; *vocabulary plan* retired. `docs/okf-v02.md` rows for typed relations, equivalence and taxonomy point here.
- **What goes wrong at 300 people, honestly** (research 76): kind drift — a long tail of one- and two-concept kinds and two departments using *Policy* differently — noticed from the Kinds list and the tail signal, fixed by a merge commit; predicate-less edges that a guide expectation cannot select by relation, met by an enrichment over edge sentences when it is wanted. Each is addressed when it appears; none needs a day-one schema.
- Amends ADRs 0010 (its rejection read strictly: no relation schema in the bundle either), 0013, 0014, 0019, 0023 as recorded on each; `docs/vision.md`'s "Admins (sources, vocabulary, …)" becomes "kinds".

## Amendment — 2026-08-30, five named edges — three about concepts, two about the platform's own bookkeeping (ticket 79, the pre-build gate; applied by T-001)

"The only named edges are `SUPERSEDES`, `CITES` and `IS_CONCEPT`" reads against ADR 0019, which writes `DERIVED_FROM` for trust lineage, and ADRs 0021/0023, which write `SAME_AS` for a confirmed entity merge. It is not a contradiction once the rule is stated properly, and stating it is this amendment's job.

**This ADR's rule is about relations *between concepts*.** A relation between two concepts comes from a link in a concept's body and is **never named**: it is a `LINKS_TO` edge carrying the two endpoint kinds, the section and the sentence, and an agent that wants the predicate reads the sentence. No relations list, no predicate matcher, no `RELATES_TO` matrix. That is the decision and it is untouched.

**`DERIVED_FROM` and `SAME_AS` are platform-derived edges the graph writes about its own bookkeeping.** They are not relations the company asserts and they derive from no link: `DERIVED_FROM` carries trust lineage (ADR 0019), and `SAME_AS` hangs each contribution off a canonical entity under its own binding, class and audience (ADR 0023). By the minting rule (ADR 0011) they are **records in graph shape** — the platform keeps them because it runs a use case — which is precisely why they may be named while a relation may not.

**So the map carries five named edges**: `SUPERSEDES`, `CITES` and `IS_CONCEPT` about concepts; `DERIVED_FROM` and `SAME_AS` about the platform's bookkeeping. Everything else between concepts is `LINKS_TO`. *(The alternative, recorded: making the two bookkeeping edges properties instead would hold the count at three, at the cost of a supersession or lineage walk becoming a property scan rather than an edge traversal. Three was not worth that.)*

**And the label clause in the Graph consequence is withdrawn.** It reads "`LINKS_TO {from_kind, to_kind, section, sentence}` **between nodes labelled by kind**"; ADR 0023's *graph is application data* amendment withdrew that half. There is **one `Concept` label and `kind` is an indexed property**, because a label is a registry — a schema object created, named, indexed and granted in the catalogue before any row can wear it — and this ADR's whole decision is that a kind is registered nowhere. Labels-by-kind would have rebuilt the vocabulary file ADR 0001 died for, inside the Postgres catalogue, where a rename that this ADR makes *one bulk commit* would become a schema migration. This ADR had already reached that conclusion without noticing: it made `from_kind` and `to_kind` edge **properties**. The rest of the Graph consequence — the three concept edges, no `RELATES_TO` matrix — stands.
