### The rulings — settled, not open

Build to these. Each was asked and answered during the loop; re-deciding one is re-opening a closed question.

1. **The publish gate reads the latest `index` job by subject, never the `state` column.** Under T-128's grants the worker holds `SELECT` alone on `source_binding`, so the app writes the state word: **landed** by the bind, **published** by the publish. ***Indexing* and *indexed* are never stored** — they are the job's status, rendered between the two by a list read that is T-135's. The column's CHECK admits four words; this ticket writes two.
2. **`done` alone lets a publish through.** Queued, claimed, `failed` and `poisoned` all refuse **`not-indexed`**. **Do not reach for `JOB_IS_OVER`** — it admits `failed` and `poisoned`, which this gate does not. A publish says somebody reviewed what the run found; a failed run found nothing to review, and the road out is a reprocess.
3. **Ruling 1 contradicted ADR 0013's amendment of 11/09/2026, so this ticket corrected it** — the superseded sentence struck with `~~…~~` inside that amendment (the index's own convention for a superseded sentence, never a deletion), a dated corrected paragraph under it, and the `docs/adr/README.md` row in the **same commit** (wave B).
4. **Acceptance line 4 is held with the platform's one predicate, in the suite.** T-133's `passageAt` is not an edge of this ticket, so `readableClause` and `readableParameters` from `packages/core/src/access/index.ts` are rendered against `index.chunk` in the test — the same predicate T-133's reads will render — with the passage written down as a literal. This is a deliberate reading of the line, not an omission.
5. **The published act's detail is scalar-only and derived.** `DetailValue` is `string | number | boolean` and `DETAIL_KINDS` is `id · id? · role · flag · iri · gitSha · contentHash · count · sensitivity · audience` — **a nested object is not available**. So the totals by category are **one `count` per category, the shape derived from `REDACTION_CATEGORIES`**, the DPIA hash is `contentHash`, and the three confirmations are three `flag`s. No name, no filename, no free string in any detail.
6. **Wave B's two schema constants are kept.** `BINDING_PUBLISHED_STATE` and `JOB_DONE_STATUS` are declaration-only: both words were already members of sets the database holds, so neither adds a column, a CHECK, an index, a default or an enum member. Evidence, checked by reading the diff: fifteen added lines across the two files, every one a comment or a `const` export outside the `withRLS(...)` call, and `git diff --name-only s1..HEAD -- packages/schema/migrations contracts` is **empty**. They exist because the repo's habit is a constant beside its closed set, and `JOB_DONE_STATUS` keeps *this run succeeded* apart from *this run is over*, which is the whole of ruling 2.
7. **`reprocessBinding` writes no ledger row of its own** — the acts that call it record. See *For the verifier*.

**This ticket makes no migration and no contract change.** Four iterations have held that, the rebase included. If iteration 5 finds one, stop and ask.

### For the verifier — one reading to raise before it is discovered

**`reprocessBinding` writes no ledger row of its own.** The one-transaction rule says every Admin act writes its audit event in the same transaction as the rows it describes, and this act is Admin-gated and deletes rows — so the question is fair and should be asked.

The reading the loop took, and why: `reprocessBinding` is **half of an act, never a whole one**. Its two callers are S0's erasure routine (step 7) and the rule-change edit, and **each records its own act** — the deletion and the enqueue are steps inside something already on the ledger, not a thing an Admin did on its own. A ledger row here would be a second row for one act, which the one-transaction rule forbids in the same breath: *one row per act and target; a bulk act is N rows sharing one batch id, never one row hiding N.*

If the verifier disagrees, the fix is small — declare `sources.binding.reprocessed` and record it bare — but it should be a decision taken openly rather than a row added quietly, because it changes what the ledger claims an Admin did.
