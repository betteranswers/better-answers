# T-022 — The first screen: shell, sign-in and the routes surface

*Spec written 2 September 2026 from the T-022 grilling (ADR 0006, 0009 and 0022 amendments dated 2026-09-02; research `docs/research/t-022-better-auth-admin-plugin.md`; the handoff of the same day). Source of truth for scope is the T-022 ticket body plus those amendments. Decisions recorded here are taken; do not re-open them.*

## Problem Statement

Everything built so far is reachable only by a test or by a Claude host over OAuth. A person cannot open Better Answers in a browser, sign in, and see anything their workspace holds. The single-page app is three files with a heading; the three pages a person passes through today (email code, workspace picker, consent) are plain server-rendered forms that exist for the OAuth flow, not for the product. The planning is extensive and none of it is visible.

The owner's directive is that something live to build against "will bring much of the planning to life". The first screen has to prove the whole stack, browser to row-level policy, on a table that already exists and is genuinely useful on day one: the workspace's LLM routes, where the hosted Mistral embedding route becomes visible and is shown as fixed.

## Solution

A person opens `app.`, signs in with an emailed code, lands in a workspace-scoped shell, and sees the **System** screen's routes list: one row per purpose (extraction, enrichment, answering, judging, embedding) with provider and model, the embedding route marked as fixed. A person in several workspaces picks one first. A person in none sees a refused screen and a sign-out. A member of one workspace cannot see another's routes, and one end-to-end test proves it through a real browser, the real server and a real Postgres.

Under the screen: the tRPC transport is pulled forward from its B9 slot; a first `packages/core` capability slice for routes; the SPA shell on TanStack Router and TanStack Query with the design system's tokens carried into Tailwind v4; better-auth-ui's screens under a `localization` that says *workspace*; the sign-in and picker pages moved into the SPA; the layering lint the ticket promised. The design system package shrinks to what the app imports.

## User Stories

### Signing in

1. As a workspace member, I want to open `app.` and sign in with a six-digit code sent to my work email, so that I need no password and no second sign-in in front of the first.
2. As a workspace member, I want the sign-in screen to tell me plainly when a code was sent, when it did not work, and when I have asked for too many, so that I know what to do next without guessing.
3. As a member of exactly one workspace, I want to land in it straight after the code, so that I never see a picker with one choice.
4. As a member of several workspaces, I want to pick one before I see any screen, so that everything I then see is scoped to that workspace.
5. As a signed-in person who belongs to no workspace, I want a screen that says so and offers sign-out, so that I know to ask an Admin rather than hunting for a button that does not exist.
6. As a signed-in person, I want to sign out from the shell, so that a shared machine does not keep my session.
7. As a person whose credentials an Admin has revoked, I want my existing browser session refused on the next request, so that revocation means what it says.
8. As a person whose session has ended, I want to be sent to sign-in and returned to where I was afterwards, so that an expired session costs me one step.

### The shell

9. As a workspace member, I want the shell to name the workspace I am in, so that I never act in the wrong one.
10. As a workspace member, I want the shell to show my name, my role and a sign-out control, so that I can see who the platform thinks I am.
11. As a workspace member, I want the shell to be Control Centre's frame with its six screens named, with the five unbuilt ones saying so rather than pretending, so that the product's shape is visible from day one.
12. As a workspace member, I want the shell to use the words in the glossary (*workspace*, never *organisation*; *map*, never *graph*), so that the interface and the documentation agree.
13. As a keyboard user, I want every control in the shell reachable and operable by keyboard in DOM order with a visible focus ring, so that I can use the product without a pointer.
14. As a screen-reader user, I want landmarks, labelled controls and announced outcomes, so that sign-in, picking and the routes list work with assistive technology.

### The routes screen

15. As a workspace member, I want to see my workspace's routes, one per purpose, with provider and model, so that I know which model answers which job.
16. As a workspace member, I want the embedding route shown as fixed, with its dimension count and a line saying why it never changes once vectors exist, so that nobody expects to edit it.
17. As a workspace member, I want the purposes with no route yet shown as absent rather than omitted, so that I can see what is unconfigured.
18. As a workspace member, I want the routes list to render within the latency budget, so that the first screen sets the standard the constitution demands.
19. As a workspace member, I want the routes list to be read-only in this ticket, with no editing control, so that a later ticket adds editing with its own rules rather than this one shipping a half-gated write.
20. As a member of workspace A, I want workspace B's routes to be invisible to me even if I hold a valid session, so that tenancy holds at the policy, not the screen.

### The OAuth flow through the product

21. As a person connecting Claude to Better Answers, I want the connector's sign-in to be the product's own sign-in on `app.`, so that I pass one sign-in, not two.
22. As a person connecting Claude, I want the workspace pick to be the product's picker, so that the connector and the product agree on where I am.
23. As a person connecting Claude, I want the consent page to stay outside the product's shell, so that a decision to grant access is never dressed as an ordinary screen.
24. As a Claude host, I want the OAuth flow to resume after sign-in and pick exactly as before, so that the conformance test still passes with the pages moved.

### Building and reviewing

25. As a builder, I want one tRPC client instance typed by the router, so that a procedure's input and output types reach the screen without a generated file.
26. As a builder, I want the layering lint (app → features → shared, no cross-feature imports) to fire on the wrong import and stay silent on the right one, so that the structure is enforced rather than remembered.
27. As a builder, I want the design system's tokens available as Tailwind theme values, so that no screen invents a colour, a size or a radius.
28. As a builder, I want better-auth-ui's screens, Kibo UI and AI Elements installed through the shadcn registry at pinned versions, so that the interface takes their behaviour and keeps our meaning.
29. As a builder, I want a Playwright suite that starts the real server over a real Postgres and drives a real browser, so that the acceptance test crosses every layer.
30. As a builder, I want a local loop that runs the same server with captured emails so that I can sign in from a browser without an email provider.
31. As a reviewer, I want Cubic to know the Principal-first rule and the seam rule before this PR opens, so that the first product PR is reviewed against the constitution.
32. As the owner, I want the UI-kit choice recorded as an ADR in this PR, so that a hard-to-reverse decision has its reasons written down.

## Implementation Decisions

### Sequence and scope

- **tRPC is pulled forward from B9.** The server factory's docblock reserves that slot; this ticket takes it. The router, its context and the Hono mount arrive here, with one procedure. B9 keeps the rest of its scope.
- **Build order:** the T-012 remainder first (Cubic proven against the constitution), then T-022, then T-005 (deploy unit, email transport), then T-027 (People), then T-029 (embedding immutability in the database). The T-012 remainder is the first ticket cut from this spec; its outstanding items are the ones in T-012's progress note of 2026-09-02.
- **No worker-pipeline dependency enters this ticket.** A screen that needs indexed content is a later ticket.

### Hostnames and origin (ADR 0006 and 0022, amended 2026-09-02)

- The api serves the single-page app's static build on the `app.` hostname. The SPA and the api are one origin; the tRPC endpoint and Better Auth's handler are reached on that origin.
- One Hono process answers both `app.` and `mcp.`. The `app.` origin joins Better Auth's trusted origins so a browser POST from the product passes the CSRF check. The OAuth endpoints, the protected-resource metadata and the discovery documents stay what they are on `mcp.`.
- The session cookie is scoped to the apex through Better Auth's cross-subdomain cookie setting, so the session made on `app.` answers the OAuth flow on `mcp.`.
- `app.` is open at the edge. Cloudflare Access is struck from in front of it; the app's per-IP counters and Better Auth's limiter are the abuse controls. This is already in the deploy tree's decision record; the compose and tunnel changes land with T-005.
- How Better Auth behaves when its base URL is the `mcp.` origin and requests arrive on `app.` (cookie domain, redirect targets, the `Origin` it compares against) is verified against the installed version's source before the wiring is written. Any surprise is a research note beside the existing one, not a guess.

### Sign-in, picker and the refused screen move into the SPA (ADR 0009, amended 2026-09-02)

- The three server-rendered pages T-004 shipped are reduced to one: **consent stays server-rendered on `mcp.`**, because consent must never sit behind the product's own shell. The sign-in and workspace-picker pages are deleted; Better Auth's `loginPage` and `postLogin.page` point at the SPA's routes.
- The SPA's sign-in is better-auth-ui's email-code screen under a `localization` that says *workspace* wherever the library says *organization*. The picker is the library's organisation switcher or a screen built on its headless hooks, whichever the pre-build research verifies works with the platform's `workspace` model name and field mapping.
- After a pick that began as an OAuth flow, the SPA completes the resume the way the T-004 page did, through Better Auth's own continue endpoint with the carried signed query. A pick that began in the product simply lands in the shell.
- **A signed-in person with no membership sees a refused screen and a sign-out.** There is no create-workspace control anywhere in the product (T-004 judgement call 1; workspaces are platform-provisioned).
- The T-004 tests for the deleted pages move to the browser-to-policy suite; the consent tests stay where they are.

### Session to Principal inside tRPC

- The tRPC context carries the Postgres door, the auth instance and the request headers. It does **not** carry a Principal: the Principal exists only inside the transaction that resolved it, and nothing caches one beyond a request.
- A workspace procedure base reads the cookie session into Claims the same way the existing `/me` route does, then runs the procedure's work inside the resolver, in the same transaction as the read it authorises. The `/me` route is the template and stays as the non-tRPC probe.
- Refusals map to tRPC errors: no session or no active workspace is `UNAUTHORIZED`; a resolver refusal (not a member, credentials revoked, role disagrees, role unknown, malformed claims) is `UNAUTHORIZED` with the refusal name as the message, never a default role. No procedure takes a workspace argument.
- The router is mounted with `@hono/trpc-server` under one path on the same origin. No transformer is configured unless a Date crosses the wire; the routes table has none.

### The routes slice and the one procedure

- A **routes** capability in the `llm` slice of `packages/core`, reached through that slice's export: list the workspace's routes as the Principal, one row per purpose, ordered by the purpose enum, with the embedding route's dimension count. The read runs under the Principal's transaction so RLS is the guarantee and the statement says the workspace anyway.
- The slice returns a domain shape (purpose, provider, model, dimensions, and whether the route is fixed), not the table row. *Fixed* is true for the embedding route; the database refusing to change it is T-029's.
- One query procedure, `routes.list`, calls the slice. No mutation ships in this ticket.
- Any workspace member at any of the three roles may read the list. Control Centre's Admin gating arrives with the first screen that acts; this list is read-only and nothing else exists yet.

### The screen

- The routes list is the **System** screen's first card. The other five screens and the rest of System exist in the navigation as named, unbuilt destinations that say so in words.
- Rendering follows the design system's register and the constitution's disclosure rule: the purpose, provider and model first; the dimension count and the fixed-route line on the embedding row; no action, because there is none. Trust and state are words, never colour alone; sentence case; British spelling; no emoji.
- Empty purposes are rows that say no route is set, so the list always has five rows.
- Every screen in this ticket carries the WCAG 2.2 AA line and is checked with a keyboard and a screen reader.

### UI kit (recorded as a new ADR in this PR)

- **Tailwind v4** through the design-system bridge: the design system's tokens become Tailwind theme values in one bridge stylesheet the app imports. No locally invented styles.
- **shadcn primitives**, **Kibo UI** and **Vercel AI Elements** through the shadcn registry, plus **better-auth-ui via the shadcn registry** for the auth screens. Three registries, one rule: they own behaviour (keyboard, focus, ARIA, streaming); the platform owns meaning (the trust words, the citation unit, the register, the registration marks).
- **Versions are pinned from the source on the day**, per the constitution's dependency rule. better-auth-ui releases daily; the pin read at 2 September 2026 was 1.7.18, and the builder re-reads it.
- better-auth-ui's provider needs the router's `navigate`, a `Link` wrapper mapping `href` to `to`, a `QueryClientProvider` above it, and the `localization` override. Its TanStack Start integration is the model for TanStack Router in a Vite SPA.
- The design system's icon choice (Phosphor), font (Geist, already self-hosted) and textures stand as the design system's readme records them.

### Router, query and the one type that crosses

- **TanStack Router** for routes and **TanStack Query** for server state. The tRPC client is built on the TanStack Query integration.
- **`AppRouter` is imported as a type in exactly one file**, the tRPC client instance, following bulletproof-react's api-layer pattern (a single pre-configured client instance; request declarations colocated per feature). A per-file lint override allows the `import type` and nothing else from the api; runtime coupling stays zero. This is ADR 0006's one exception.
- Request declarations live in the feature that owns them (a `routes` feature holds the list query options); the app layer composes features; shared holds the client, the design-system bridge and the primitives.

### Layering and lint (the bulletproof-react substance the ticket promised)

- The layering zones are expressed as per-glob `no-restricted-imports` overrides, because oxlint 1.80 has no `import/no-restricted-paths`: no feature imports another feature; the direction is app → features → shared and never back; shared imports nothing above it.
- `unicorn/filename-case` in kebab-case over the SPA.
- The `import type`-only override for the client-instance file.
- Testing-library and jest-dom rules are enabled only if this ticket writes component tests; the acceptance test is a browser test and may be the only test the SPA gains.
- Every rule lands with a functional test that runs it against a throwaway tree, asserting where it fires and where it stays silent, in the shape the existing lint-rule tests use.

### The design system package shrinks

- `packages/design-system` keeps tokens, the stylesheet and the Tailwind bridge, and gains a `package.json` so the SPA imports it as a workspace package with fonts wired.
- The `.jsx` components and the `ui_kits` click-through are deleted in this PR: the shadcn-registry components replace them, and a second component set that nothing imports is drift. The guidelines and readme stay; the readme was updated by the owner on 2 September 2026.

### Cubic before the PR (the T-012 remainder)

- `custom_rules` gains the Principal-first rule and the seam rule; one of the five generic agents is dropped or folded into `custom_instructions` to stay under the five-agent cap. Which one is the maintainer's call and is recorded in T-012.
- `ignore.files` gains every `lifts/` path.
- Cubic reads its config from `main` only, so the T-012 remainder merges first and T-022's PR is the one that proves it. The review loop is the one in the code-review agent doc: `cubic review -b` before push, one commit per round, three rounds at most.

### Records

- A new ADR for the UI kit, with its line in the ADR index in the same commit.
- The server factory's docblock loses its "B9 the tRPC router" sentence.
- The constitution's functional-test rule gains an `apps/web` line (see Testing Decisions).
- No new glossary word. *Workspace*, *role*, *route*, *screen* and *client (connected)* are settled; Better Auth's *organization* never reaches a screen.

## Testing Decisions

**A good test crosses the seam a caller crosses and asserts what the system does for whom.** It never imports a slice's internals, never mocks our own code, builds its state through factories, and runs against a real Postgres.

### Seams, highest first

1. **Browser to policy** — the one seam the ticket's acceptance criterion names. A Playwright suite in the SPA workspace starts the real server (through the server factory, with the email sender captured and the CIMD transport in process) over a Testcontainers Postgres, serves the built SPA, and drives a real browser. It signs in with the captured code, picks or lands, and reads the routes list. This is where "a second workspace's routes are invisible" is proven: two workspaces provisioned through the harness's existing factory, one person a member of one, and the other's routes never on the page. The T-004 page tests that move here are the sign-in and picker flows and the OAuth resume through them.
2. **The api endpoint** — `server.request` against the tRPC path, through the existing test harness. Every procedure refusal is a test here: no session, no active workspace, not a member, revoked credentials, a role the member row disagrees with. The harness's two-workspace factory and `revokeCredentials` already exist for exactly these.
3. **The core export** — the `llm` slice's list function through its export, in the shape of the workspaces slice's tests: seeded routes for two workspaces, read as each workspace's Principal, the other's rows absent; the embedding row flagged fixed; five rows always.
4. **The lint rules** — the throwaway-tree pattern of the existing lint-rule and import-direction tests, one `describe` per rule, asserting where it fires and where it stays silent.

The e2e seam is the deliverable; the endpoint and export seams exist because a refusal is cheaper to enumerate at the endpoint than in a browser, and the constitution names both as functional-test surfaces.

### The constitution's functional-test rule gains a line

`[TEST1]` names the endpoint for `apps/api`, the job entry for `apps/worker` and the export for `packages/core`. It gains: for `apps/web`, the served build driven by a browser (Playwright), or a rendered component through Testing Library where a component's behaviour is the thing under test.

### Infrastructure

- Playwright's browsers are installed as a step in CI; the SPA's `check` runs the e2e suite after the build.
- `agent-browser` is the dev-loop tool for looking at the running app; it is not a test runner.
- The dev loop's email problem: the production entry point's email sender throws until T-005 wires Resend. The local loop runs the same in-process harness the e2e suite uses, printing captured codes from the harness (not from the app's logger, which the constitution forbids from holding a code).
- Mutation testing over the SPA stays on its weekly schedule; a browser test is excluded from Stryker's mutate set.

### Prior art

- The app harness (`TestApp` with `provision`, `addMember`, `revokeCredentials`, captured emails) and the OAuth-flow suite for browser-shaped flows.
- The workspaces and principal suites in `packages/core` for slice tests through the export.
- The lint-rule and import-direction suites for rule tests.
- The llm-routing contract suite for how routes are seeded from the fixture.

## Out of Scope

- **People** (T-027): members, roles, invitations, the accept page; the two invitation fences stay up.
- **The platform console** (T-028) and anything from Better Auth's `admin()` plugin.
- **The database refusing changes to the embedding route** (T-029); this ticket only renders it fixed.
- **Email transport, deploy, tunnel and compose changes** (T-005), including the `app.` edge change's enactment and the dogfood workspace.
- The other five Control Centre screens and the rest of System; the Account page and personal tokens.
- Editing a route, adding a route, spend or signals.
- Role-gating Control Centre; groups on the Principal.
- Any create-workspace control; self-serve stays one flag later.
- The OpenAPI mount, the MCP App, any worker or pipeline work.
- A dark theme beyond what the token alias flip already gives; a logo (none exists).
