# T-441 — The app's text says where you are and what to do next

## Problem Statement

The owner tested the new sign-in and People screens and found the text hard going. A review on 26/09/2026 measured every string a person can see, then walked the new-user and sign-in routes in a browser.

Sentence length is not the fault. The new-user path averages 8.0 words a sentence; documenso's onboarding averages 7.6. The fault is what the text says:

- **It explains the system instead of the next step.** The display-name hint reads "The one line the platform credits you by wherever it names you: on a check you make, as the author of a change, in a member list." That is the glossary's definition of *display name*, copied onto a screen.
- **Everyone lands on the wrong screen.** Every role's first screen is System → Routes and spend: 113 words about model routes and embedding vectors. An invited Editor reads 244 words before reaching it, and none of it is theirs to act on.
- **Every error leads with a code word.** "Refused: malformed. The reason needs a character other than a space."
- **"The platform" is a character.** 28 strings make it the subject: "The platform could not read what this screen sent."
- **Empty states fill every slot.** The Groups tab repeats its sentence under its own create form. The Requests tab offers "Invite a person by address" beside the toolbar's "Invite a person".
- **One dead end.** The consent page's session refusal says "Sign in again" and offers no link.

The cause is the one T-382 found for comments. Agents copy the house voice of the rules and the glossary into whatever they write. The design-system readme's §3 adds to it: its rules are written as shapes, so agents fill every slot. "Empty states are two lines and an action", "Consequence before the click" and "Errors … naming who can fix it" each map to a family of long strings. §3 never says the text is there to be acted on.

The browser suite makes the text expensive to change. Its specs assert about 350 sentences as literals. That breaks the suite's own rule, "Read the SPA's own constants rather than copying them". A test that pins wording tests the copy, not the behaviour, and fails on every rewrite.

## Solution

- **§3 gets a *Clarity* rule in place of *Length*.** A screen answers three questions, in order: where am I, what happened, what do I do next. It says those, then stops.
- **Each role lands where it can act.** An Admin lands on People → Members. An Editor or Viewer lands on Questions.
- **A refusal shows its sentence, never its word.** The word stays in the logs and on the wire.
- **An invitee gives their name on the invitation screen.** The separate display-name screen stays for everyone else.
- **The new-user and sign-in path is rewritten under the rule**, with the shared refusal and empty-state templates and the api's consent pages.
- **The specs assert behaviour.** A spec reads a sentence from the SPA's own word tables and asserts the state it belongs to. It never pins prose as a literal.

## User Stories

### A person signing in for the first time

1. As a new person, I want the sign-in screen to name the product as "Better Answers", so that I know where I am.
2. As a person who followed an invitation link, I want the sign-in screen to say I am signing in to join that workspace, so that I know I am in the right place.
3. As a person who pressed Connect in Claude, I want the sign-in screen to say I am signing in to connect Claude, so that the step makes sense.
4. As a person who typed a wrong code, I want a way to send a new code on the same screen, so that I can finish without starting again.
5. As a person who asked for too many codes, I want to be told how long to wait, so that I know when to try again.
6. As a new person, I want the name screen to say who sees my name, in one line, so that I can fill it in without reading about the platform.
7. As a person whose name was refused, I want to be told what to change, so that I can fix it at once.
8. As a signed-in person with no workspace, I want one clear way on, so that I am not choosing between two routes through the same Admin.
9. As a person asking to join, I want the field to ask for the workspace's short name in plain words, so that I don't need to know what a slug is.
10. As a person who has asked to join, I want to see "Request sent" and what happens next, so that I know to wait for an email.
11. As a person with no workspace, I want the text to be true, so that I am not told to sign in again when I don't need to.

### A person arriving by invitation

12. As an invitee without a name, I want to give it on the invitation screen, so that joining is one step, not two.
13. As an invitee, I want the invitation screen to name who invited me and what my role lets me do, so that I know what I am agreeing to.
14. As an invitee, I want the heading, body and button to say different things, so that I read each once.
15. As an invitee signed in at another address, I want to be told the invitation is for a different address, so that I know to switch.
16. As an invitee whose link no longer works, I want to be told so plainly and who can send a new one, so that I can ask them.

### After joining

17. As an Admin, I want to land on People → Members, so that my first screen is one I act on.
18. As an Editor or Viewer, I want to land on Questions, so that my first screen is about what I do.
19. As an Editor or Viewer, while Questions is not built, I want its screen to say in one line what I will do there and that I can ask through Claude now, so that I am not stranded.
20. As any member, I want each screen's lead line to say what the screen is for, so that I don't read a list of the nav beside it.
21. As an Admin opening an empty tab, I want one line saying what is missing, so that I can act without reading policy.
22. As an Admin, I want one button for each act, with one name wherever it appears, so that I don't wonder whether two buttons do different things.
23. As a keyboard user, I want the shortcuts button to be called "Keyboard shortcuts", so that I know what it opens.
24. As a person on a screen that failed to load, I want to be told that other screens still work and be offered my own home, so that I can carry on.
25. As a person at an address that doesn't exist, I want to be told so and offered my own home, so that I am not sent to a screen I can't use.

### Errors

26. As a person refused by any act, I want to read what went wrong and then what to do, so that I can fix it.
27. As a person refused, I don't want a code word in front of the sentence, so that the message reads as a sentence.
28. As a person whose save failed, I want to be told whether anything was saved, so that I know whether to try again.
29. As a person refused for my role, I want to be told who can do it, so that I know whom to ask.
30. As a person removed from a workspace, I want the picker to say I am no longer a member and to stop listing it, so that I don't keep trying.
31. As a returning person whose session ended, I want the sign-in screen to say so, so that I know why I am there.

### Connecting Claude

32. As a person connecting Claude, I want the consent page to say plainly where I will go next, so that I can decide whether to trust it.
33. As a person whose session ended before Connect, I want a link to sign in again that brings me back to the connection, so that I am not stranded.
34. As a person refused on a consent page, I want a next step on every such page, so that each page ends with something to do.

### The people who build the product

35. As an agent writing a screen, I want §3 to say the text is there to be acted on, so that I write the next step and stop.
36. As an agent, I want §3 to say a glossary definition is never a screen's sentence, so that I don't copy the glossary onto screens.
37. As an agent, I want the empty-state rule to say one line, with an action only where the screen has no other way to take it, so that I don't add a second button.
38. As an agent writing a spec, I want to read a screen's sentences from the SPA's word tables, so that a wording change doesn't break the spec.
39. As the owner, I want the specs to test behaviour, so that rewording a screen during development costs nothing in the suite.
40. As an operator reading logs, I want the refusal word still logged, so that I can find a refusal a person reports.
41. As an agent calling an act over MCP, I want the word as before, so that I can act on its class.

## Implementation Decisions

### The rule

- **§3's *Length* paragraph is replaced by *Clarity*.** Its text is the review's draft, adopted as written:
  - A screen answers three questions, in order: where am I, what happened, what do I do next. Say those, then stop.
  - Say what to do, not how the system works. Explain a rule only when the reader can't act without it.
  - Use the reader's words. A glossary word goes on a screen only when the reader needs that exact word to act, and it's explained where they first meet it.
  - Give one next action, its label naming the effect: "Join Acme", not "Continue".
  - Don't repeat the heading in the body, or the body in the button.
  - An empty state says what is missing, in one line. Add an action only where the screen has no other way to take it.
  - A consequence line states the one thing the reader would regret not knowing: that it can't be undone, or who will see it. Record-keeping isn't a consequence for the reader.
  - An error says what went wrong, then what to do. Name who can fix it only when the reader can't. A code word never leads.
  - "The platform" isn't a character. Write "Nothing was saved", not "The platform did not answer".
  - Turn stacked conditions into two short sentences.
- **§3's *Person* paragraph drops "the platform in the third".** The audit log's actor column still names the platform's own acts "the platform". That column names an actor; it doesn't address the reader.
- **"The glossary is binding" becomes "Never contradict the glossary."** A screen uses the glossary's word for a thing. The glossary's definition is never a screen's sentence.
- **The trust words stay a closed set**, word for word.
- The design skill reads the readme and holds no copy of §3, so the readme is the one edit.

### Where each role lands

- **A surface's home is declared per role**, not once. Control Centre's homes:
  - Admin: People → Members.
  - Editor and Viewer: Questions. Once Questions has a built view, that view is their home.
- **Questions' unbuilt screen says one thing:** what an Editor or Viewer will do there, and that they can ask through Claude now.
- The index route reads the role from the membership the session resolves, and redirects to that role's home.
- The failed screen and the unknown screen offer the reader's own home, not System.
- The console keeps its one home, Workspaces.
- No ADR names the home, so no ADR changes.

### Refusals

- **A screen shows a refusal's sentence, never its word.** The shared refusal template renders two parts: what went wrong, then what to do. There is no lead-in and no code element.
- **The word still crosses every transport as `{ word, class }`**, as ADR 0043 says. The web client receives it and chooses the sentence by it. MCP clients and `pnpm ops` see the word as before. The crossing function still logs a refusal with its word.
- **The glossary's *refusal* entry changes one sentence.** "A word reaches a screen, an agent and an operator as itself" becomes: "A word reaches an agent, an operator and the web client as itself; a person reads its sentence."
- Each feature keeps one word table: per word, what went wrong and what to do. The class fallbacks are rewritten under the rule, in plain words.
- **The forbidden class names who can act**, because the reader can't. The other classes tell the reader what to do.
- A failed response is not a character. "The platform did not answer, so nothing changed" becomes "No response, so nothing was saved. Try again in a moment."
- The console's refusal line already reuses the shared template, so the rewrite has one place to change.

### Empty states and lead lines

- **The shared empty-state template takes one line and an optional action.** The action is used only where the screen has no other way to take it.
- **Inviting has one label, "Invite a person."** The empty Invitations and Requests tabs offer no second invite button. The empty Groups tab adds no sentence under its create form.
- **Each screen's lead line says what the screen is for, in one plain sentence**, or is dropped. It no longer lists the nav beside it.

### The new-user and sign-in path

Each screen is rewritten under the rule. The review's suggested rewrites are the starting point. These decisions go beyond wording:

- **Sign-in names the destination it carries:** joining a workspace, or connecting Claude. It also says why the person is there when the session ended or they signed out. It never says "we". The header shows "Better Answers".
- **The code step gains a "Send a new code" action.** It uses the same send as the email step.
- **The code ceiling names the wait** whenever the refusal carries one.
- **An invitee without a name gives it on the invitation screen.** The screen shows a name field above the join button when the person has none. Submitting runs the display-name act, then the accept act.
  - If the name is refused, nothing is joined and the field shows the name's sentence.
  - If the name lands but the accept is refused, the name stands. The accept's sentence shows.
  - The separate display-name screen stays for a person who arrives without an invitation. T-027's story 38 still holds: the name comes before the join.
- **The invitation screen names the inviter and the role**, and says in a newcomer's words what the role lets them do. The role's meaning table already exists; a newcomer's line is added beside it. The audit-log clause goes.
- **The no-workspace screen offers one way on: ask to join.** The field asks for the workspace's short name. The sentence telling the person to sign in again goes, because it isn't true.
- **The picker drops a workspace the person was removed from**, and says they are no longer a member of it.
- **The routes card is trimmed**, although no role lands on it now. When no route is set, it shows one line. The embedding note shows only once an embedding route exists. The "Listed only" line and the list of unbuilt views go.
- **The shared keystroke words are rewritten.** The button is "Keyboard shortcuts". A "Move focus to … first" hint names what to select.

### The api's consent pages

- The consent page's warning says where the person goes next, in one sentence.
- **The session refusal gains a sign-in link that carries the OAuth query**, so the person comes back to the connection.
- Every refusal page ends with a next step.
- The "Sign in first" page's heading matches its body.
- The pages keep their own look. Only their words and the one link change.

### Tests read the words; they don't copy them

- **A spec reads a sentence from the SPA's own tables.** These are a feature's word table, the screen list and the role meanings, just as the routes spec reads the screen list today. It asserts the state the sentence belongs to: the region, its role, the next action.
- **A spec never pins prose as a literal.** Controls are still located by role and accessible name, and the name is read from the same table where one exists.
- **Some things stay literal:** the trust words, which are a closed set and part of the behaviour, and anything a person must type.
- **Every spec pinning a sentence this spec rewrites moves to this form**, in the ticket that rewrites that screen. Other specs move when their screen is next touched; there is no sweep.
- **The browser-suite skill's constants rule names words as well as screens.**
- **The api's consent-page suites read the pages' words the same way.**

## Testing Decisions

- **A good test asserts what a person can do and what state the screen is in.** It locates by role and accessible name, and reads any sentence from the SPA's own tables. It never asserts on a component's internals.
- **The browser suite is the seam for every screen here**, driven through the api harness's acts as today. No new seam is added. The owner ruled on 26/09/2026 that no new check holds the text.
  - **Landing:** a spec per role signs in and asserts the home. The routes spec is the model.
  - **The invitation's name field**, in the accept-invitation spec. Cover a person with no name and a person with one. Cover the name refused, where nothing is joined. Cover the accept refused after the name lands.
  - **Refusals:** a spec per class shows the word's sentence, and does not show the word. The absence check reads the word from the table.
  - **Empty states:** each rewritten tab shows its one line, and the invite act appears once.
  - **Sign-in:** the heading names the carried destination. The code step's "Send a new code" sends a code.
  - **The accessibility gate** runs over every rewritten screen, as it does today.
- **The api's own suites cover the consent pages.** The session refusal's link must carry the OAuth query and return to consent.
- **Prior art:** the routes spec reading the screen list; the accessibility gate; the api harness's acts.

## Out of Scope

- Screens beyond the new-user and sign-in path: the sources dialogs, review acts, the console and People's populated tabs. They meet the rule when next touched. The shared templates reach them anyway.
- A check or lint rule on the app's text. The owner ruled on 26/09/2026: no new check.
- The consent pages' look.
- The rail's icon-only labels. That is a layout change for its own ticket.
- Renaming glossary terms or code identifiers.
- Better Auth's own error bodies.
- A sweep of every spec's literals outside the rewritten screens.
