**Nine things wave D must know, and four of them are traps:**

1. **The chunk row is nearly built.** A `Chunk` already carries the id, the ordinal, the span, the **full wire locator** and the content. What wave D adds per row is `workspace_id`, `binding_id`, `source_document_id` and the three visibility columns from the binding narrowed by the document. The `Table` constant and the row derivation are still wave D's (ruling R1); the address arithmetic is not — call `split_into_chunks` and do not re-derive an id or a locator anywhere.
2. **`Host._config` is now `Host.app_config`**, public to the package. `land_rows` and `drop_binding` were repointed and are otherwise untouched. A module with its own main function builds its own app around it, which is what `landed.py` does; that is the pattern wave D follows if it needs a second flow.
3. **A failed document is absent, not raised.** The engine catches a component's exception, logs it and lets the run finish — so an unreadable document is simply missing from `LandedRun.documents`, and `read_afresh` still counted the attempt. **Wave D has no way to name *which* document failed**, and the catalogue reconcile needs that for the outcome word. Naming the failure per document is T-130's quarantine line; if wave D's reconcile needs it sooner, it is a line in a report and not a quiet addition here.
4. **`normalised_key` is `NOT NULL` on `LandedDocument` and nullable in the database** — the column is NULL until a run has converted the document (`source-tables.ts`). **Wave D's reader must derive it when the column is null.** The shape the schema's own tests use is `documents/<document id lowercased>/normalised`, beside the bind act's `…/original`. Wave C did not invent that derivation because the key is the bind act's to choose.
5. **The object key needs the workspace prefix and the column does not hold it.** `object_key_of` is the whole of it and `Bucket` applies it; a reader that passed the column's value straight to a bucket would find nothing and find it silently.
6. **`read_afresh` rests on one run per process.** The counter is module-level, which is correct only because `config._one_run_only` refuses `MAX_CONCURRENT_RUNS` at anything but one. If wave D ever runs two bindings at once in one process, that figure stops meaning anything.
7. **The `content_hash` the catalogue reconcile wants is over the original normalised text *before* the seam** (the ticket's line). `RedactedDocument` does not carry it — it carries the text after. Wave D hashes what `_converted` produced, which today means hashing the bytes it read, or wave C's shape grows a field. **Say which in the report.**
8. **The counts are sorted pairs and not a mapping**, and the findings are S0's own `Finding` — `category`, `tier`, `rule_id`, `start`, `end`, `score`, the offsets being code points into the text the seam was **given**, never into the redacted text it returned. The `finding` rows land from those directly.
9. **R4 still binds.** `worker_rt` has no `SELECT` on `index.chunk`, so a suite verifying rows reads on the owner connection; and every pool in a test connects as a login role `IN ROLE worker_rt`, never the harness's superuser.

#### The one correction to the design as written — read this before wave C or D

**F1, the spec and this note all say the workspace scope goes in the pool's connection
`init`. It cannot, and the test found it.** asyncpg resets a connection when it goes back
to the pool and its reset is `RESET ALL`, which takes a session setting with it
(`asyncpg/connection.py`, `_get_reset_query`). A scope applied in `init` therefore holds
for exactly the first checkout and is gone from the second — so a run lands its first row
and a later one is refused. The hook that runs **after** the reset, on every acquisition,
is `setup`, and that is where `open_pool` puts it.

Evidence, from the engine's own writes with the scope in `init`:

broken shape. Nothing in wave C or D needs to do anything about this; it is recorded so

### Wave C, iteration 3 — 11/09/2026

#### What the engine actually does, read off the installed 1.0.22

Four readings, each probed rather than assumed, and two of them changed the design.

1. **`RecursiveSplitter.split(text, chunk_size)` counts `chunk_size` in bytes** and reports
   both a `byte_offset` and a `char_offset` per end. **The `char_offset` is a Unicode code
   point** — confirmed on the fixture's astral text, where the first row ends at character
   37 and byte 40. So nothing is converted, and **hazard H15 is closed by measurement**
   rather than by a conversion nobody could have tested.
2. **The splitter trims the separator it cut on**, and this is the reading that changed the
   code. Over the `document-chunk` fixture at its own size of 80 it answers three rows at
