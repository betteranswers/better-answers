# S6 · A bid document's questions answered as one document

**Destination.** An Editor brings a bid document's questions in, confirms them in a table, and gets a response to each, drafted in the background and shown as each finishes. Unanswered questions sort to the top. The set goes out as one response-set document. Question sets is the first page of the area for work produced from the knowledge.

**Done when.**

- The browser suite takes a bid document to a confirmed question table on Question sets, and no response exists before the person confirms.
- The api claims the question-set job, and a queued job of that kind older than a lease leaves the worker healthy.
- A response-set document records one *usage* row per response.
- The owner reads the efficacy measure for the first customer's past question sets.

**Rests on.** ADR 0005, two tiers that share no code, so the api claims the job. ADR 0014, a question set's questions as rows and its input object Restricted. ADR 0004, a response as a write-up's second home. ADR 0016, an answer asserting only what concepts state, and the question set's flow.
Words: *question set*, *response*, *usage*, *write-up*, *job*, *claimant*, *principal*, *area*, *suggestion*, *promotion*, *Questions asked*.

**Builds on.** `claim_job` takes the kinds its caller runs, and the api's role may call it (`packages/schema/migrations/0087_the-held-lapsed-claim.sql`). `packages/schema/src/platform/job-tables.ts` gives each kind a claiming tier, and every kind today is the worker's. The worker claims only the kinds in `apps/worker/src/better_answers_worker/kinds.py`. S2b's answer path is `packages/core/src/answering/`. `packages/schema/src/knowledge/write-up-tables.ts` holds `write_up`.

**Must carry.**

- **Confirmation first.** The question set is extracted as a suggestion and confirmed by the person before any response is drafted. It is never a source and never company knowledge.
- **The bid document is Restricted.** The input object is Restricted by default, passes the redaction seam before extraction or any model call, is retained by rule and is in the erasure map (ADR 0014).
- **The job the api claims.** The question-set job's claiming tier is the api, which claims it through `claim_job` with the lease, heartbeat, reaper and poison that *job* and *claimant* name. Responses stream per question, unanswered ones first (ADR 0016).
- **Worker health by claiming tier.** `apps/worker/src/better_answers_worker/health.py` counts a claimable job of any kind as waiting, so an api-claimed job would mark the worker unhealthy. It counts only the worker's kinds.
- **The deferred principal.** The job runs under a deferred principal, which records the person it borrowed from and expires with that authority. This block settles its type in `packages/core/src/kernel/principal/principal.ts` and writes it into *principal* in `CONCEPTS.md`.
- **The document.** A response-set document records one *usage* row per response and is never an export. A `.docx` with real footnotes is beyond v0.1 (ADR 0016).
- **Promotion.** Each response is a *Questions asked* record an Editor may raise as a *promotion*.
- **The area's first page.** Question sets sits in the rail beside Ask and Knowledge.
- **The efficacy measure.** The first customer's past question sets run through this path, each response measured against the library `Answer` it must reuse.

**Open for the plan.**

- The deferred principal's shape: a fourth principal kind, or a user principal carrying the borrowed person and an expiry.
- How a finished response reaches the page: a tRPC subscription over the job, or a read of its outcome rows.

**Seams.** The core interface, extraction to document. The tier contract's queue cases for a kind the worker never claims. The api harness for the stream. The browser suite for Question sets.
