### C1 — the restore act (`/mattpocock-skills:tdd` first)

`packages/core/src/sources/findings.ts`, re-exported from `sources/index.ts`:

- `declareActs("sources", { restored: act("sources.finding.restored", { findingId: "id" }) })`. **The detail is the id and nothing else**: the reason is free text an Admin typed and could name a person, so it lands on the row and never on the ledger. No new `DetailKind`.
- `restoreFinding(principal, tx, { findingId, reason })` → `Result<FindingRestored, FindingRestoreRefusal>`:
  1. `requireAdmin` — a Viewer's and an Editor's `RoleRefusal` before any read.
  2. Parse the id through `boundarySchemas.finding.select.shape.id` and the reason through the boundary's own `restoreReason` refinement (ADR 0028 — never a second bound written here); a blank reason is `malformed`.
  3. `SELECT tier FROM finding WHERE workspace_id = $1 AND id = $2 FOR UPDATE` → `no-such-finding` when absent; **`not-the-always-set` when `tier <> REDACTION_ALWAYS_TIER`** — the **tier column, never the category**, because the officer-block post-pass raises a `person-name` at the always tier and that span *is* restorable.
  4. `UPDATE finding SET restored_at = now(), restored_by = $actor, restore_reason = $reason` — `now()` is the database's, ADR 0040 (a row's own timestamp), so this act takes no clock; `$actor` is `actorIdOf(admin)`, never a hand-built string.
  5. `record(...)` **bare, after the row**, with `subjectId` the finding id (ADR 0014 rule 4: its rejection aborts the transaction the row landed in).
  6. Answer `{ findingId, auditEventId, restoredAt }`.

Tests — `packages/core/test/findings.test.ts` (new file, the slice-interface seam, real Postgres, factories, expected values as literals):

1. An Admin's restore of an always-set finding: the row carries `restored_at`, `restored_by` equal to the Admin's actor id and `restore_reason` equal to the literal sentence; one ledger row with `act`, `family`, `subject_kind`, `subject_id`, `actor` and `detail` written down as literals.
2. The pair both ways: a **Viewer**, an **Editor**, a **default-on** finding and a **default-off** finding are each refused by the named refusal, with the row's three restore columns still null **and no ledger row** in the workspace.
3. A blank reason is `malformed`; a finding of another workspace is `no-such-finding` — nothing written either way.
4. The one-transaction rule: under `whileWritesAreRefused("audit_event")` the act rejects and the finding's restore columns are still null afterwards — the row and its event land or fail together.
5. A finding raised at the always tier whose **category is a default-tier one** (the officer-block shape) restores, which is the hazard written down as a test.

## Decisions taken in this plan (the orchestrator's to amend)

- **D1 — processor and country.** `llm_route` has neither column. The document names the **processor** and the **country** from a small declared table in `dpia.ts` holding only what the ADRs state — `anthropic` (Anthropic, United States), `mistral` (Mistral AI, the EU endpoint — unreachable in v0.1 since the embedding route is excluded), `local` (no sub-processor; the platform's own estate) — and *not recorded* for any other provider word. The alternative is no table at all and *not recorded* everywhere, which makes the fields dead until S2.
- **D2 — scope and retention class.** Neither is a column on `source_binding` (the glossary lists them among a binding's fields; the column arrives with the binding-management surface, S1 for upload and S4 for the connectors). Both fields are present in the typed document and read *not recorded*, with a docblock naming the block that fills them.
- **D3 — who may read it.** `requireAdmin`, as the publish act that will call it is an Admin's and the sources slice's other act is.
- **D4 — which routes are listed.** Every configured route row of the workspace except the `embedding` purpose (ADR 0020, amended 09/09/2026). A purpose with no row is not listed at all.
- **D5 — where the category list lives.** `packages/core/src/sources/dpia.ts` (H2), held to `contracts/redaction/cases.json` by C3.
- **D6 — the route read stays behind its owner's door** (the orchestrator's ruling, 11/09/2026, reversing the plan's first answer). `listRoutes` in `packages/core/src/llm/index.ts` already answers one `WorkspaceRoute` per purpose; it gains `retentionTail`, its suite gains the field both ways, and `dpiaInputFor` calls it and drops the embedding purpose. No SQL against `llm_route` is written in the sources slice and `table-ownership.ts` is untouched — there is no cross-owner read to record, because there is no cross-owner read.
- **D7 — the restore's refusal set and the ledger's detail.** `RoleRefusal · malformed · no-such-finding · not-the-always-set · Error`; the detail is `{ findingId: "id" }` alone, so no new `DetailKind` and no free text on the ledger. A second restore by an Admin is allowed and writes its own ledger row — the correction of a reason is itself an act, and the ledger keeps both.
