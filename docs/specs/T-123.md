### The defect, and how the plan let it in

`dueDateOf` at `packages/core/src/erasure/requests.ts:102` is
`setUTCMonth(getUTCMonth() + 1)`, which **rolls past a short month's end**:

| `clock_started_at` | answers | should answer |
| --- | --- | --- |
| 2026-01-31T09:00Z | 2026-03-03 | 2026-02-28 |
| 2026-01-30T09:00Z | 2026-03-02 | 2026-02-28 |
| 2026-08-31T09:00Z | 2026-10-01 | 2026-09-30 |

Three days late on a statutory deadline, **in the one direction a clock must not move** — and the
table's `subject_request_clock_check` cannot catch it, because it only asserts
`due_at > clock_started_at`. The test named *"across a month's end and a year's"* uses 2 April and
15 December, which never reach the case.

**This is the plan's fault as much as the implementor's.** The *Iteration 1* section of this note
said the clock was "one month on (`setUTCMonth(+1)`, **as the schema factory already computes
it**)" — it named the flawed copy at `packages/schema/test/factory.ts:741` as the model, so the
defect was specified, then duplicated, and the docblock's claim that the arithmetic is "written
once" was untrue from the first commit. A plan that hands an implementor an expression to copy
carries that expression's bugs; the plan should have said what the answer must be — *the same day
of the month, or that month's last day when it has no such day* — and let the implementor write it.

## Plan

### Iteration 1 — the request, the act and the clock (acceptance 1, 2, 3)

`packages/core/src/erasure/requests.ts`, re-exported from the slice's face.

- `SUBJECT_REQUEST_ACTS = declareActs("people", { received: act("people.subject_request.received", …) })`.
  The act's subject is the request's id; its detail carries the person id where the subject has
  one and **nothing from the identifier set**. The identifier count is the one thing
  the detail says about the set, as a `count`.
- `recordSubjectRequest(principal, tx, input)` → `Result<SubjectRequestRecorded, SubjectRequestRefusal>`.
  Shaped exactly as `narrowBinding` is (`packages/core/src/sources/index.ts` is the model): the
  role guard first (`requireAdmin`, refusal `role-forbids`), then the boundary parse
  (`boundarySchemas.subjectRequest.insert`, refusal `malformed`), then the row, then the ledger
  row written **bare** through `record` so its rejection aborts the transaction the row landed in
  (ADR 0014 rule 4). Ids minted with the kernel's `ulid`; the instants come from the
  caller (`clock_started_at`, `received_at` as `Date`s — ADR 0040, no ambient clock, no defaulted
  `Date` parameter).
- The clock is arithmetic the slice owns, written once: `dueDateOf(clockStartedAt)` is one month
  on (`setUTCMonth(+1)`, as the schema factory already computes it) and `deadlineOf(request)` is
  `extended_to ?? due_at`. `clock_started_at` later than `received_at` is accepted; earlier is
  refused by the table's `subject_request_clock_check`, which the act lets speak.
- `subjectRequestFor(principal, tx, id)` — the Admin-only read that returns the row **with** its
  identifier set. An Editor and a Viewer get `role-forbids` and never the set. This is the read
  acceptance line 2 is about.

**TDD first** (`/mattpocock-skills:tdd`) at `recordSubjectRequest`: the pair both ways
— the act writes both rows, and an act whose ledger write is made to fail leaves no request row —
is the test that fixes the shape before the body exists.

### Iteration 2 — the erasure map (acceptance 4, 5)

`packages/core/src/erasure/map.ts`.

- **One declared descriptor per store family**, the shape S0 already uses for the redaction
  categories: the family's word, the categories of personal data it holds (what the access answer
  reads), and its finder. The registry is `satisfies Record<ErasureFamily, FamilyDescriptor>` over
  a `const` tuple `ERASURE_FAMILIES`, so a family added without a finder does not compile.
- The union, from the spec's step 2 and acceptance line 5 — nine families:
  `concept-file` (the files at the bundle's head and their history: `generated.by`,
  `verified[].by`, git author lines), `bundle-commit`, `concept-verification`, then the five
  identity-set families `identity-user`, `identity-session`, `identity-verification`,
  `identity-invitation`, `identity-account`, and `source-document` — declared, its finder
  returning none until S1.
- Every finder takes the request's **identifier set** (and the person id where one exists) and
  answers locations — what in that family names the person — never a passage's text. The Postgres
  arms match `actor = human:<person id>` (`bundle_commit`, `concept_verification`), the person id
  (`user`, `session`, `account`) and the emails (`verification.identifier`, `invitation.email`,
  `user.email`). The git arm matches the emails over blobs and author lines.
- `erasureMapOf(platform, tx, git, request)` walks the registry in the tuple's order and answers
  one entry per family. For a subject with no user row the git and identity arms find nothing and
  the map **says so** — an entry with no locations, never a missing entry.
- The compile-time exhaustiveness is held in the suite by a `@ts-expect-error` case (the prior art
  is `packages/core/test/audit.test.ts` and `test/kernel.test.ts`; `tsc --noEmit` over `test/` is
  a step of `packages/core`'s own `check`), plus a runtime assertion that the registry's keys
  equal `ERASURE_FAMILIES` both ways.

**TDD first** at the family union and `erasureMapOf`: the map for a member is written as a literal
before a finder exists.

## The decisions as they were put (kept for the record)

**D1 — the act's detail needs an optional field, which the audit template does not have.**
`DetailShape` makes every declared field required (`detailRefusal` refuses a missing one), but the
ticket says the detail carries the person id *where the subject has one* — and for a person the
company's files name who never signed in there is none. Three ways out:

1. **(proposed)** the smallest extension to `packages/core/src/audit/vocabulary.ts`: a shape's
   value may be written `"id?"` — the kind with a `?` — meaning the field may be absent;
   `DetailOf` makes it optional and `detailRefusal` skips an absent optional and still refuses an
   absent required one. The act is then
   `act("people.subject_request.received", { personId: "id?", identifierCount: "count" })`.
2. the detail carries `{ namesAMember: "flag", identifierCount: "count" }` and no person id at
   all — which contradicts the ticket's line.
3. two acts, one per case — which contradicts the spec's one act name.

**Conflict note, checked:** `audit/vocabulary.ts` is the one file outside the erasure slice this
plan edits, and T-126's own note (its D7) says its detail is `{ findingId: "id" }` alone, adds no
`DetailKind` and does not touch that file — the reason an Admin typed lands on the row and never on
the ledger. So this is the only ticket in flight editing it and the serialisation risk is nil.

**D2 — `concept-file` is one family, not two.** The spec writes "concept files and their history"
as one phrase and the routine's git step rewrites both in one pass, so the map carries one entry
whose locations name paths at the head and commits in history. Say the word if you want
`concept-file` and `concept-file-history` split.

**D3 — the git arm needs a read the git door does not have.** `packages/core/src/store/git/index.ts`
has `head`, `commit`, `commitsAfter` and `readCommit`, and nothing that searches history. A slice
may not shell out to `git` itself (ADR 0029: the four stores are the doors), so this plan adds one
read to the git door — `historyNaming(platform, door, workspaceId, needles)`, answering the commits
and paths where a needle appears in a blob or an author line. No other ticket in flight touches the
git door, so the conflict risk is nil, but it is outside the strict "erasure slice only" scope the
brief drew.

**D4 — the map runs under the platform principal.** It is the routine's step 2 (T-124), the
identity-set arms read rows no workspace Admin should be handed across tenants (ADR 0035's
rejected oracle), so `erasureMapOf` takes a `PlatformPrincipal` and a scoped `Tx` (`withScope`).
The Admin's road to the same facts is the access answer over a map the platform computed.

## Known hazards

- **The slice sits at the top of the graph.** ADR 0029 rule 4: `erasure` may import other slices'
  interfaces and **nothing may import `erasure`**. `test/import-direction.test.ts` enforces it and
  already names the erasure face in its cases; a test importing the slice is the one importer
  allowed to.
- **The act lands with its row in one transaction**, declared against the audit
  slice's template, and the detail carries ids and never an email or a name. The ledger door
  rejects rather than returning a `Result` — that rejection is what
  aborts the transaction, so it is written bare and never wrapped in `attempt`.
- **The act name needs no schema change.** `audit_event.act` is `family.subject.verb` held by a
  regex and a template-literal type, not a closed enum, so `people.subject_request.received` needs
  no migration and no edit to `packages/schema`. `test/audit.test.ts` loads every entry point the
  exports map names, so the new declaration is walked with no edit to that suite either.
- **The git-history finder reads a real bare repository in a temporary directory.** The prior art
  is `suiteWithBundles()` in `packages/core/test/workspace-with-bundle.ts` — a migrated Postgres,
  a bundle root and an Admin, Editor and Viewer in one arrange block. Use it; do not hand-roll a
  repository.
- **A concept file names a person by email, the ledger by person id.** `generated.by` and
  `verified[].by` carry `human:<email>` (ADR 0019, `kernel/actor.ts`'s docblock); `bundle_commit.actor`
  and `concept_verification.actor` carry `human:<person id>` (ADR 0035). The finders must not
  assume one form — this difference is the reason the routine rewrites files and never the ledger.
- **The identity set is RLS-exempt**, so a scoped transaction reads `user`, `session`, `account`,
  `verification` and `invitation` without a second door; `rls-exemptions.ts` says why each is out.
- **jscpd runs at zero clones** in the root `check`, and nine finders written as nine near-identical
  SQL reads is exactly the shape it failed T-120 on. One shape over the descriptor table, not nine
  copies.
- **knip runs in the root `check`.** The slice's exports have no production caller until T-124, and
  knip counts a test's import as a use — so the suites must import everything the face exports, or
  the gate fails at the very end for a reason the named suites never showed.
- **Docker must be up**: every `packages/core` suite starts a Testcontainers Postgres.
- **Three tickets run beside this one** (T-121, T-126, T-127) in their own worktrees. Touch nothing
  outside `packages/core/src/erasure/`, its suites, and — subject to D1 and D3 — `audit/vocabulary.ts`
  and `store/git/index.ts`.
- **The `/implementing-gdpr-data-subject-access-request` skill** names the search identifiers and
  the clock's pause; read it before writing the finders and `clock_started_at`.
- **GitNexus** is the main checkout's index at the block's tip: `impact` before editing a symbol
  that exists there (`declareActs`, `DETAIL_KINDS`, the git door's exports), `detect_changes` with
  this worktree's absolute path before every commit. A symbol this ticket creates has no caller to
  report.
