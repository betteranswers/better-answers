# T-382 — Comment rules, commit conventions and a quality sweep

*Spec written 24 September 2026 in the owner's session that day. Two read-only reviews ran first. One judged the comment setup from first principles against the new `code-comments` skill. The other measured this repository against five standard ones: cal.com, documenso, dub, tRPC and Hono. The owner accepted both, with two changes: no CONTRIBUTING.md, and full Conventional Commits rather than a mixed form. The owner then adopted `complexity-gate`'s cap of 8. The same day the owner answered the spec's two open questions: the doc-block cap, and what holds short sentences. Both are written in below as decisions. Every decision here is taken.*

## Problem Statement

The owner finds much of what happens in this repository hard to follow. The rules are mostly sound. The setup around them is custom, and the language is a house style that no other repository uses.

Comments are the clearest case. The first comment rule already said "explain why". Agents read it as "explain" and copied the narrative voice of the rules files, and comments reached about 4.5 words per line of code. A strip brought them down to 0.019 comment lines per code line in TypeScript source. The tooling that holds that level is about 2,400 lines of custom gates, plus 1,940 lines of one-off strip scripts nothing calls any more. That is about eight times the comments it polices. The policy sits in eight places, and an editor shows no breach of it; only `check` does.

The language departs from the norm in the same way:

- 83% of commit subjects state what is now true and end with a ticket id. `pnpm land` refuses a Conventional Commits label outright.
- Ticket titles run to 50 or 60 words.
- Test titles have a median of 14 words, against 4 to 8 elsewhere.
- Contributor docs average 21.8 words a sentence, against 8.6 to 14.9. The read-first set is about 45,000 words.
- ADR file names run to 219 characters (median 85).

Two further gaps:

- Nothing caps how complex a function may be. 93 TypeScript functions and 3 Python functions are over 8 today.
- The skills the workflow now names live only on the owner's machine: `code-comments`, `mutation-testing`, `repo-quality-sweep` and `complexity-gate`.

## Solution

The repository keeps its few real rules and holds them with standard tools, in the forms a reader from any of the five comparators would recognise.

- **Comments.** Three short rules. Stock oxlint and ruff rules hold most of them. One custom rule holds the rest, and it lives in the one lint config, so an editor shows a breach as it happens. An exported function may carry a short doc block.
- **Commits, PRs and tickets.** Conventional Commits, checked by one commitlint config in the commit hook, in `pnpm land` and on the PR title.
- **Tests.** Short titles, held by a stock lint rule.
- **Docs.** Contributor docs in short sentences, written with `human-writing`. `writing-for-agents` is kept to the agent-facing files it was written for. ADR files under short names.
- **Complexity.** A cap of 8 per function, held by stock rules in both tiers.
- **Skills.** The five skills the workflow names are tracked in the repository, so every agent loads the same copy.
- **The sweep.** Once the rules and gates land, `repo-quality-sweep` brings existing code in line, one area per PR.

## Implementation Decisions

### The comment rules

- **The comment rule** is rewritten. A comment says only what the code cannot say: a constraint, a trade-off or a trap. It uses plain words and 25 words at most. Absent is the default. A comment never restates what the code does. It carries no history, and no ticket, date, ADR or rule tag. A comment that sits on a declaration uses `/** */`, so editors show it on hover. The `Reviewer:` line stays, because no tool can read a comment's intent.
- **The rule-tag rule** is unchanged: a rule tag is written in a rules file, a review finding or a gate's failure message, and nowhere else.
- **A new directive rule.** A directive names what it suppresses and gives its reason on the same line. This covers `@ts-expect-error`, oxlint and ESLint disables, `// Stryker disable`, `# noqa` and `# type: ignore`. The reason counts against the 25-word cap. `@ts-expect-error` is the only TypeScript suppression; `@ts-ignore` is refused. There are no TODO, FIXME or XXX comments: the ticket is filed instead.
- **Doc blocks on exported functions.** An exported function in `packages/core`, `packages/schema` or the worker may carry a doc block. It states only what the signature cannot: units, ranges, what `null` or an empty result means, side effects, the refusal it returns. It runs to 50 words at most, tags' prose included. It carries no citations, no TODOs and no history. It is allowed, never required.
- **The word cap stays a check.** The skill is guidance and the cap is what holds it: the first clean-out grew back within 16 days with nothing enforcing it. A doc block on an exported function may run to 50 words. Every other comment stays at 25. Internal functions and members get no doc block. A boolean whose meaning is not in its name is renamed rather than documented.
- The `type-assertion` rule's text changes to "the disable's reason", because the `as` ban already forces a disable with a reason.

### The lint that holds them

- **One lint config.** `.oxlintrc.json` holds every comment rule, so `pnpm lint`, the pre-commit hook and editors all show them. The separate comment-gate config and its script entry go. The Claude Code hook runs the same config.
- **Stock oxlint rules at error:** `typescript/ban-ts-comment` (a description required), `typescript/prefer-ts-expect-error`, `eslint/no-warning-comments`, `unicorn/no-abusive-eslint-disable`, and `--report-unused-disable-directives`. A dry run of the first four finds 0 problems in today's tree.
- **Stock ruff rules for the worker:** `PGH003` and `PGH004` (no blanket `type: ignore` or `noqa`), `FIX001`–`FIX004` (no TODO, FIXME, XXX or HACK), and `RUF100` (no unused `noqa`).
- **One custom rule stays: `comment-only-the-why`.** It keeps the 25-word cap and the citation ban, and allows 50 words for a doc block on an exported function. It gains two checks: a disable carries a reason (no stock oxlint rule does this), and a directive's reason counts against the cap. Six reasons run 27 to 35 words today and are trimmed. One disable has no reason and gets one. The rule's string-literal citation check moves out into a rule of its own, because it polices user-facing text, not comments.
- **The Python gate is narrowed to `.py` files.** It holds the same caps: 50 words for a public function's docstring in the worker, 25 for every other comment. Its shell, SQL and TOML lexers go, along with the hard-coded exemption they needed. The density ceiling holds comments in config files alone.
- **The density ceiling stays** as the volume backstop, at 0.10 comment lines per code line in source and 0.05 in tests. Doc blocks on exports count toward it. If every exported function gained a three-line block, source would reach about 0.07, still under the ceiling.
- **The tag test reads its list from the JSON file** it now retypes by hand.

### What is retired

- The one-off strip and proof scripts, and their two `package.json` entries (1,940 lines).
- The `require-safety-comment-for-type-assertion` rule. The five sites that carry both a safety comment and a disable reason lose the safety comment (8 lines).
- The separate comment-gate oxlint config.

### Complexity

- **The cap is 8 per function, in both tiers.** TypeScript uses oxlint's stock `complexity` rule (`max: 8`), available at the pinned 1.85. A probe confirmed it reports a function over the cap. Python uses ruff's `C901` with `max-complexity = 8`, in the worker's and devtools' ruff configs.
- **Baseline, 24 September 2026:**
  - **TypeScript:** 93 functions over 8, in 58 files. 73 are in source and 20 in tests. By workspace: `packages/core` 41, `apps/api` 22, `packages/devtools` 11, `scripts` 9, `packages/schema` 6, `apps/web` 4. The median is 11, the highest 36, and 14 are over 15. The vendored anti-slop lift is excluded, as the lint config already excludes it.
  - **Python:** 3 functions over 8. Two are in the worker (one source, one test) and one is in devtools' Python gate.
- **Rollout: file-level baseline, not touched files.** The whole-tree lint in `check` has no mode that checks only changed lines or functions. oxlint's `overrides` and ruff's `per-file-ignores` work per file. So the rule goes in at error from the first ticket, with the baseline files listed in one override that turns it off.
  - Every file not on the list is held at once, including every new file.
  - The sweep's complexity step clears the list area by area and deletes a file's entry as it clears it. An agent whose ticket touches a listed file may do the same.
  - The override is deleted when the list is empty. The list only shrinks.
- `complexity-gate` names ESLint as its tool. Here oxlint's rule does the same job, and the project's rules set the tool. The skill's CRAP report is used by the sweep's inventory as a one-off ranking, not as a gate.

### Commits, PRs and tickets

- **Conventional Commits**, subject 72 characters at most: `type(scope): summary`.
  - The summary is imperative and lower-case, with no full stop.
  - Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `revert`.
  - The scope is optional and names a workspace or area: `api`, `web`, `worker`, `core`, `schema`, `devtools`, `design-system`, `deploy`, `ci`, `docs`.
  - The body explains what changed and why, in plain prose.
  - The ticket goes in a footer, `Refs: T-nnn`, not in the subject.
- **One checker.** One commitlint config, extending the stock `@commitlint/config-conventional`. The commit hook runs it in place of today's custom subject-length check. `pnpm land` runs it in place of its own subject rules, and reads the ticket id from the footer to name the branch. A CI step runs it on the PR title, since that title becomes the merge commit's subject.
- **The PR title is the commit subject, and the PR body is the commit body.** The repository's merge settings stay as they are.
- **Renovate** writes Conventional Commits (`chore(deps): …`).
- **Ticket titles** take the same form, `type(scope): summary`, 72 characters at most. The detail goes in the body. The ticket's id is not part of its title. The issue tracker doc says so. The open tickets on the board are retitled once, origin first; closed tickets keep their titles as history.
- The workflow doc's section on the commit's prose form is replaced by this form. Its steps that say how a PR title is made follow it.
- History is not rewritten.

### Test titles

- **A test title is a short phrase in the present tense saying what the system does:** "refuses a name over 100 characters". It has 10 words at most and never uses "should". The `describe` block names the unit under test. The rule on titling a test is rewritten to say this.
- **TypeScript** is held by the stock `vitest/valid-title` rule: `disallowedWords: ["should"]`, and `mustNotMatch` set to a slash-delimited pattern refusing 11 words or more. A probe confirmed both fire. At pinned oxlint the pattern works only in the slash-delimited string form; the object and plain-string forms fire nothing.
- **Baseline:** 1,846 TypeScript titles are over 10 words. By workspace: `packages/core` 821, `apps/api` 580, `packages/schema` 234, `packages/devtools` 141, `apps/web` 70. The rule goes in with the same file-level baseline override as complexity, and the sweep clears it.
- **Python:** a test function's name follows the same shape, `test_refuses_long_name`. No stock ruff rule holds its length, so the rule's `Reviewer:` line holds it. Today 269 of 378 Python test names are over 10 words, and the sweep renames them.

### Contributor docs

- `AGENTS.md`, `docs/agents/workflow.md` and `CODING_RULES.md` are rewritten to about 15 words a sentence. Qualifications become Do and Don't bullets. The rules file keeps the form the rule-form test holds.
- The glossary is used only where a term is needed. Where a plain word says the same thing, the plain word is used.
- ADR bodies are not rewritten.
- **`/writing-for-agents` narrows to its own scope.** `AGENTS.md` says to use it "when editing ANY file". That changes to skills, `AGENTS.md` and `CLAUDE.md`, the files the skill is written for. Its "leading words" technique compresses ideas into coined terms. That is what made the docs hard for a person to read. It is a plugin skill, so it is not edited.
- **Any doc a person reads goes through `/human-writing`.** `docs/agents/workflow.md` names it for those docs. The skill now carries a target of about 15 words a sentence where a project sets none. It also says to turn stacked qualifications into bullets, and to use the common word over a coined one, defining a coined term where it first appears.
- **No gate holds sentence length; review does.** The sweep's closing inventory re-measures the average sentence length of the three contributor docs. Vale's stock sentence-length rule is added only if the average drifts past about 18 words.

### ADR file names

- Each ADR file is renamed `NNNN-short-slug.md`, with a slug of about five words. The full decision sentence stays as the file's title and as its index row.
- Every inbound link moves in the same PR. The ADR-index test follows the new names.

### Skills

- `code-comments`, `mutation-testing`, `repo-quality-sweep`, `complexity-gate` and `human-writing` are tracked under `.claude/skills/`, with `.gitignore` exceptions and entries in the skills lock. The owner's updated copies are the ones committed.
- Where a skill and this repository's rules differ, the rules win. `code-comments` already says so. The tracked copy is the one agents load.

### The workflow edit

- The owner's uncommitted `workflow.md` change lands with the comment-rules work, once the skills are tracked. It adds `/code-comments` while building and `/mutation-testing` in the review slot, before `/code-review`. Its wording is tidied: the clause without a verb gets one, and the capital after the semicolon goes.
- The same change names `/human-writing` for any doc a person reads, and `AGENTS.md`'s skills line narrows `/writing-for-agents` to skills, `AGENTS.md` and `CLAUDE.md`.

### The sweep

- It runs after the comment rules, the complexity rule and the test-title rule have landed, so the gates hold its output.
- Phase 0's inventory is filed as an ordna ticket with one checkbox per area, not as a GitHub issue.
- Each area is one PR through `pnpm land` and the merge queue, under about 400 changed lines, and behaviour-preserving. A bug it finds is filed as a ticket and fixed separately.
- Per file, in order:
  1. Duplication: jscpd and knip, which are already in `check`.
  2. Complexity: decompose each function over 8, and delete the file from the baseline list.
  3. Comments: add a doc block to an export where a caller would otherwise guess, move declaration comments to `/** */`, and trim directive reasons.
  4. Test titles: rename to the short form, and delete the file from that baseline list.
  5. Verify: typecheck and the suites green, lint clean, and a scoped `/mutation-testing` run on logic steps 1 and 2 touched, with before and after quoted in the PR.
- The closing inventory also re-measures the average sentence length of `AGENTS.md`, `docs/agents/workflow.md` and `CODING_RULES.md`. It reports the figure, and a ticket for Vale's rule if it is over about 18.

### The ADR amendment

- ADR 0045 gains a dated amendment. The comment gates are now one lint config. It uses stock oxlint and ruff rules, one custom rule, a Python gate for `.py` files only, and the density ceiling. The complexity cap and the test-title rule are held by stock rules in the same config. The `docs/adr/README.md` row moves if its live conclusion moves.

## Testing Decisions

- **One seam: the gate runner.** Every gate is proved by running its tool over a throwaway tree, as `packages/devtools` already does for every gate. Each rule gets a fixture it refuses and one it accepts, controls both ways.
- **Comment fixtures:**
  - a 26-word line comment (refused)
  - `@ts-ignore` (refused)
  - `@ts-expect-error` with no reason (refused)
  - a disable with no reason (refused)
  - a disable that suppresses nothing (refused)
  - a directive reason over 25 words (refused)
  - a TODO (refused)
  - a `/** */` on a declaration (accepted)
  - a doc block on an export that states units and the refusal (accepted)
  - a 50-word doc block on an export (accepted), a 51-word one (refused), and a 26-word block on an internal function (refused)
- **Python fixtures:** a blanket `noqa`, a blanket `type: ignore`, an unused `noqa` and a TODO, each refused. A 50-word docstring on a public worker function is accepted and a 51-word one refused.
- **Complexity fixtures:** a function of complexity 9 in a file off the list (refused), the same function in a listed file (accepted), and a function of 8 (accepted). The same three for Python.
- **Test-title fixtures:** an 11-word title (refused), a title with "should" (refused), and a 10-word title (accepted).
- **Commit messages:** commitlint is proved through `pnpm land`'s own command in a throwaway repository, and through the commit hook with a fixture message. A Conventional subject is accepted. A declarative subject, a subject with the ticket in it, and a subject over 72 characters are each refused. The branch name is read from the `Refs:` footer.
- **The PR-title step** is held by the workflow tests, and any action it adds is pinned to a commit.
- **Docs:** the ADR renames are held by the ADR-index test and the docs lane's link check.
- **Prior art:** the lint-rules suite, the comment-gate suites, the land suite in `packages/devtools`, `workflow-tools.test.ts` and `workflow-pins.test.ts`, and `adr-index.test.ts`.
- **A good test here** runs the real tool over real files and asserts what it refuses and what it accepts. It never asserts a config file's contents.

## Out of Scope

- A CONTRIBUTING.md. Nobody else will contribute.
- Rewriting git history or the titles of closed tickets.
- Rewriting ADR bodies; only their file names change.
- Renaming domain terms in code, or the avoid-word test and the glossary's avoid-lists. Both reviews noted them; the owner has not ruled on them.
- A CRAP gate. The CRAP report is only an inventory aid for the sweep.
- Mutation-score targets. The nightly mutation run is T-229's and T-381's.
- Editing `/writing-for-agents`. It is a plugin skill; only where `AGENTS.md` points to it changes.
- A gate on sentence length, unless the sweep's closing inventory finds the average past about 18 words.

## Further Notes

**Evidence.** The figures come from two reviews on 24 September 2026: a first-principles review of the comment setup, and a benchmark against cal.com, documenso, dub, tRPC and Hono, with cocoindex for Python.

- Comment lines per code line: 0.019 in TypeScript source, 0.008 in tests, 0.021 in worker source. Before the strip, 0.55 and 0.66.
- JSDoc: 2 of 1,229 TypeScript functions have a block; none of 491 exported functions and none of 201 public Python definitions do.
- Sampled comments that give a real reason: 22 of 30 here, against 6 to 10 of 30 elsewhere.
- The complexity and test-title baselines were counted for this spec with oxlint 1.85 and ruff 0.16.5.

**Order of the work, for `/to-tickets`.** Each ticket is blocked by the ones before it unless noted.

1. Skills tracked, the comment rules and their lint, the retire list, the ADR 0045 amendment, and the owner's workflow edit with the `/human-writing` and `/writing-for-agents` lines.
2. The complexity rule with its baseline override. It edits the same lint config as 1.
3. Conventional Commits: commitlint, the hook, `pnpm land`, the PR-title step, Renovate, the workflow and issue-tracker docs, and the open tickets retitled. It can run beside 2.
4. The test-title rule with its baseline override. It edits the same lint config as 2.
5. The contributor docs rewrite, after 1 and 3, which both edit `workflow.md` and `CODING_RULES.md`.
6. The ADR file renames. They can run beside 5.
7. The sweep's inventory ticket, then one PR per area.

**This spec's own commits** are in the old form. `pnpm land` refuses a Conventional Commits label until ticket 3 lands.
