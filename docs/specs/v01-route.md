## Problem Statement

*As of 09/09/2026, when this was written. Each block's status row says what has changed since.*

The owner of better-answers set out to build a living company knowledge map for one first customer — its product, service and sector guides, its four bid libraries as `Answer` concepts, search and cited Q&A, a question set answered from the knowledge with citations, a read-only MCP surface, and Control Centre — on a foundation locked by the pre-build gate. The foundation is built and enforced: four store doors, the governed write and its reconciler, the map as application data, one read predicate rendered once, one person id, one origin, the tier contract, six repository gates. The product is not on any route. Layer 1 of the knowledge system — sources — is a substrate with no pipeline; `ask` always refuses; guides are a cascade helper; the erasure seam is eight lines; five of Control Centre's six pages render *unbuilt*. None of the gate's B7 to B10 has a ticket, and every build ticket since the gate has re-grilled at build time what the map had already decided, because the step the Wayfinder hand-off names — one spec over the cleared map — was skipped and the gate's §7 task list stood in for it. About one task in five since the gate has been product work. Code is waiting on "the map revisit", a document that did not exist until this one.

## Solution

One document holds the route: this spec. Its head is the vision's v0.1 row expanded into the stories a completed v0.1 satisfies. Its body is a numbered sequence of **blocks**, each about a page: a one-line destination, the ADRs and glossary words it rests on, what in the tree it builds on, the obligations pinned in code or research it must carry, its blocking edges, the open tasks it absorbs, and a seam sketch. The gate's horizontal B7 to B10 are re-cut vertically — S1 is one uploaded document to a cited passage, not "sources"; B10's six pages dissolve into the blocks, each landing its own page through the browser suite — and four things the build showed missing from §7 are added: the redaction seam (S0), the model client and signals (S2b, O1), the question set (S6) and the producer (S7); one reserve block, S8, holds the concept vectors ADR 0016 defers to a measured trigger, so no map is ever charted for them. Every open product task in the tracker (ordna's board then, Linear since 30/09/2026) is named in exactly one block; every platform-level mutation finding is placed in the block whose seam it names; the two obligations the 7 September addendum pinned in code are placed by name. Remediation moves off the route, one Linear issue each, among the findings put off for later. The status table is the frontier: a product session opens it, picks the first unblocked block, takes it to `/ce-brainstorm` and `/ce-plan`, and comes back to change its row.

## User Stories

### The Admin at the first customer

1. As an Admin, I want to connect an uploaded document to my workspace, review what the pre-scan found in it by category and rule, and publish it, so that my company's knowledge enters the platform through a gate I ran and can explain.
2. As an Admin, I want every connected source to count as Restricted until I publish it, the publish to release the sensitivity I chose, and every widening to be my recorded action, so that doing nothing is the safe thing and nothing reaches a reader I did not admit.
3. As an Admin, I want a sort code, a date of birth or a home address in a document withheld before it is split, embedded, extracted or sent to any model, so that no derived store and no processor ever holds the value.
4. As an Admin, I want the platform to emit the DPIA input for each connected source — the data types, the sensitivity, the rules in force, the model choices with their processor and country, the retention tail — so that our privacy assessment is written from what the platform actually does.
5. As an Admin, I want to connect my company's public website by URL prefix and a SharePoint library, see the enumeration and a cost estimate at review, and accept the estimate once, so that every sync indexes and extracts on a cadence within a scope I priced.
6. As an Admin, I want a spending limit the platform refuses at, in one sentence naming who can raise it, so that a sync never silently narrows the work and never silently spends past what I set.
7. As an Admin, I want every suggestion of every kind — suggested concepts from a sync, an Editor's edit, a promotion, an alias merge, a platform-bundle update — waiting on one page, *To decide*, with a summary that names the kinds it introduces, so that nothing platform-prepared reaches the knowledge base without my decision.
8. As an Admin, I want a bulk acceptance to write one commit per suggestion with per-item outcomes, and a set the platform refused mid-acceptance returned to its proposer with the reason, so that partial success is a state I can see and never a silent one.
9. As an Admin, I want a poisoned sync's suggestion set reversed by sync in one action, so that a bad extraction stays out of a history that is permanent.
10. As an Admin, I want the Kinds list on Knowledge with counts per kind and per collection, and to rename or merge a kind by one bulk commit, so that my company's language is read off its concepts and corrected by me, never declared in a file.
11. As an Admin, I want Knowledge › All knowledge over every concept and write-up, with exports on its toolbar, and conflicts and verification requests beside it on Knowledge › Conflicts and Knowledge › Due for verification, so that the state of the map is read in one area.
12. As an Admin, I want to invite a person by email, change their role, remove them, and end every sign-in and token they hold in this workspace, so that access follows the people my company has today.
13. As an Admin, I want groups, flat and Entra-aligned, as the one thing an audience names, so that who may see a connected source's content is one group lookup.
14. As an Admin, I want to name a concept's owner per collection, with a per-concept override, so that *edit* suggestions and verification requests reach a named person's Inbox and not only mine.
15. As an Admin, I want System's eight cards over real rows — boxes, backups, sources and the worker, the map, knowledge, questions, connected assistants, personal data — each line with an action, so that I find out about a missed backup or spend at 80 % of the spending limit before a customer does.
16. As an Admin, I want to export the knowledge base at a commit, the whole repository, the records about its concepts, or a guide's prose, so that my company's knowledge is its own asset and leaves with it.
17. As an Admin, I want a person's valid erasure request to rewrite every author and verifier id the platform wrote for them, across history, the index, the evidence and the map, and the report to say exactly what it did and did not do, so that "beyond use" is honest.

## Implementation Decisions

### What a block is, and the rules every block's plan follows

- A **block** (`CONCEPTS.md`) is a destination a session can pick: about a page here, taken to `/ce-brainstorm` and then `/ce-plan` before its build. Its plan in `docs/plans/` holds the units, its tracer bullets, and the pull request that lands each one names the block's Linear issue where it has one. The block itself is never one of its plans. A block lands its own page — the six-pages layer of the gate's B10 dissolves into the blocks below, and ADR 0037's latency budget is asserted per page as it lands.
- **The authority order** stated at the top binds every block's plan. A plan cites levels one to four for what and the rest for why.
- **The staleness pass, scoped.** The first step of each block's planning is an AFK research pass over only the map tickets and briefings that block cites, reporting per claim *stands* or *overtaken by ADR nnnn / commit*. It never re-assesses all 85 tickets. The seed list of tickets already known to be overtaken is in Further Notes.
- **Findings put off for later** are where a finding from a gate, a mutation run or a review goes: one Linear issue, no map, no plan until it is picked up, no grilling — *a finding put off for later*, in `docs/agents/issue-tracker.md`'s words. A Wayfinder map is charted only for a destination this document does not hold.
- **The api's skills are read first** (grill Q8, Q15, 09/09/2026). A seam sketch that touches `apps/api/` names the skill under `apps/api/.claude/skills/` it follows — router, validators, links, non-JSON content types, error handling, subscriptions — and the tRPC-skills rule in `apps/api/CODING_STANDARDS.md` binds the build the same way. No second HTTP route is opened beside tRPC for a shape a skill already covers.
- **A partial edge binds the bullets it names, never the block** (grill Q19). "Blocked by S1 for `open` by locator only" means the block is planned when its other edges are done, and the units that need S1 name it in their plan's dependencies; the status table's *blocked by* column says which lines an edge holds.
- **The next block is marked, not inferred** (grill Q5). One row per *strand* (`CONCEPTS.md`) carries **next**, set by the owner in the commit that changes a status; table order decides only when no row is marked. A parallel session may plan a second unmarked block whose edges are done.

### The blocks

#### S0 · The redaction seam and erasure

**Rests on.** ADR 0020 (the seam in the worker's conversion step, the three tiers of redaction rule, findings by category × rule, the `Person` concept, the routine, the narrowed promise of 30/08 and the erasure report's fixed wording, the erasure pseudonym of 05/09); ADR 0035 (one person id; the user row pseudonymised, id kept); ADR 0022 (every restore replays the erasures completed after the dump before `api` turns healthy; every third drill rehearses the routine on a synthetic subject); ADR 0012 (author lines mailmapped to the pseudonym; the erasure re-derive as a map rebuild reason); ADR 0024 (bare repositories and the mirror; no forge to pause); ADR 0013 (findings at three moments; widening blocked while special category is unreviewed). **The one memo is the detector's** (ADR 0036, amended 21/09/2026; built 22–23/09/2026 as T-285 to T-288). It is `detected(normalised_text, detection_key)` in the worker's `pipeline/detected.py`, and it holds no text. Conversion is unmemoised on every sync. A withholding is applied per finding and never cached (T-286). The detection key is its own digest, split from `RULE_VERSION` (T-287). The routine's LMDB wipe is **one action in order**: the connected source's passage rows deleted in the api's transaction, the directory removed, an `index` job enqueued (T-113, 10/09/2026, worker-host F2, F4). ## Testing Decisions

A good test drives external behaviour through the interface a caller uses and asserts what that caller can observe — commits, rows, refusals, invisibility, a passage, a page — never internals. Real Postgres always; our own code never mocked; setup through factories; a pair checked both ways; an expected value written down. A block's functional tests are named in its plan, before a line is written, and every mutation finding a block carries is a runtime test in that block's acceptance criteria.

The seams, agreed 09/09/2026 — seven that exist and one new:

1. **The core slice interface** over real Postgres and, where a block writes the bundle, a real bare repository (prior art: the concepts, workspaces and members suites). Every block's actions and refusals.
2. **The api HTTP harness** for the MCP surface, tRPC and the authorization server (prior art: the MCP, oauth-flow and ops suites). Every block reached through a transport.
3. **The browser suite** over a served build, one spec per page a block lands, with its ADR 0037 budget and the accessibility gate (prior art: the models-and-spend and picker specs; the browser-suite skill).
4. **The worker pytest harness** (prior art: the tier-contract, pg-harness and rebuild suites). S0's detector, S1's and S4's pipeline steps, S7's extraction.
5. **`contracts/` conformance**, both tiers' suites reading the same fixture; a fixture on disk but not in the manifest fails both (prior art: the twelve agreements in `contracts/manifest.json`). S1 adds the first document-shaped agreement.
6. **The `runOps` seam** — *done · refused · not built* (prior art: the ops suite). S0's two commands, ~~S5's stuck-ref command~~ (T-108 closed 19/09/2026, #73), P2's provisioning.
7. **Rebuild-equivalence, cross-tier and live** (T-057) — the enforceable meaning of *derived, never a source of truth*; every block that touches the map keeps it green.
8. **The document-shaped cross-tier test** — new, S1's: the api's actions, the worker as a real process, the api's read; no fixture between the tiers. S4 and S7 extend it rather than adding a seam.

Two third-party doubles on the route: a fetch-shaped fake at the model client's wire seam for S2b's model client — the shape is S2b's ADR — reused by S7; and a SharePoint fake at the Graph API in S4, for the same reason. A third, at the embeddings endpoint, arrives only with S8: no v0.1 block embeds.
