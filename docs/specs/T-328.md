# T-328 — Provisioning pulled forward from P2: the first client's workspace and its memberships by two ops commands, so the reviewed bundle can land

*Spec written 22 September 2026 by the Coordinator of the T-307 goal, from the route's P2 and C1 blocks, T-028's lines 3 and 4 (owner, 04–05/09/2026), ADRs 0009, 0020, 0035 and 0038, T-063's spec, the T-022 research on Better Auth's `admin()` plugin, T-307's spec, and the owner's three answers of 22/09/2026 recorded under Implementation Decisions. No grill: every decision below is either on the map already or one of those three answers. The pull-forward is the owner's agreement of the same day; P2 stays blocked by P1 for everything else.*

## Problem Statement

The client's four bid libraries are one reviewed OKF bundle — 243 concepts under `.planning/client-bundle/knowledge/` — and the loader that lands them, `pnpm ops import-bundle`, is on `main` (T-307). Nothing can run it against a real workspace. No workspace exists for the client; the platform provisions a workspace only from the api harness's test builder and the bootstrap of the first drill, never by a command an operator runs; and nothing in production creates a membership — email-code sign-in creates the person's user row, and that is where it stops. The loader refuses a `verified` event whose person is not a member (`verifier-not-a-member`, and every concept in the bundle is verified by `human:matthew.burgess@phew.org.uk`), and it runs as a named Admin or Editor of the workspace (`--as`), never as the platform. So the operator cannot land the bundle, on staging or on production, until a workspace exists with two people in it.

The route lands provisioning in P2, the platform console, which is blocked by P1 (the People screen and Microsoft sign-in). C1 waits on P2 "for the provisioning act and first membership only". That is the piece the loader needs, and nothing else of P2.

## Solution

Two commands at the `runOps` seam, beside `replay-erasures` and `import-bundle`, both platform acts:

- `pnpm ops provision-workspace --name <name> --slug <slug> --admin <email>` creates the workspace and its first membership, an Admin, for a person who has already signed in, and prints the workspace id the operator needs for every later command.
- `pnpm ops add-member --workspace <id> --email <email> --role <Admin|Editor|Viewer>` adds a later membership for a person who has already signed in — the stopgap that makes the verifier a member until P1's invitations exist.

With them, one runbook procedure lands the first client: staging first, with Matthew Burgess's account created and signed in and the owner signed in beside him, the bundle imported and read back, then staging wiped; then production the same way, the owner as the running Admin and Matthew a member as the verifier, more members added when the client is ready. The real bundle gains the `manifest.yaml` it still lacks before either run. Provisioning's and the membership's audit rows land in the new workspace's own ledger (ADR 0038); the operator's own identity behind the command stays a log line, and ADR 0009 records that deferral with a date.

## User Stories

### Provisioning

1. As an operator, I want one `pnpm ops provision-workspace` command taking a name, a slug and the first Admin's email, so that a client's workspace comes into being without me touching the database by hand.
2. As an operator, I want the command to refuse `no-such-user` when the named person has not signed in, and to say so in a line that tells me to have them sign in with an email code first, so that a workspace is never created around a person the identity set does not hold.
3. As an operator, I want the command to refuse a slug another workspace already holds, naming the refusal, so that two clients never share an address.
4. As an operator, I want the command to print the workspace id it minted, so that I can pass it to `add-member`, `import-bundle`, `smoke` and `reconcile-watermark` without reading the database.
5. As an operator, I want provisioning to be one transaction — the workspace row, its partition, the first membership, its configuration and its audit row, or nothing — so that a failure half-way leaves no half-workspace.
6. As an Admin provisioned this way, I want my membership to be the Admin role with a minted id like every other membership, so that nothing about a first membership is special once it exists.

### Membership

7. As an operator, I want one `pnpm ops add-member` command taking a workspace id, an email and a role, so that I can make a signed-in person a member of a client's workspace before the People screen exists.
8. As an operator, I want `add-member` to refuse `no-such-user` for a person who has not signed in, `no-such-workspace` for an id that is not a workspace, `already-a-member` for a person the workspace already holds, and a usage line for a role that is not Admin, Editor or Viewer, so that every wrong input is named and nothing is written.
9. As an operator, I want a repeat of `add-member` to be refused rather than to change the role, so that a role change stays the Admin's act on the People screen (P1) and never happens by accident from the command line.
10. As a verifier named in the bundle's files, I want to be a member before the import runs, so that the loader accepts every `verified` event that names me and readers see *Checked by* my name.
11. As the running Admin of the import, I want to be a member with the Admin role, so that `import-bundle --as` accepts me and every commit and ledger row carries my name and person id, never the platform's.

### The ledger

12. As an auditor, I want provisioning's row and each membership's row in the new workspace's own ledger under the platform's actor id, carrying the person id and the role word and never an email or a name, so that the workspace's history starts with who was let in and by what.
13. As an auditor, I want ADR 0009 to say by date that the operator's own identity behind a command, and every other workspace-less act, stays a log line until the identity-set ledger lands with T-028, so that the gap is recorded and not forgotten.

### Landing the first client

14. As an operator, I want a runbook procedure that takes me from an empty staging to the client's bundle imported and read back, and then the same on production, so that the first client is landed by following a page and not by remembering a conversation.
15. As an operator, I want the real bundle to carry its `manifest.yaml` before the first run, with a ULID minted once, so that the loader accepts the tree and the bundle's id never changes between staging and production.
16. As an operator, I want to rehearse the real bundle on staging with real sign-ins for the two people the run needs, and to wipe staging afterwards, so that production's run is the second time I have done it.
17. As an operator, I want the import's closing numbers — landed, skipped, checks, links, seconds — written into the estate-size record C1 asks for, so that the first measurement of a real client exists.
18. As a client writer, I want to `find` and `open` my company's approved answers through the MCP surface once the production run is done and I am a member, so that the loader's promise reaches me.

### What is refused

19. As an operator, I want every refusal to name its word and, where the remedy is a person's act, to say what to do next, so that a refused command is a step and not a dead end.
20. As an operator, I want `provision-workspace` and `add-member` to leave nothing behind when refused, so that a rerun after the fix starts clean.

## Implementation Decisions

### The owner's three answers of 22/09/2026

- **Nobody else needs to get in before P1.** The pull-forward makes exactly two people members — the running Admin and the verifier — and further members are added with the same command when the client is ready, or through P1's invitations once T-027 lands (its own session). Invitations, role change and removal are not built here.
- **The staging rehearsal is against the real bundle with real sign-ins.** Matthew Burgess's account is created on staging and signed in; the owner signs in beside him; the bundle is imported and read back; staging is wiped afterwards. This overrides the runbook's line that a rehearsal that is not a drill uses the synthetic fixture: the first client's rehearsal may hold the client's bundle on staging for the rehearsal's duration by the owner's say-so, and the runbook says so where that line stands.
- **The running Admin is the owner, `liam.jons@phew.org.uk`**, on staging and on production, reading only what they already hold as the platform's developer; a further member account for the client's own administration is created when the set-up is ready. Matthew Burgess is a member as the verifier.

### The two commands

- Both commands live at the `runOps` seam, dispatched like `replay-erasures` and `smoke` rather than through the table-presence check the slice commands go through: the identity set's tables always exist, so neither can answer *not built* (T-028's line 3, owner 04/09/2026). Both keep the runner's contract — usage on a missing or malformed flag, `REFUSED — <word>` and a stop on a refusal, one `done —` line on success — and its exit codes.
- `provision-workspace` takes `--name`, `--slug` and `--admin <email>`. It mints the workspace id, resolves the email to the person's user row case-insensitively as the loader and the import already do, and calls the workspaces slice's existing provisioning act under the platform principal the runner holds. The act's refusals cross as themselves: `no-such-user` (the person has not signed in; the line says to have them sign in with an email code and run again), `slug-taken`, `malformed`. The done line carries the workspace id, the slug and the Admin's email, the id first because the operator copies it.
- `add-member` takes `--workspace <id>`, `--email` and `--role`. The role is parsed against the platform's three role words at the boundary, so a fourth word is usage, never a refusal. It calls a **new act on the workspaces slice**, beside provisioning and under the same platform principal: the platform adds a signed-in person to a workspace with a role. The act reads before it writes — the workspace exists (`no-such-workspace`), the person exists (`no-such-user`), the pair is not already a membership (`already-a-member`) — inside the identity write, and writes the membership row with a minted id and its audit row in one transaction. A repeat is `already-a-member` and writes nothing; changing a role is P1's Admin act and is refused here by that word. The act sits in the workspaces slice, not the members slice, because it is a platform act like provisioning, and the members slice holds the Admin's acts over people.
- The two acts declare their refusal words once, in the shape the refusal registry T-231 is landing takes; `no-such-user`, `slug-taken`, `malformed` and `no-such-workspace` are words the tree already speaks, `already-a-member` is new and is the conflict class.

### The ledger

- Provisioning already writes `platform.workspace.provisioned` in the workspace it creates (ADR 0038, owner 05/09/2026). The membership act writes one row the same way — `people.member.added`, declared by the workspaces slice, actor the platform's own id, detail the person id and the role word, never an email — in the same transaction as the membership row, as the audit rules require.
- **The identity-set ledger is deferred, by date.** ADR 0009 gains a dated amendment saying that the operator's own identity behind an ops command, and every other act with no workspace, stays a log line — the runner's own output names the command, the workspace and the outcome — until the identity-set ledger lands with T-028, which now holds every remaining line of P2. The amendment records a deferral and moves no live conclusion, so the index row stays as it is.

### The real bundle's manifest

- `.planning/client-bundle/knowledge/manifest.yaml` is written by a person, once, before the staging run: `id` a ULID minted once and never changed between staging and production, `origin: company`, `ref` the four libraries' titles and versions as `REPORT.md` names them, `owner` as ADR 0002 defines the key, `content_version` the first. The bundle's own checker still passes with the manifest beside the concepts, since it enumerates concept files and the manifest is not one. The manifest travels with the tree when it is copied to the box.

### The runbook

- One new procedure, *Provision the first client and land its bundle*, beside *Import a company's bundle*: the pre-flight gates (T-209 merged, so a path another writer holds refuses before the commit; the rewind command T-108 built; the bundle's checker green with the manifest present); staging brought up; the two people signed in with an email code; `provision-workspace`, then `add-member` for the verifier; the tree copied to the box; `import-bundle --dry-run`, then the run; `smoke --find` and an `open` through the MCP surface; the closing numbers recorded; staging wiped by the drill's own wipe. Then production, the same steps, the numbers into the estate-size record. The sentence that says a rehearsal that is not a drill uses the synthetic fixture gains the owner's exception for the first client's bundle, dated.

### What T-028 keeps

- T-028 keeps the operator principal kind, the admin plugin's migration and its adversarial pass, the disabled paths, `/admin/list-users` and its ADR 0009 amendment, revoke everywhere, the console's screens and the identity-set ledger. Its body gains one line saying its lines 3 and 4 landed here.

## Testing Decisions

A good test drives the behaviour through the interface a caller uses and asserts what that caller can observe — the lines, the exit code, the rows, the ledger, the next command working — never the act's internals; real Postgres always; setup through the factories; expected values written as literals, as the testing rules require.

- **The `runOps` seam, first and highest** (prior art: the ops suite's `import-bundle`, `replay-erasures` and `erasure-rehearsal` blocks). `provision-workspace`: done with the id, slug and Admin on the line and the workspace, partition, membership, configuration and ledger row readable afterwards; `no-such-user` for an email no user row holds, with nothing written; `slug-taken`; usage on a missing flag. `add-member`: done for each of the three roles; `no-such-user`, `no-such-workspace`, `already-a-member` on a repeat, with nothing written and the ledger unchanged; usage on a fourth role word. **The chained case**: `provision-workspace`, then `add-member` for the verifier, then `import-bundle` over the fixture bundle, the two new commands standing where the harness's own provisioning and membership builders stand today, and `find` reading back *Checked by <the verifier's name> · imported*.
- **The workspaces slice's interface** (prior art: the workspaces suite's provisioning cases): the new membership act's refusal table and the shape of its ledger row — the family, the actor, the detail's two fields and no third.
- **The docs gates** for the runbook and the ADR amendment; the ADR index test says the row did not move.
- Nothing is mocked; the platform principal is the one the runner already holds for its other commands.
