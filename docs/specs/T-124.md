## Corrections to carry — fold into the next iteration that starts

**The four beyond-use dates are calendar intervals, not day counts** (the orchestrator, 11/09/2026, correcting iteration 2). Iteration 2 counted them in days, six months included, reasoning that the object store's lifecycle rule has no notion of a calendar month. That is wrong for the reason that matters:

- `deploy/backup.sh` writes each dump's `backup_run.expires_at` as `now() + interval '<life>'` with the tier's lifetime spelled **"48 hours", "30 days", "8 weeks", "6 months"** — Postgres month arithmetic.
- A report counting 180 days would therefore **disagree with the platform's own row for the same copy by up to three days**, and O1's anchor-from-`backup_run` would print a date that is not the row's.

So: compute the four dates **as Postgres does** — the same instant one interval on, a month landing on the same day-of-month or the target month's last day, which is **exactly the rule `dueDateOf` already states** (T-123). Reuse core's one implementation of that rule rather than writing a third copy of it.

Three places change:
1. The date arithmetic behind `erasureReportOf` / the `erasure_request` row's four `beyondUse*At` columns.
2. **The routine's docblock** says it plainly: *the report's date is the row's promise, and the bucket's lifecycle rule — set by hand in days — is configured no shorter than it.*
3. **The schema factory's copy** is fixed to match. The schema's tests cannot import `core`, so the factory states the same rule in its own line and the two docblocks name each other — the pattern T-123 established for `dueDateOf` and the `subjectRequest` seed.

Iteration 7's **ADR 0020 amendment carries this in its anchor item**, not as a separate item.

### 6 — The replay copy

Step 10, acceptance line 10's second half.

**The ordering, ruled by the orchestrator 11/09/2026:** the copy is written **before** step 11's completion commits. **One** clock reading for the completion instant, used twice — the copy carries it, then the row commits with the same instant, so the two can never disagree. If the run dies between them, a copy without its row is a re-run's input and nothing else: the routine is idempotent and the replay reads the copy, which is exactly the case the copy exists for. The other order risks **no copy at all**, silently losing the erasure to a restore from a dump older than the request — the precise failure the copy exists to prevent.

The spec's *"the routine's last write"* means **the last of the routine's writes to the object store**, not the last write of the routine overall. The docblock says the order and why, because the spec's sentence is what will make the next reader think the code has it backwards.

**The asymmetry with the report is deliberate and the docblock says so:** the report is a document handed to a person and is starved of the identifier set and the pseudonym (iteration 2); the copy is the input to a re-run and carries both.

- Written through the door founded in iteration 1, under a **platform prefix**, as the routine's last write: workspace, the subject's person id where one exists, the pseudonym, `completed_at`, the identifier set the suppressions were written from, and the map.
- It holds nothing a finder does not need — asserted both ways: what must be there is there, and the things a finder never reads are absent.

Suite: `erasure-routine.test.ts` + `objects.test.ts`.
