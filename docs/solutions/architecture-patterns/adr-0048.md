status: accepted
title: "An Admin or the operator confirms a second factor before anything else, by a gate derived on every request"
applies_when:
  - "Adding a tRPC procedure, an api route or a Better Auth plugin endpoint a signed-in browser reaches"
  - "Adding an action that makes a person an Admin or the operator, or removes a second factor"
  - "Changing what a session's confirmation stamp, pending clock or setup grant means"
---

An Admin in any workspace must hold a second factor, and so must the operator. A session of such a person is pending until it confirms a second factor.

A pure kernel predicate, `standingOf`, derives the session's standing afresh on every request. A gate sits at every root a browser reaches. The gate lets a pending session reach the pending set of routes and nothing else.

Better Auth's two-factor plugin intercepts only its own password sign-in. Email-code, passkey, and social sign-in each mint a full session, so the gate has to be the platform's own.

## Rejected

- Turning on the two-factor plugin's own flow. It covers password sign-in alone, and its verify step mints a new session.
- A `pending` column. It goes stale whenever a change made elsewhere alters the person's standing.
