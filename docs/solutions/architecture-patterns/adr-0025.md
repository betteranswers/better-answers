applies_when:

  - "Adding code that calls a model"
  - "Reaching for a metrics store, a scrape or a dashboard product"
---

A signal is a named query over rows the platform already keeps. Its threshold is a config row that an Admin changes on the System page. The platform has no metrics store, no scrape, and no dashboard product.

Every model call writes one `llm_call` row. The row holds the call's tokens, its seconds, and its priced cost, and never the prompt or the completion. The spending limit, the price drift check, and replay spend all read these rows.

Every signal that a sync emits is already a row or a count over rows, so no instrumentation is needed. A threshold in code would make every change to it a release.

## Rejected

- A metrics store now, such as VictoriaMetrics or Prometheus with Grafana. It needs 0.5 to 1 GB on a 4 GB box and a second login, and a restore does not bring its signals back.
- Spend derived from _Questions asked_ and the syncs' job rows. That misses enrichment and embedding calls, and it cannot price a sync while it runs.
