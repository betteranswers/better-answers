---
status: accepted
title: "Trust is derived from the file, told in fixed words, and moved only by a verification"
applies_when:
  - "Showing a concept's trust word or rider to a reader"
  - "Checking a concept, or computing or comparing its content hash"
  - "Writing, importing or erasing an actor id in a concept file"
---

Everything the platform tells a reader about a concept's trust is derived from the concept's OKF file, by the spec's own rules. The platform never stores it. It is told in a closed set of words. Only a verification moves it, and the verifier must be someone other than the generator.

If the platform showed a word that another reader of the same file could not derive, the platform would disagree with the bundle it exports.

Both tiers must compute the same content hash, so the hash is a specification. It is SHA-256 over the RFC 8785 canonical JSON of the frontmatter without its trust and identity keys, followed by the normalised body. `contracts/concept-file/cases.json` holds the exact form that both tiers test against.

## Rejected

- The platform writing `stale_after` on every verification. That would put platform policy in the file as if it were knowledge.
- Opaque per-member ULIDs in the file. A reader of the raw file wants the email, and the erasure map carries the cost of keeping it.
