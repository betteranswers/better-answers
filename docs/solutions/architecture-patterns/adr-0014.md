---
status: accepted
title: "Records attach to concepts by IRI, are versioned where edited, and audited in one audit log"
applies_when:
  - "Adding a record family or a table that refers to a concept"
  - "Writing an action that must leave an audit event"
  - "Adding a version table for text a person edits"
---

A record attaches to a concept by `(workspace_id, iri)`, a composite foreign key to its `concept_identity` row, and never restates it. A saved list inside a column cannot be a foreign key, so a changed concept would reach its write-ups by a scan or not at all. Only text a person edits gets a version table, append-only with no status or current flag, because a version table with a mutable flag is not append-only, and every action lands in one audit log per workspace (ADR 0038 holds its shape).

## A copy is a usage row, not an audit event

Taking a write-up out of the platform writes one `usage` row per write-up version taken, naming the version, the act and who took it, and never the text. A copy is not an Admin action, a governed write or a platform action, so it writes no audit event. The `usage` table belongs to the `usage` slice, which imports only the kernel and the doors, so the guides and concepts slices can record a use without a cycle through `answering`.

## A guide snapshot is a usage row, and an export is an audit event

Exporting a guide's prose takes each write-up version out of the platform, so it writes one `usage` row with act `exported` per version carried. The export itself is an Admin action, so it also writes one audit event, in the same transaction as its usage rows. A snapshot of the knowledge base writes an audit event and no `usage` row, because it takes no one concept into a document.

## Rejected

- One generic JSON version table, or before-and-after in audit payloads: no types, and a history a UI cannot list, diff or restore.
- Per-action audit tables: a union across tables, nothing queryable by target.
