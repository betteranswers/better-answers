status: accepted
title: "Personal data is withheld at the redaction seam, and erasure rewrites what the platform wrote"
applies_when:
  - "Adding a step that reads a document's text before splitting, embedding, extraction or a model call"
  - "Changing a redaction rule, a descriptor, the window rule or what a finding row holds"
  - "Touching the erasure routine, a subject request, a suppression or the replay copy"
  - "Adding a store, a column or a copy that could hold a person's identifier"
  - "Sending a model text a person typed, such as a question or a note"
---

The redaction seam withholds personal data in the worker's conversion step, before splitting, embedding, extraction and every model call, so no derived store and no model ever holds the value, whatever a later predicate or prompt does with the text. Text a person types skips the seam and goes through the api's `checkTypedText`, which withholds the always tier's patterns but not names. The erasure routine rewrites every actor id the platform wrote, in files, git history and rows, to a per-workspace pseudonym, except in the append-only audit log, and leaves text the company wrote for a person to edit.

## Rejected

- Quarantining flagged documents, or gating their passages by role. The useful file is the flagged one, and the value would still reach every store.
- Rewriting history every time someone leaves, or never. The first makes every clone diverge, and the second leaves "we cannot" as the only answer to an erasure request.
