title: "Personal data is withheld at the redaction seam, and erasure rewrites what the platform wrote"
applies_when:
  - "Adding a step that reads a document's text before splitting, embedding, extraction or a model call"
  - "Changing a redaction rule, a descriptor, the window rule or what a finding row holds"
  - "Touching the erasure routine, a subject request, a suppression or the replay copy"
  - "Adding a store, a column or a copy that could hold a person's identifier"
  - "Sending a model text a person typed, such as a question or a note"
---

The redaction seam withholds personal data at two points: the worker's conversion step and the return of the read-live tool. Both come before splitting, embedding, extraction, and every model call. No derived store and no model ever holds the withheld value. The original bytes stay in the object store, and only an Admin can read them.

Text that a person types does not pass through the seam. It goes through the api's typed-text check instead. That check withholds the patterns of the always tier, and it does not withhold a name.

The erasure routine rewrites every actor id that the platform wrote to a per-workspace pseudonym. The rewrite covers files, history, and rows, except the append-only audit log. Text the company wrote is different. A person edits it.

A placeholder written before splitting is the one control that still holds whatever a predicate, a prompt, or an assistant's context later does with the text.

## Rejected

- Quarantining flagged documents, or gating the passages by role. The useful file is the flagged one, and the value would still reach every store.
- Rewriting history every time someone leaves, or never rewriting it. The first makes every clone diverge. With the second, the only answer to an erasure request is "we cannot", and that is not a basis for refusing it.
- A targeted text replacement over concept bodies. It would rewrite what the company asserts.
