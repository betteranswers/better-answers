A write-up's prose is stored as markdown. Every claim that rests on a concept carries a footnote reference labelled with the include's id. The include row holds the IRI, the chosen wording, and the content hash. Footnote definitions are rendered from those rows and never stored.

The guide page promises three things: the passage beside the claim, the contradiction check at the sentence, and a copied text that keeps its citations. All three need a mark in the stored prose that survives editing.

## The editor

The concept editor reads and writes this markdown. Visual mode is Tiptap 3 with its markdown extension. Source mode is CodeMirror 6, one key away. In the visual editor, a footnote reference is a node of its own, so `[^source-1]` comes back exactly as it went in. If the visual editor would change any part of a body, the body opens in source mode and the editor says why.

Saving is explicit. A client draft in `sessionStorage` keeps unsaved text, and the editor asks before the person leaves a page with unsaved changes.

## The Brief editor and the page profile

The Brief editor places and removes footnote markers. It never changes include rows. A deleted marker leaves its include in place, and the editor shows that include as "not placed". A Brief save therefore never regenerates the guide's skeleton.

The renderer's page profile numbers markers from 1 in order of first appearance. It drops a marker when the reader cannot read its include, or when its concept has no index row. The markers after a dropped one are renumbered, so the numbers have no gap.

## The clipboard profile

The renderer's clipboard profile returns the Brief in two forms: HTML with superscript numbers, and plain text with bracketed numbers. Each form ends with a **Sources** list. An entry in the list names the concept's title, the sources the concept cites with their locators, and the wording used. An entry for a concept that cites nothing says "No source recorded".

An entry leaves out any source that is another concept or a passage of a connected source. Neither means anything outside the platform. Neither form carries a trust word or a link back to the platform.

Numbers restart at 1 in each copy. A number that names no footnote is dropped, so every number in a paste has an entry. The HTML is built from the parsed markdown and never from the markdown as text, so raw markup shows as text. A link keeps only an `http`, `https`, or `mailto` address.

The paste matrix has two halves. The browser suite proves that the clipboard holds both forms. It also proves that a paste into an editable region and a paste into a plain field keep the superscripts and the brackets. The suite cannot reach Word on the desktop, Word on the web, Google Docs, or Word's **Keep Text Only** paste. The operator pastes into each of those by hand in the review gate.

## Rejected

- A markdown link on the claim, pointing at the concept's IRI. Every cited phrase becomes a hyperlink, and nothing can say which wording or which version it cites.
- Footnote definitions stored in the prose. Every rename would leave a stale title and source.
- A rich-text editor that stores JSON or HTML. One text would have two formats.
- An editor with source mode only. The Expert and the Commercial Controller type prose, not markdown.
