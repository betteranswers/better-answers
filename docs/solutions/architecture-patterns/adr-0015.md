A write-up's prose is stored as markdown, and every claim that rests on a concept carries a footnote reference labelled by the include's id. The include row holds the IRI, the wording chosen and the content hash, and footnote definitions are rendered from those rows and never stored. The guide page promises the passage beside the claim, the contradiction check at the sentence and a copied text that keeps its citations, and all three need a mark in the stored prose that survives editing.

## The editor

The concept editor reads and writes this markdown. Visual mode is Tiptap 3 with its markdown extension, and source mode is CodeMirror 6, one key away. A footnote reference is a node of its own in the visual editor, so `[^source-1]` comes back as it went in. A body opens in source mode when the visual editor would change any of it, and the editor says why. The save is explicit, a client draft in `sessionStorage` keeps unsaved text, and leaving the page with unsaved changes asks first.

## The Brief editor and the page profile

The Brief editor places and removes footnote markers and never changes include rows. A deleted marker leaves its include in place, and the editor reads that include as "not placed". A Brief save therefore never regenerates the guide's skeleton. The renderer's page profile numbers markers from 1 in order of first appearance, and it drops a marker whose include the reader cannot read or whose concept has no index row, renumbering past it so the numbers leave no gap.

## Rejected

- A markdown link on the claim pointing at the concept's IRI: every cited phrase becomes a hyperlink, with nowhere to say which wording and which version.
- Footnote definitions stored in the prose: a stale title and source on every rename.
- A rich-text editor storing JSON or HTML: two formats for one text.
- A source-only editor: the Expert and the Commercial Controller type prose, not markdown.
