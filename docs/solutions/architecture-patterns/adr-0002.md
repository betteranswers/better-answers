status: accepted
title: "A concept is identified by an opaque platform-minted IRI, a bundle by its manifest"
applies_when:
  - "Minting, storing or reading a concept's IRI"
  - "Writing a link from one concept to another, in the same bundle or another"
  - "Reading or adding a field of a bundle's manifest"
  - "Putting an okf:// URI anywhere other than an MCP message"
---

OKF identifies a concept only by its path inside a bundle, and it gives a bundle no identity at all. The platform adds both. When it creates a concept, it mints an IRI of the form `https://better-answers.com/c/<ulid>` and stores it in the concept file under the code-owned `iri` key. A bundle is identified by the `knowledge/manifest.yaml` file at its root.

The IRI is the one key that can never be re-keyed, so its form was fixed before anything was built on it. It is opaque on purpose. An IRI derived from a name would carry that name into every place the IRI is copied.

## Rejected

- Identity by path alone, with a platform log of renames. Verification history and cross-bundle references would re-key on every move.
- An `okf://` URI or a `cross_refs:` key for references inside a file. Either one needs a resolver in every reader, or link checkers cannot see it.
