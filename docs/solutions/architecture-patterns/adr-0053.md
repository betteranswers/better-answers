applies_when:
  - "Writing a test, and choosing whether it runs in-process, on a real store, as a process or image, in a browser or on the schedule"
  - "Adding a store door, or a slice that reads or writes through one"
  - "Adding a browser spec, or a regression test for a bug a page shows"
---

A test sits at the lowest of five layers that can see its claim: in-process, a real store, a process or image, a browser, or a scheduled reading. A real store is used only where the store is the claim, such as row-level security, migrations, the SQL a slice runs, locks and races, and the tier contract's SQL agreements. When every test used the real stores, the suites' time went to seeding, process launches and browser tests, not to claims about a store. A decision over rows a slice has already read is a pure function tested in-process, so the store doors stay concrete and the unit layer needs no fake store.

## Rejected

- PGlite as an in-process Postgres. It has one backend, so two clients share a pid, a role and an advisory lock, and a lock or race test passes without testing anything.
- In-memory store doors behind ports. A fake Postgres door cannot reproduce row-level security, recursive walks or locks.
- Module mocks. The `anti-slop/no-module-mocking` lint bans them, and the injected seams such as the clock and the model client's `fetch` carry the unit layer.

## Consequences

- Each folder under `packages/core/test` mirrors one directory under `src/`, and reaches any other directory only through an `index.ts` the `exports` map names. The `import-direction` lint rule enforces this layout.
