title: "The tier contract is a list of agreements in three forms, each proved by both tiers' suites"
applies_when:
  - "The api and the worker both read or write the same value, list or format"
  - "Adding a fixture, a SQL function or an agreement under contracts/"
  - "Changing a queue function, the credential envelope or the shape of an id"
  - "Deploying a schema or contract change the worker has to match"
---

Some answers must be the same in the api and the worker: a value, a list, or a format. Each such answer is an agreement in the top-level `contracts/` directory. An agreement takes one of three forms:

- a SQL function that both tiers call
- a golden fixture that both test suites read
- rows generated from one source

Each tier's suite proves every agreement from its own side. When the tiers disagree, the failure lands in the tier that diverged.

The contract's version is a digest of the `contracts/` directory. `migrate` stamps the digest into the database. The worker compares the stamp with its own digest before it claims a job.

Two codebases that implement the same prose drift apart. One survey found a shared helper at 39 lines in one repository and 115 in the other.

## Rejected

- A pnpm package named `contracts`. The Python tier cannot read it.
- One suite, in a third workspace, that boots both tiers. It cannot name the tier that diverged.
