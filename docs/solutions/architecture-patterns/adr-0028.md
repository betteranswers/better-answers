title: "A boundary schema is generated from its table and a refinement only narrows it"
applies_when:
  - "Adding a table, or a column to one, in packages/schema"
  - "Validating a row or an input against a table's shape with zod"
  - "Branding an id or narrowing the values a column accepts"
---

`drizzle-zod` generates every zod schema over a table, and it runs in `packages/schema` alone. Each table gets a select, an insert, and an update schema. A refinement is a per-column callback that may only narrow its column. A parity test against a real Postgres proves that each refinement narrows.

The callback form matters. A refinement written as a plain schema replaces the whole column and drops its nullability at runtime. The select schema then rejects a row that Postgres returned legitimately.

The types never check a refinement against its column. Without the parity test, a retyped column or a widened enum fails nothing.

## Rejected

- Hand-written zod schemas beside the tables. They drift from the tables, and this decision exists to stop that drift.
- Generated schemas with no refinements, narrowed at each boundary. Every caller would re-derive the branded id and the ULID check, and each caller would do it differently.
