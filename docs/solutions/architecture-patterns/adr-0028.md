status: accepted
title: "A boundary schema is generated from its table and a refinement only narrows it"
applies_when:
  - "Adding a table, or a column to one, in packages/schema"
  - "Validating a row or an input against a table's shape with zod"
  - "Branding an id or narrowing the values a column accepts"
---

Every zod schema over a table is generated from the table by `drizzle-zod` in `packages/schema` alone, in select, insert and update shapes, and a refinement is a per-column callback that only narrows, proved by a parity test against a real Postgres. A plain-schema refinement replaces the column wholesale and drops nullability at runtime, so a select schema rejects a row Postgres legitimately returned. The types never check a refinement against its column, so a retyped column or a widened enum fails nothing without the parity test.

## Rejected

- Hand-written zod schemas beside the tables: the drift this decision exists to close.
- Generated schemas with no refinements, narrowed at each boundary: every caller re-derives the brand and the ULID check, differently.
