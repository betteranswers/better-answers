title: "Better Auth runs in-process as the api's own authorization server, behind a seam"
applies_when:
  - "Importing better-auth, or reading a Better Auth table, anywhere outside the auth modules"
  - "Running work that outlives a person's session, such as a job, a scheduled run or a replay"
---

Better Auth runs in-process as a library, and the api is its own OAuth 2.1 authorization server for the MCP surface and the email-code sign-in for the SPA, behind a seam no Better Auth type crosses. A transport verifies a bearer and builds a `Principal` of one of three kinds, a user principal, the platform principal or the operator, and work that outlives a session (a job, a scheduled run, a replay) runs under the platform principal or a deferred principal that records whose authority it borrowed, never under a live session. Every container is an operational cost paid for good, and the library adds no process, no second backup and no second migration owner, while the seam keeps `packages/core` testable without the library.

## Rejected

- Keycloak: about 1.25 GB, a third-party extension for email-code sign-in, and configuration outside the repository.
- Supabase Auth: moves the database's home and adds a second migration owner.
- The MCP SDK's own OAuth helpers: Express-only and frozen.
