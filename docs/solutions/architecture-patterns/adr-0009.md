title: "Better Auth runs in-process as the api's own authorization server, behind a seam"
applies_when:
  - "Importing better-auth, or reading a Better Auth table, anywhere outside the auth modules"
  - "Running work that outlives a person's session, such as a job, a scheduled run or a replay"
---

Better Auth runs inside the api process as a library. With it, the api is its own OAuth 2.1 authorization server for the MCP server, and it runs the email-code sign-in for the SPA. Better Auth sits behind a seam, and no Better Auth type crosses it.

A transport verifies a bearer token and builds a `Principal` of one of three kinds: a user principal, the platform principal, or the operator. Work that outlives a session, such as a job, a scheduled run, or a replay, never runs under a live session. It runs under the platform principal, or under a deferred principal that records whose authority it borrowed.

Every container is an operating cost paid for good. The library adds no process, no second backup, and no second migration owner. The seam keeps `packages/core` testable without the library.

## Rejected

- Keycloak. It is about 1.25 GB, needs a third-party extension for email-code sign-in, and keeps its configuration outside the repository.
- Supabase Auth. It moves the database's home and adds a second migration owner.
- The MCP SDK's own OAuth helpers. They work only with Express, and they are no longer developed.
