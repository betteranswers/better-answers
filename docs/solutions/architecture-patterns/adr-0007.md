status: accepted
title: "Plain Postgres, with the api owning every migration and all DDL"
applies_when:
  - "Adding or changing a table, index, partition or constraint, in public, index or the map"
  - "Letting the worker or cocoindex create, drop or alter anything in the database"
  - "Changing how a workspace's passage partition is made at provisioning"
  - "Proposing Supabase, Neon or another database host"
  - "Writing a migration that renames, takes a lock writers wait on, or writes a tenant table's rows"
---

The database is one plain, self-hosted Postgres with pgvector, and the api owns every migration and all DDL in `public`, `index` and the map. Two tiers writing one schema with two migration tools would break ADR 0005's data contract, so the worker treats the schema as read-only and every cocoindex target sets `managed_by=ManagedBy.USER`. Under the engine's default, deleting one connected source could drop `index.passage` for every other source.

## Consequences

- A migration that takes a lock writers queue behind first runs `SET LOCAL lock_timeout = '5s'`. A failed migration can be run again, and the writers stuck behind its lock cannot.
- A migration writes a tenant table's rows inside each workspace's `set_config` scope, because row-level security is forced.
- A workspace's passage partition is created as its own table and then attached. `CREATE TABLE ... PARTITION OF` holds `index.passage` in ACCESS EXCLUSIVE mode and deadlocks with writers of `source_document`.

## Rejected

- Supabase, self-hosted or hosted. Most of its services would sit idle, and it invites features only Supabase has.
