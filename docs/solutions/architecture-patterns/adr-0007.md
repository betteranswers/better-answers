title: "Plain Postgres, with the api owning every migration and all DDL"
applies_when:
  - "Adding or changing a table, index, partition or constraint, in public, index or the map"
  - "Letting the worker or cocoindex create, drop or alter anything in the database"
  - "Changing how a workspace's passage partition is made at provisioning"
  - "Proposing Supabase, Neon or another database host"
  - "Writing a migration that renames, takes a lock writers wait on, or writes a tenant table's rows"
---

The database is one plain self-hosted Postgres with pgvector, and the api owns every migration and all DDL across `public`, `index` and the map, while the worker treats the schema as read-only and every cocoindex target declares `managed_by="user"`, because the engine's default would let one connected source's deletion drop `index.passage` under every other. Two tiers writing one schema with two migration tools is the failure the data-not-code contract must prevent, so the schema has one author. That author bounds a migration's wait for a lock writers queue behind with `SET LOCAL lock_timeout = '5s'`, reset before the next migration, because a migration has someone to re-run it, writes a tenant table's rows inside each workspace's `set_config` scope because row-level security is forced, and attaches a workspace's passage partition rather than creating it `PARTITION OF`, which holds `index.passage` in ACCESS EXCLUSIVE and deadlocks with writers of `source_document`.

## Rejected

- Supabase, self-hosted or hosted: most of its services would idle, it invites Supabase-only features, and the predecessor's 274 role-keyed policies on a Supabase helper are the cautionary case.
- The worker owning its own tables with Alembic: two pipelines and two migration stamps, the shape the predecessor ended in.
