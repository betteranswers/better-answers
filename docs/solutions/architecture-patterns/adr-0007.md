title: "Plain Postgres, with the api owning every migration and all DDL"
applies_when:
  - "Adding or changing a table, index, partition or constraint, in public, index or the map"
  - "Letting the worker or cocoindex create, drop or alter anything in the database"
  - "Changing how a workspace's passage partition is made at provisioning"
  - "Proposing Supabase, Neon or another database host"
  - "Writing a migration that renames, takes a lock writers wait on, or writes a tenant table's rows"
---

The database is one plain, self-hosted Postgres with pgvector. The api owns every migration and all DDL in `public`, `index`, and the map. The worker treats the schema as read-only.

ADR 0005 makes the contract between the tiers data and not code. Two tiers that write one schema with two migration tools would break that contract, so the schema has one author. For the same reason, every cocoindex target declares `managed_by="user"`. With the engine's default, deleting one connected source could drop `index.passage` for every other source.

A migration that the api writes follows three rules:

- It bounds its wait for any lock that writers queue behind with `SET LOCAL lock_timeout = '5s'`, and it resets the timeout before the next migration. A failed migration has someone to re-run it. The writers stuck behind its lock do not.
- It writes a tenant table's rows inside each workspace's `set_config` scope, because row-level security is forced.
- It creates a workspace's passage partition as a separate table and then attaches it. `CREATE TABLE ... PARTITION OF` holds `index.passage` in ACCESS EXCLUSIVE mode and deadlocks with writers of `source_document`.

## Rejected

- Supabase, self-hosted or hosted. Most of its services would sit idle, and it invites features that only Supabase has. The predecessor's 274 role-keyed policies on a Supabase helper show where that leads.
- The worker owning its own tables with Alembic. That gives two pipelines and two migration stamps, which is how the predecessor ended up.
