---
status: accepted
title: "A secret is stored by who owns it and what the platform does with it, never by a named class"
applies_when:
  - "Adding a secret to either tier's config module or a compose file"
  - "Adding a table or column that holds a token, a key or a sealed frame"
  - "Building a connected source's credential, an acting credential or the share agent's token"
  - "Rotating the envelope key, or deciding what a compromise of one box exposes"
---

The deployment's own secrets stay out of the database. The one exception is Better Auth's signing keys, which Better Auth keeps encrypted in its own table. Where a deployment secret lives depends on what reads it:

- A process in either tier reads it once from its environment, through that tier's config module.
- A container outside the two tiers reads it from its own environment.
- A host job or a mounted service reads it from a file that only root can read.
- A secret that no box may hold stays in escrow.

A workspace's or a person's secret never comes from the environment. It is a row the worker cannot read, protected by row-level security or by revoked grants. The platform seals the secret under the envelope key if it sends the secret onward. It hashes the secret if it checks the secret when someone presents it.

The seven named credential classes are retired. They mixed target systems, purposes, and a lifecycle. Nothing in code could enforce a list of names, but a column type, a config reader, and a lint can each enforce a shape.

## Rejected

- One `credential` table with a `class` column. A class is a name a row carries, not a shape the schema enforces.
- `repository` and `object store` as classes. Each named a target system that held secrets of several shapes.

## Consequences

- Better Auth's tables keep the library's own conventions behind ADR 0009's seam. That includes its JWT signing keys, which Better Auth encrypts under the auth secret.
