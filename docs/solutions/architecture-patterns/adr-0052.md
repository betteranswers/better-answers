---
status: accepted
title: "A secret is stored by who owns it and what the platform does with it, never by a named class"
applies_when:
  - "Adding a secret to either tier's config module or a compose file"
  - "Adding a table or column that holds a token, a key or a sealed frame"
  - "Building a connected source's credential, an acting credential or the share agent's token"
  - "Setting, reading or rotating a workspace's model key, or rotating the envelope key"
---

A deployment's own secrets stay out of the database, except Better Auth's signing keys, which Better Auth encrypts in its own table. A process reads a deployment secret from its environment through its tier's config module, a host job reads it from a root-only file, and a secret no box may hold stays in escrow. A workspace's or a person's secret is a row the worker cannot read. The platform seals it under the envelope key, which only the api holds, if it sends the secret onward, as with a model key. It hashes the secret if it checks the secret when someone presents it. A column type, a config reader and a lint can enforce a shape, and nothing can enforce a list of class names.

## Rejected

- One `credential` table with a `class` column. A class is a name a row carries, not a shape the schema enforces.

## Consequences

- No command re-seals the model keys. After the envelope key changes, every workspace sets its model key again, and after a compromise every model key is reissued at its provider.
