status: accepted
title: "Concept types emerge from the concepts; a link is the relation and is never named"
applies_when:
  - "Adding a field, a table or a check that lists or validates concept types"
  - "Adding a rename, a merge or an edit to the Concept Types page"
  - "Adding an edge label to the map, or a key to a concept file that names how two concepts relate"
---

A concept's type is the string its producer chose for OKF's `type` key, folded for case and plural by `foldConceptType` when the concept is written. Its name is concept type: `conceptType` in TypeScript, `concept_type` in Postgres, and `type` in a concept file and in MCP output. The Concept Types page counts the types in the concept index under the read predicate and offers no rename or merge. No file declares the types and no check refuses one, because OKF's first non-goal is a fixed taxonomy and a list of types is a registry someone has to maintain.

A relation between two concepts is the markdown link in the concept's body. The map stores it as a `LINKS_TO` edge that carries the link's sentence, and the relation has no name. A named relation would add an edge label to `MAP_EDGE_LABELS` and change nothing on the answer path, because the drafting model reads the link's sentence.

## Rejected

- A list of relations matched against link sentences. It gives a wrong answer with no error when two relations join the same pair of concept types.
