status: accepted
title: "Groups are flat, an access request is answered neutrally, and the audit log is append-only"
applies_when:
  - "Adding a group, a member or a People page field"
  - "Writing an action that lands an audit event"
  - "Changing how a non-member asks to join a workspace, or how an Admin answers"
  - "Porting a page whose fields assume teams, several roles or access that expires"
---

A group is a flat set of a workspace's members, aligned with Entra groups. A group changes only what a person may see, never what they may do. The platform has no teams, no second role per person, no access that expires, and no Suspended state.

A signed-in person who is not a member can ask to join a workspace by its short name. The platform answers every such request with the same neutral acknowledgement, whatever the short name resolves to. If a real workspace and an unknown one got different answers, anyone could use the request to test which workspaces exist.

The audit log, `audit_event`, is an unpartitioned tenant table. The database keeps it append-only, because the migration revokes the privileges to update and delete its rows. An append-only rule enforced in code is a convention the next migration forgets.

## Rejected

- Nested groups, or teams beside groups. Every access check would walk a tree, and teams would be a second concept for one set of people.
- Approving a request through Better Auth's invitation endpoint. Core would then depend on the identity provider.
- Partitioning the audit log by month. Partitioning a table that carries policies changes what the RLS suite proves. The table's row count, not a date, is what reopens this question.
