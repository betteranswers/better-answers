status: accepted
title: "The MCP surface is MCP SDK v2 in apps/api, behind one fetch-shaped seam"
applies_when:
  - "Changing the MCP surface, its entries or the library under it"
  - "Proposing FastMCP, a Python MCP server or an MCP App framework"
  - "Proposing an outbound connector, a sync or a write into a system that is not a connected source"
---

The MCP surface is built on the MCP SDK in `apps/api`. Every request reaches it through one fetch-shaped seam. The seam verifies the bearer token and runs each entry under a `Principal`.

The seam hides the library, so replacing the SDK takes an afternoon. Moving the surface to another tier does not, because the `Principal` and the read predicate live in the api tier.

FastMCP's real advantage is authentication. It is Python-only, and it depends on an OAuth proxy where another party owns the accounts. ADR 0009 makes the platform its own authorization server, so that advantage does not apply here.

The platform builds no connector into a system that is not a connected source. For those systems, the Claude platform is the integrator. It reaches them through the person's own MCP servers, with credentials that Better Answers never holds.

## Rejected

- FastMCP in Python, with the MCP surface moved to the worker. A transport would then sit on the other side of the tier boundary from the `Principal` and the read predicate.
- Outbound connectors, an OAuth client, or a sync engine into third-party SaaS that is not a connected source. A nightly sync with no person in the loop would need its own ADR and its own deployable.
